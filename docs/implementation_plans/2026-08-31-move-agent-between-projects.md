# Move agent between projects (any directory)

> **Supersedes M4 of `2026-08-27-cross-project-operations-and-central-store.md`.** That milestone was scoped to projects sharing one working directory, on the premise that a cross-directory move breaks Claude's `--resume` and could only be fixed by writing falsified records into Claude's private session store. On 2026-08-31 that premise was found stale at CLI 2.1.251 and disproven by live probe: the CLI resumes a session from any cwd through its own fallback chain, appending to the transcript in place. Findings are recorded in `docs/harness-behavior.md` §3.5c — **that section is the authority for the CLI behavior this plan depends on; this plan cites it and does not restate the evidence.** Everything else in the old M4 (the surgery, gating, and recovery design, which went through seven review rounds) is carried into this plan unchanged; the delta is the lifted directory restriction and the one mechanism it requires.
>
> Ships as **one PR**; each milestone is a commit (sub-steps may be their own commits). After finishing a milestone: stop, summarize, wait for review before starting the next. Every commit builds and passes `make check`.
>
> Round-2 (2026-08-31, pre-implementation review; two reviewers + verification, all findings code-verified): **the effective-session-directory convention now enumerates every Claude session-identity consumer** — above all the cross-process session lock, whose Claude key includes cwd by design and would otherwise silently stop guarding a moved agent's transcript (the round's most serious finding). Also: pin partitioning corrected to the canonical `agent:hydration:` key shape (the plan had named only the temporary send-alias shape, which would have left most real pins behind); `session_home` pinned as a stored physical path that consumers must never re-canonicalize (a `DirectoryId` was considered and rejected — it would follow a catalog re-point away from the frozen transcript location; re-canonicalizing strands once the old directory is deleted); move refuses on a canonical target-name collision, closed by holding `registry_write` from the check through surgery rather than widening the maintenance flag; the move gate explicitly distinguished from `begin_maintenance`'s evict-and-auto-release guard; sidecar copies use core's durable atomic writer (existence checks alone miss a crash-truncated destination); both projects' `instance.lock`s are acquired before any file is touched, by moves and by recovery.

## What this builds

From an agent's row actions: **Move to project…**, offering every other project — same directory or not. The agent — same identity, same session, full history including pinned messages — now lives in the target project: its transcript renders there (past failed/cancelled markers included), and its next turn dispatches and journals there, running in the **target project's** working directory. If the app crashes mid-move, the next launch completes it before either project opens. Cross-directory moves are the point of the rescope: moving an agent from a checkout to its worktree (or any other directory) is the primary user-facing win.

Two accepted, user-visible limitations (both must reach the README when this ships — symptom first, per the README's register rules):

- **Attachment images from before the move do not survive it.** Attachments are per-project; the move rewrites journals, so the source project's reference-GC collects the moved agent's staged files on its next load. Recorded `Send.attachments[].path` values are **never rewritten** (send↔turn correlation reconstructs exact dispatched text — see the `align_surplus_candidates` doc comment in `crates/app/src/commands.rs`), so only the file goes: old thumbnails render broken, and asking the agent to re-read one gets file-not-found. The copy-on-move mitigation is recorded in the old plan's attachments decision and deliberately **not built** here.
- **A moved agent's conversation still refers to its old directory.** Its history is full of absolute paths from where it used to run. Inherent to moving a conversation; document, don't engineer around.

## Decisions settled in discussion (do not re-litigate; do not silently deviate)

- **Cross-directory move is in scope, uniformly, for all three harnesses.** Codex and Antigravity sessions were never directory-bound. Claude works because the CLI itself resolves a cross-cwd `--resume` (§3.5c); Switchboard's only obligation is fixing **its own** lookup — `build_args` derives the session-file existence check from the spawn cwd, and after a cross-directory move that lookup misses, passes `--session-id`, and strands the agent permanently (§3.5b's exact signature). The fix is one recorded field consumed by one adapter; there is **no harness-conditional move surface** and **no writing into any harness's private session store**.
- **Resume stays by session id, not by transcript path.** The CLI also accepts a `.jsonl` path in place of an id, but the id form is what the probe and the live canary cover, and the global-scan single-match rule is satisfied because a moved agent's id exists in exactly one encoded directory. Do not switch forms "for robustness" — that changes the depended-on CLI surface without changing the guarantee.
- **The dependency on undocumented CLI fallback behavior is accepted the same way `encode_cwd` itself is:** re-verified per CLI bump (`docs/harness-update-review.md`), with live canaries as tripwires (M2's DoD). If a canary breaks on a bump, cross-directory moves are what's at risk — the canary names must make that legible.
- **A move requires both projects' directories to resolve.** The target's directory is where future turns run; the source's is needed to decide the session-home question. If either `directory_id` is unresolvable, refuse the move with a clear error rather than guessing. (Planner's call, consistent with the move's refuse-don't-improvise posture; the old plan never faced it because same-directory implied one shared resolution.)
- **The quiescence gate exists for the *other* agents' journal writes, not the moved agent's.** Journal appends take no shared lock; any agent in either project completing a turn during journal rewrite would have its record silently lost. Record this rationale in the gate's code — it is the answer to "why block the whole project for one agent's move."
- **Crash recovery is a durable intent record plus idempotent steps — no phase tracking, and no "re-running heals."** The retracted position is worth preserving in the recovery module's docs: individually atomic writes do not make a multi-file operation atomic; a crash after the commit point leaves source-side residue with no trigger to finish, because the agent row you'd re-run from now lives in the target.
- **The move partitions pins; it never prunes them.** A missing or unresolvable session file degrades to an *empty* transcript (`load_transcript_impl`), so "no row" is not evidence a pin is dead; orphan pins are inert. Pruning during a move was considered and rejected as unsafe.
- **Rationale survives into the code.** Every non-obvious decision above (gate rationale, step ordering, session-home rules, the §3.5c dependency, the no-prune rule) lands as a comment or doc comment at the place that embodies it — not only in this file.

## Shared conventions (established where first needed, reused everywhere after)

- **Effective session directory** — `session_home ?? owning project's working directory`, computed by **one** helper. Defined with `session_home` in M1; every consumer is swept onto it in M2. The consumers, enumerated because missing one is silent: Claude `build_args`'s existence lookup; `resolve_session_file` (`crates/app/src/commands.rs` — the documented single path-resolution authority, serving session info, the copy-ready resume command, and freshness fingerprints); `session_lock_keys` (`crates/app/src/dispatch_context.rs` — **both** the own-session branch and the fork-parent branch; `session_lock_key` includes cwd for Claude by documented design, so a lock keyed by the project directory after a move names a session that doesn't exist while the real transcript goes unguarded — quietly disabling the cross-process corruption protection for exactly the moved agents); fork-materialization existence checks; and the session-id collision scans. Anything else deriving a Claude session location from a directory is a defect. The spawn cwd and the resume command's `cd '<dir>'` stay the target project's directory — the CLI resolves from there via §3.5c.
- **Journal-record identity for idempotence** — `(variant tag, turn_id)`. Every current `JournalRecord` variant carries a `turn_id` with at most one of each per turn. `JournalRecord` is `#[non_exhaustive]`; state the key in the journal-ops docs so a future variant without a `turn_id` is forced to define its own identity rather than silently duplicating.
- **Vocabulary** — a *move* is the whole user-initiated operation; the *surgery* is its file-rewriting middle; the *commit point* is the source-registry rewrite (step d), after which the agent's row lives in the target. Use these terms in code and tests.

## M1 — Core: move primitives (`session_home`, registry mutation, journal surgery ops)

### Goal & Outcome

Pure-Rust foundations in `switchboard_core`, with no app or adapter wiring yet.

- `AgentRecord` carries an optional `session_home`: the working directory whose harness-side encoded directory holds this agent's session files, present **only** when it differs from the owning project's directory. Additive and serde-defaulted, so existing registries parse unchanged; additive on the TS wire type too.
- A registry gains one sanctioned way to change an agent's `project_id` (and set `session_home`), following the existing mutate-in-place-then-recache convention (`rename_agent` is the precedent). `AgentRecord`'s doc comment currently declares `project_id` immutable — update it to name this method as the single mutator.
- Journal operations exist to extract one agent's records from a journal and append records a journal lacks, preserving original order and timestamps, deduplicating by `(variant tag, turn_id)` — via `switchboard_core::journal` types, never string-level line filtering.

### Implementation Outline

- `session_home` is a stored physical `PathBuf` — the source project's already-resolved working directory at move time, the exact string dispatch passed as cwd — and its doc comment must carry the full contract, because nothing else in core explains it: set only by a cross-directory move; consumed only through the *effective session directory* convention; once set, never changed by later moves (the transcript never leaves its original encoded directory — §3.5c); absent means "sessions live under the owning project's directory," which is every agent today. Two deliberate negatives belong in that comment because each was proposed in review and each would strand the agent (§3.5b's permanent signature): it is **not a `DirectoryId`** — the catalog exists so a *live* dispatch target follows a user's re-point, but this field records the frozen historical fact of where Claude encoded the transcript (`realpath` at write time; the file never relocates), so following a re-point is precisely the failure the field prevents; and consumers must **never re-canonicalize it** — `session_exists_in` currently canonicalizes its cwd and fails when the path doesn't resolve, so once the old directory is deleted (the pruned-worktree case, the feature's flagship scenario) a re-canonicalizing lookup misses forever. The stored value is already the final string to encode.
- The registry-side adoption primitive (the `project_id` mutator's target half) validates canonical name uniqueness in the target roster (`check_name_unique` semantics: case-insensitive, hyphens as underscores): a duplicate name under a *different* `agent_id` is a typed conflict; the same `agent_id` already present is the recovery no-op. Registration and rename enforce this invariant; a move writing rows in through a path that skips it would create roster states the ordinary APIs forbid.
- The journal ops are the substrate for M4's idempotent steps, so their contracts are: *extract* partitions a journal's records into (moved agent's, everyone else's) — the moved agent's `Send`/`Outcome`/`TurnLink` records, matched by agent attribution; *append-missing* appends only records whose `(variant tag, turn_id)` the target lacks. Both are pure functions over parsed records plus the existing atomic-write path. Re-applying either is a no-op — that property is what M4's recovery leans on, so assert it here, in isolation, per operation.
- Edge to preserve in the method docs (so nobody "fixes" it later): a fan-out `send_id` that included the moved agent and others ends up in **both** journals — each project renders its own copy grouped by `send_id`, which is correct per-project behavior; cross-journal dedup is explicitly not wanted.

### Definition of Done

- Unit tests: registry round-trip with and without `session_home` (absent field parses; unknown-field tolerance unchanged); the `project_id` mutator persists and recaches; adoption refuses a normalized name collision (typed, roster unchanged) and no-ops on an identical already-present `agent_id`; journal extract/append round-trip preserves order and timestamps; append-missing is idempotent (second application changes nothing) including the fan-out-spans-two-journals case; dedup key behavior when the target already has a subset of the records.
- `make check` green.

## M2 — Claude session identity through the effective session directory (adapter + app consumers, + live canaries)

### Goal & Outcome

Every place that derives a Claude session's location from a directory honors `session_home`, and live tripwires exist for the CLI behavior the whole feature stands on. This lands before any move exists so the sweep is reviewable on its own and provably a no-op for every agent without a `session_home`.

- A Claude agent whose `session_home` is set resumes correctly when spawned in a different directory: the session-file existence check looks under the *home* directory while the subprocess still runs in the project's directory — including after the home directory has been **deleted**.
- The cross-process session lock guards the agent's *actual* transcript: a moved agent contends with any other instance driving the same session from its home directory.
- Session info, the copy-ready resume command, freshness fingerprints, and fork gating all report a moved agent's session correctly instead of "absent."
- Two live canary tests pin the §3.5c behaviors so a CLI bump that breaks them is caught by `make test-live-claude` before users hit it.

### Implementation Outline

- Introduce the single effective-session-directory helper and route the enumerated consumer list (shared-conventions section) through it: `build_args`'s existence lookup, `resolve_session_file` (which serves session info / resume command / fingerprints and is called from `session_lock_keys`' fork branch), and `session_lock_keys` — both branches; the fork-parent branch otherwise misclassifies a moved *materialized* fork as unmaterialized and takes the wrong lock. The spawn cwd and the resume command's `cd` target are untouched.
- The lookup path for a `session_home` must **not** re-canonicalize (M1's contract): `session_exists_in` canonicalizes today and fails on a nonexistent path, so the home-directory lookup needs a variant that encodes the stored string directly. The comment at the `build_args` lookup currently asserts lookup-cwd and spawn-cwd must be identical; rewrite it to name the moved-agent divergence and cite §3.5c — that comment is the first thing a future debugger of a stranded agent will read.
- The fork arm needs **no** session-home handling, and a comment must say why so nobody adds it defensively: a moved parent's fork dispatch resumes the parent by id (the CLI's fallback chain finds it), and the CLI writes the child transcript into the **forking cwd's** encoded directory (§3.5c fork edge) — so the child is native to the new directory and the existing spawn-cwd existence check is *correct* for it. Setting `session_home` on a child would make its existence check miss forever and re-fork every turn.
- Live canaries, named per the `live_claude_` convention and shaped like the existing live tests (tiny "ack" prompts):
  - `live_claude_cross_directory_resume_appends_in_place` — create a session in one temp dir, resume from another using the adapter's real arg shape, assert success and that the transcript stayed under the original encoded directory (no second file).
  - `live_claude_cross_directory_fork_lands_in_forking_cwd` — fork a session from a foreign cwd, assert the child transcript appears under the forking cwd's encoded directory and the parent's file is untouched.
- Run `make test-live-claude` before this milestone's review (adapter-touching change; AGENTS.md policy).

### Definition of Done

- Unit tests (existing fixture style, `home_override`): with `session_home` set and the file present under home, `--resume` is chosen even though the spawn cwd's encoded dir is empty — the exact post-move shape; the same holds when the home directory itself no longer exists on disk (the no-recanonicalize contract — fails against today's `session_exists_in`); with `session_home` set but no file anywhere, first-turn/fork arms behave as today; `session_home` absent is byte-identical to current behavior (regression guard over the existing `build_args` suite).
- Lock and app-consumer tests: a moved agent's session-lock key equals the key the same session takes from its home directory (the contention guarantee — fails if the key is derived from the project directory); a moved *materialized* fork takes only its own lock, never the parent's; `resolve_session_file` finds a moved agent's file (session info reports it present, the resume command is offered).
- Both live canaries pass locally; recorded CLI version noted in the test or fixture comments.
- `docs/harness-behavior.md` §3.5c gains a one-line pointer to the canary names (its "re-check on bump" instruction should name the tripwires).
- `make check` green.

## M3 — App: move admission — per-project maintenance flags and the quiescence gate

### Goal & Outcome

Both projects involved in a move can be atomically closed to new work, and a move can verify true quiescence — before any surgery code exists.

- While a project's maintenance flag is set, no turn starts for **any** of its agents: sends are refused at admission, workflow steps at their preflight, and — decisively — queued items at turn start.
- The gate can answer: zero in-flight turns, zero queued sends, zero active workflow runs, for a given pair of projects.

### Implementation Outline

- The flag is checked in **all three** places the mid-turn fork gate checks — `send_message_impl` (send admission), the workflow-step preflight in `workflow.rs` (workflow admission), and **`DispatchContextFactory::preflight`** (authoritative turn-start; name the trait at every mention — a workflow-side function shares the word `preflight`). The third is not optional and not redundant: without it there is a check/enqueue race — a send passes admission, the move sets the flag and observes an empty queue, and the queued send starts mid-surgery. Closing that race is the documented purpose of the start-moment preflight; refusal there leaves no durable trace, which is what a blocked turn wants.
- Set-order contract for M4 to consume: flags are set for both projects **before** re-verifying quiescence (closing the check-then-act window), and cleared **only** on successful completion of a move or of a recovery — never on an arbitrary error path, which would re-enable dispatch into half-moved state.
- The workflow condition matters because a run can hold a *future* step targeting a currently-idle agent — quiescence is about commitments, not just activity.
- **This gate is not `begin_maintenance`, and the distinction must be explicit because reusing the existing guard looks like free leverage and quietly breaks the recovery invariant.** The lifecycle guard (`begin_maintenance` / `MaintenanceGuard`, `crates/app/src/commands.rs`) does two things that are correct for delete/re-point and fatal for a move: it evicts all routable state up front (the move needs both projects *loaded* — to verify queue quiescence, and to resume normally after), and its `Drop` discards-and-releases on any early return (the move requires both projects to stay blocked after a failed surgery until recovery succeeds — auto-release is exactly the half-moved-state re-enable the intent design prevents). The shape: **reuse the mark set** (`state.maintenance`, so every dispatch gate that already consults the marks refuses for free, and the overlapping-claim refusal is inherited — a move overlapping an in-progress delete/re-point on either project is refused and vice versa) under a **distinct guard type** with move semantics: marks both projects under `registry_write`, no evict, no generation bump, sticky across early returns, released only by explicit success or by recovery. Verify at the three admission sites that the marks are actually consulted there; add the check where one isn't. Record this contrast as a comment on the new guard — it is the answer to "why not `begin_maintenance`."
- Flags are process state; durable blocking across restart is M4's job (derived from unrecovered intent files), so don't persist flags here.

### Definition of Done

- Concurrency tests: a turn completing for a *different* agent in a flagged project has its journal record survive (regression for the append-loss hazard the gate exists for — must fail without the gate); dispatch against a flagged project is refused with the maintenance error at each of the three sites; the race test — a send admitted just before the flag is set is refused at turn start rather than running (fails if the check lives only at admission).
- Guard tests: a move-guard claim overlapping an in-progress lifecycle claim (delete / re-point) on either project is refused, in both directions (the shared mark set's inherited overlap refusal); an early return between marking and explicit release leaves both marks set (fails with `MaintenanceGuard`'s `Drop` semantics — the assertion that distinguishes the two guards).
- Refusal wording is a user-legible "project is briefly under maintenance" error, not an internal code.
- `make check` green.

## M4 — App: the move operation — surgery, intent record, recovery

### Goal & Outcome

The move itself, correct under crash, mid-operation failure, and concurrency. This is the riskiest milestone in the plan; every hazard below came out of review and needs deliberate handling, not incidental behavior.

- A move relocates the agent's registry row, journal records, pins, and sidecars from source to target; sets `session_home` when (and only when) the rules require; and leaves both projects dispatchable again.
- Refused unless both projects are fully quiescent (M3's gate); running work is never cancelled to make a move happen.
- A crash at any point mid-move is completed automatically at next launch, before either project opens. An in-app failure mid-move triggers the same recovery immediately, with both projects still blocked. A recovery that itself fails blocks exactly the two named projects with a repair-required error naming the intent file — never the whole app, and never silent re-enable.

### Implementation Outline

- **Operation ordering overall**: acquire the process-wide move mutex (moves are rare and user-initiated; serializing removes the concurrent-move question) → ensure **both projects are open in this process, holding their `instance.lock`s** — the target may be cold, because the picker's read-only browse deliberately never locks, so the commit path goes through the real open; a lock held by another process is a typed refusal (the existing `ProjectLocked` surface) → resolve both directories or refuse → set both flags, then verify quiescence (M3) → drain the moved agent's actor → take `registry_write` and **hold it continuously through**: the canonical-name collision check (typed refusal; the hold is what makes check-then-write atomic against a concurrent register/rename in the target — chosen over widening the maintenance flag to roster mutations, which would have added user-visible refusal surface to solve a problem the existing lock already serializes) → the intent-record write → the surgery in the commit order below → `agents_by_id` and both projects' in-memory state → release, then delete the intent record → clear flags → emit the refresh events the existing agent-remove/register paths emit. All-sync under the guard per the existing no-`.await` convention — the drain happens before taking it.

  **Why in-process serialization is sufficient, stated as a comment at the mutex**: cross-process exclusion for the store's files comes from the two `instance.lock`s held above; cross-process exclusion for the harness session file comes from the session lock (M2); the mutex therefore only needs to serialize moves within this process. Without the target's `instance.lock`, a second process with the target open could append to its journal mid-surgery — the append-loss hazard the quiescence gate closes in-process, reopened across processes.
- **Intent record**: one small durable file naming `{agent_id, source_project, target_project}` under a `moves/` directory in the store — **one file per move, never a fixed name** (the gate is per-project and does not stop two moves across different project pairs). It records *what* is in flight, not how far it got; because every step is idempotent, recovery re-drives the whole sequence. Startup recovery drains every file in `moves/` **before either named project opens** (and therefore before any open-time conflict check can wall it off) — this ordering is load-bearing; state it in the code. Recovery obeys the same cross-process rule as the move: it acquires **both** named projects' `instance.lock`s before touching any file, and if either is held elsewhere it defers — the two projects stay blocked locally with the repair-required error and the next launch retries — rather than mutating files another process may be writing.
- **Surgery, in commit order — appends before rewrites, target before source**: (a) append the moved agent's records to the **target journal** (M1's append-missing), (b) copy sidecars (`sessions/<agent-id>.meta.json` / `.turnmeta.jsonl`) via core's durable atomic-write path (`io.rs`: sibling temp, `sync_data`, rename, parent fsync) — **existence of a finalized target is the idempotence predicate, and bare existence is not enough**: a crash mid-copy leaves a destination present but truncated, which a naive existence check would skip on recovery, permanently corrupting the moved metadata while recovery claims equivalence to an uninterrupted move (the same present-but-truncated trap the fork arm documents), (c) append the row to the **target registry**, (d) rewrite the **source registry** without the row — **the commit point**, (e) rewrite the **source journal** without the moved records, (f) move pins, (g) remove source sidecars.
- **Session home (step c/d territory, decided before surgery)**: the value to stamp is the source's **effective session directory** — `source_agent.session_home ?? source project's resolved working directory` — and **never the source project's directory unqualified**. That distinction is the whole rule for an agent being moved a *second* time: its transcript is still under the directory the *first* move recorded, not under the project it currently sits in, so computing the source project's directory would name the wrong place. The same effective directory is what the file-existence check reads. Stamp only when the target's `directory_id` differs from the source's **and** the agent is Claude **and** its session file actually exists under that effective directory — checked with the **no-recanonicalize** lookup (M2), because the flagship scenario is moving an agent out of a worktree the user may have *already pruned*: the transcript still exists under the old encoded directory, and a canonicalizing check would miss it, skip the stamp, and strand the agent later. `Project::adopt_agent` enforces the immutability independently (a recorded home wins; a contradicting proposal is refused), so a miscomputation here surfaces as a typed refusal rather than a silently corrupted record — do not treat that backstop as a licence to pass the unqualified directory. A never-dispatched agent or an unmaterialized fork has no file, must **not** get a `session_home`, and correctly starts or materializes its session native to the target. A subsequent move preserves an existing `session_home` unchanged. A same-directory move sets nothing. Each clause of this rule earns a line in the mutator's docs — the unmaterialized-fork clause especially (violating it re-forks on every turn, silently).
- **Pins move by key partition** (helper lives app-side, mirroring `messageIdentity.ts`'s formats — core is not taught pin-key semantics). Agent pins come in **two shapes and both must partition**, extracting the agent id exactly as `agentIdForMessageKey` does: the canonical `agent:hydration:<agent_id>:<hydration_key>` (agent id in position 2 — what every pin on a completed turn carries, i.e. essentially every durable pin; the pin store migrates the send alias to this once hydration identity appears) and the temporary/alias `agent:send:<send_id>:<agent_id>` (position 3). Matching only the send shape would classify real pins "unrecognized" and silently leave them all behind — the review round's example of a rule that would pass its own literally-specified test while breaking the feature. `user:send:<send_id>` pins move only when the moved agent was the send's sole recipient (otherwise the user's message legitimately still renders in the source); unparseable keys are retained untouched. Never delete a pin. Record the user-pin asymmetry and the fan-out-spans-two-journals note in the same method doc.
- **In-app failures use the same machinery — the intent record is not crash-only.** Once the intent record exists, any failure triggers immediate in-process recovery while both projects stay blocked; that recovery runs under the same `registry_write` hold (or reacquires it before touching files), and events emit only after release. If recovery also fails: the two projects stay blocked with the repair-required error; a startup recovery that fails does the same (those two refuse to open, everything else works, next launch retries). Blocked-across-restart derives from the presence of an unrecovered intent file — flags are process state (M3).
- **Dispatcher/actor lifecycle**: the per-agent actor's dispatch-context factory captures the owning project at creation — post-move it would journal into the *old* project. Under the gate, shut the actor down via the existing drain machinery (draining an idle actor cancels nothing); the next send lazily recreates it against the new project. Verify against the actual actor-creation code; if the factory turns out to read the project live, drain anyway and say so in a comment.
- **Collision scans**: the session-id collision scans filter Claude candidates by the project's `directory_id`; after a cross-directory move that diverges from where the session actually lives. Change the predicate to the effective session directory (the shared convention's last unswept consumer — M2 covers the others; this one lands here because its test needs a moved agent to exist). One predicate, but a correctness one — the scan exists to stop two agents driving one session file.
- **Belt and braces**: the `agents_by_id` cross-project conflict check (shipped in M2.2 of the old plan) remains the detector for anything recovery misses (e.g. an intent file lost to disk failure) — it must surface typed, never silently pick a winner.
- Attachments: the move does not touch attachment files, by decision (see "What this builds"). Assert the *absence* of path rewriting in tests, not just tolerate it.

### Definition of Done

## Deferred / out of scope (recorded so they aren't re-derived)

- **Copy-on-move attachment mitigation** — copy referenced files into the target and rewrite `path` while preserving `dispatched_path` (migration-tool machinery). Build only if the broken-thumbnail limitation proves annoying in practice.
- **Resume-by-transcript-path** as the adapter's resume form — works (probed), but switching forms changes the depended-on CLI surface for no added guarantee today.
- **Orphan-pin cleanup** — its own change if ever wanted, gated on a *successful* transcript load; never part of a move.
- **Phase-tracked / rollback-capable recovery** — rejected; with idempotent steps there is nothing for phases to buy. The "re-running heals, no durable record" position was wrong and is not to be reinstated (see the settled-decisions section).
- **Moving an agent out of an unavailable-directory project** — refused for now; revisit only with a concrete need, and note the Claude session-home question it reopens.
- **Forwarding rebuilds an operational `AgentRecord` to carry a display name** (`resolve_source` / `resolve_source_completed_only` in `crates/app/src/commands.rs`): the record it hands to transcript loading is a copy with `name` replaced by a project-qualified label. A struct doing double duty as dispatch input and display vehicle is what let M1 silently clobber `session_home` there (caught in review, fixed). Carrying the qualified name alongside the untouched record would remove that class of bug, but it is a pre-existing question in the forwarding feature and not the move's to absorb.
- **Pre-existing re-point gap (not caused, not fixed, by this plan)**: re-pointing a directory's catalog path today already breaks resume for that directory's *un-moved* Claude agents — their transcripts stay under the old path's encoded directory while `build_args` derives its lookup from the new one (§3.5b/§3.5c). Surfaced during this plan's review of `session_home`'s representation; the `session_home` machinery is the natural future fix (stamp affected agents at re-point time), but that is its own change against the re-point affordance, not part of the move.
