# OAuth for MCP prompt providers

Switchboard's MCP prompt providers authenticate with a bearer token the user
pastes into Settings (`crates/prompts/src/mcp.rs`, `McpServersSettings.svelte`).
Remote MCP servers increasingly speak the MCP authorization spec instead:
browser sign-in, dynamic client registration, refresh tokens, no token to copy.
Tiddly (`~/repos/bookmarks`) now serves that surface on both its MCP servers, so
it is the concrete target and the live-verification harness for this work.

This plan adds an **OAuth authentication mode** alongside the existing bearer
mode. Bearer is not removed: it stays the path for headless/scripted use and for
servers that only issue tokens, and every existing config keeps working
byte-for-byte.

**What we claim to support.** OAuth **with dynamic client registration**. DCR is
optional in the MCP spec, so a server that requires a pre-registered client id,
or one that uses Client ID Metadata Documents, is out of scope. Settings copy
and the README must say this rather than implying every conforming OAuth MCP
server works.

## Verified facts this plan rests on

All of these were checked against primary sources, not inferred. Do not
re-litigate them; do re-verify if `rmcp` is upgraded.

- Adding `"auth"` to the `rmcp` feature list in `crates/prompts/Cargo.toml`
  compiles clean and pulls only `oauth2 5.0` (with `default-features = false`)
  and `url` — no second TLS stack.
- `impl StreamableHttpClient for reqwest::Client` exists, so
  `AuthClient<reqwest::Client>` is the concrete client type, and
  `StreamableHttpClientTransport::with_client` is where it plugs in.
- `AuthClient` holds `Arc<tokio::sync::Mutex<AuthorizationManager>>` and
  `AuthClient::get_access_token()` holds that lock across the entire
  fetch-or-refresh. **One shared `AuthClient` per provider is therefore
  sufficient to serialize refresh** — no lock of our own is needed for that, but
  a second instance for the same provider would defeat it entirely.
- `AuthorizationManager::exchange_code_for_token` persists credentials through
  the injected `CredentialStore` and re-sends the RFC 8707 `resource`
  parameter. `register_client` persists nothing — the caller must store the
  client id itself.
- Tiddly's live protected-resource metadata returns
  `{"resource":"https://prompts-mcp.tiddly.me/mcp","authorization_servers":["https://clerk.tiddly.me"],"bearer_methods_supported":["header"]}`
  — note **no `scopes_supported`** (M5 fixes this) — and Clerk's authorization
  server metadata advertises `code_challenge_methods_supported: ["S256"]`,
  `registration_endpoint`, and `scopes_supported: [openid, profile, email,
  public_metadata, private_metadata, offline_access]`.

### Where `rmcp` stops, and why we wrap it

`rmcp` supplies the protocol mechanics — discovery, DCR, PKCE S256, refresh,
credential storage — but it is **not** a complete implementation of the spec's
mandatory client checks. Three concrete gaps drive the preflight in M2; a fourth
is unfixable from outside rmcp and is recorded here so it isn't rediscovered as a
mystery:

- `ResourceServerMetadata` (auth.rs:390) deserializes only
  `authorization_server`, `authorization_servers`, `scopes_supported`. It has no
  `resource` field, so RFC 9728 §3.3 resource-identity validation is
  *structurally impossible* with rmcp as shipped.
- No HTTPS enforcement on discovered endpoints in the authorization-code flow.
  rmcp has two scheme checks and **neither is on our path**: `is_https_url` is
  called only on the client-metadata-URL (SEP-991) path at auth.rs:2137, and the
  token-endpoint HTTPS check at auth.rs:1983 belongs to the client-credentials
  flow. Anyone who finds those helpers will assume we're covered; say so in the
  preflight's comment, naming both call sites.
- `validate_server_metadata` warns and proceeds when `S256` is absent. The spec
  requires refusal: *"If `code_challenge_methods_supported` is absent, the
  authorization server does not support PKCE and MCP clients MUST refuse to
  proceed."*
- **Token refresh omits the RFC 8707 `resource` parameter.**
  `exchange_code_for_token` sends it (auth.rs:1173); `refresh_token`
  (auth.rs:1304-1312) builds its request from the refresh token plus
  `granted_scopes` only. The spec says the parameter *"MUST be included in both
  authorization requests and token requests,"* and a refresh is a token request.
  There is no injection hook, and reimplementing refresh ourselves would forfeit
  the `AuthClient` mutex that gives us refresh serialization — so we document
  rather than work around it. **Inert against tiddly**, whose `decode_clerk_jwt`
  runs with `verify_aud: False` against a Clerk token carrying no audience claim.
  Against an authorization server that audience-binds, everything works until the
  first refresh and then every call 401s as a generic `Errored` — which is
  precisely why it is written down here.

`rmcp`'s scope selection is also non-conformant: its fallback chain ends at the
*authorization server's* `scopes_supported`, where the spec ends at "omit the
scope parameter." Against Clerk that fallback would request `private_metadata`
and `public_metadata` to fetch prompt templates. We compute scopes ourselves and
pass them explicitly, so that path never runs.

## Scope boundary

In scope: Switchboard's **own** MCP client, which exists only to serve prompt
providers (`crates/prompts`).

Out of scope: MCP servers configured inside the harnesses (Claude Code, Codex,
Gemini, Antigravity). Those are harness-owned, the harnesses run their own OAuth
flows, and tiddly's verification notes already record them working. Switchboard
only reads and displays that registry.

## Conventions established here (later milestones reuse, do not reinvent)

**Auth mode is per-provider config, defaulting to bearer.** An entry with no
`auth:` key is a bearer provider — what every existing user has.

**Secret-store keys.** Bearer tokens stay at key `<provider-name>` (unchanged —
do not migrate). OAuth state lives at `oauth:<provider-name>`. Provider names are
already validated to exclude `:` (`config.rs::is_valid_provider_name`), so the
namespaces cannot collide. Provider removal clears both.

**Registration and tokens are separate lifetimes.** The OAuth envelope has a
non-secret `registration` block (client id, the registered redirect form, the
resource URL) and a `tokens` block. Sign-out clears tokens only; removing the
provider clears the whole key. This is what makes registration reuse possible —
see M3.

**Credentials are bound to the resource they were issued for.** Every envelope
records the canonical resource URL; a mismatch against the provider's current URL
means "no credentials," never "use them anyway."

**One canonical URL, computed once at input.** The user's typed URL is normalized
per RFC 3986 syntax-based normalization — lowercase scheme and host, drop the
default port — **and the path is left untouched**. That single canonical form
feeds `AuthorizationManager::new`, the RFC 8707 `resource` parameter, the
envelope's `resource`, the session-cache key, and every identity comparison, so
they cannot disagree. Two reasons this is not optional polish: the MCP spec says
implementations *"SHOULD accept uppercase scheme and host components for
robustness and interoperability,"* and tiddly's server does the mirror-image
normalization in `_canonical_scheme_netloc`, so matching it is symmetric by
construction. The path stays significant deliberately — tiddly requires exactly
`/mcp`, and silently rewriting a trailing slash could mask a real mismatch.
Wherever an identity comparison fails, the error prints **both** values so the
honest failures diagnose themselves.

**`crates/prompts` stays Tauri-free; the app injects side effects.** Existing
pattern for config paths and `SecretStore`. The OAuth flow lives in
`crates/prompts`; opening the browser is an injected trait. Do not add `rmcp` to
`crates/app`.

**Auth state is determined locally, never by string-matching error text.** The
existing `ProviderStatus` doc comment explains why an auth-vs-unreachable split
was previously rejected: rmcp collapses transport failures into one opaque error.
OAuth changes that — `get_access_token()` returns a typed
`AuthError::AuthorizationRequired` *before any request to the MCP server*. That
is the only permitted source of a "needs sign-in" status. Extend that comment's
reasoning; don't delete it.

**Never log or embed** a token, authorization code, or refresh token in an error,
status, or tracing field — now including the callback query string.

## Milestone 1 — Config shape and OAuth credential storage

### Goal & Outcome

Teach the config and secret layers what an OAuth provider is, so later
milestones have somewhere to read and write credentials.

- A user can declare `auth: { type: oauth }` on an `mcp_providers` entry and it
  parses, validates, and round-trips; an entry with no `auth:` key still means
  bearer.
- OAuth state persists in the OS keychain and survives an app restart.
- Signing out leaves the client registration intact; removing the provider
  removes everything.
- Credentials issued for one server URL are never presented to a different one.

### Implementation Outline

**Config (`config.rs`).** Add an `auth` field to `McpProviderConfig` as a tagged,
`#[non_exhaustive]` enum mirroring `McpTransport` (`#[serde(tag = "type",
rename_all = "snake_case")]`), serde-defaulting to bearer. The OAuth variant
carries an optional `scopes: Vec<String>` override (M3 explains when it is
consulted). The existing test `mcp_providers_section_is_ignored_and_does_not_affect_local_dirs`
already writes an `auth: { type: bearer }` block — honour that shape. Per-entry
validation is unchanged: a malformed `auth:` degrades that one entry, never the
section.

**Credential envelope + `CredentialStore` bridge (new module).** Persist as JSON
under `oauth:<provider>`:

```
{
  "registration": { "client_id": "...", "redirect_uri": "http://127.0.0.1/callback",
                    "resource": "https://host/mcp" },
  "tokens": <rmcp StoredCredentials> | null
}
```

Mapping onto rmcp's trait, which only ever hands us a `StoredCredentials`:

- `load()` — return `None` if the envelope is missing, if its JSON is corrupt
  (warn; the recovery is "sign in again," and a hard error would leave a provider
  the user cannot repair from the UI), or if `registration.resource` does not
  exactly match the provider's current URL. Otherwise synthesize a
  `StoredCredentials` from `registration.client_id` + `tokens`. When `tokens` is
  null this yields `token_response: None`, which is exactly what makes
  `initialize_from_store` report "not authorized" and `get_access_token` return
  `AuthorizationRequired`.
- `save(credentials)` — **read-modify-write**. rmcp calls this on every refresh
  with only a `StoredCredentials`; the `registration` block must survive.
- `clear()` — null the `tokens` block, preserve `registration`.

**Removal.** `remove_mcp_provider` (`service.rs:490-507`) currently returns on
`self.secrets.delete(name)?`, per its documented "surface the failure, don't
swallow it" contract. Adding a second `?`-guarded delete would inherit the
short-circuit and could strand a refresh token under a provider the user
believes is gone. Attempt **both** deletes unconditionally, then surface the
first error.

### Definition of Done

- Config unit tests: absent `auth:` ⇒ bearer; explicit bearer and oauth parse;
  a `scopes` override round-trips; a malformed `auth:` skips only that entry;
  `write_mcp_providers` preserves auth mode and unrelated top-level keys.
- Credential-store tests against `InMemorySecretStore`: round-trip; a
  credentials-only `save` preserves `registration`; `clear` keeps `registration`
  and drops `tokens`; corrupt JSON loads as `None`; **a resource mismatch loads
  as `None`**.
- Removal test: a store whose first delete fails still attempts the second, and
  the error still surfaces.
- The rationale for the registration/tokens split, the resource binding, and
  corrupt ⇒ `None` lives in module docs.

## Milestone 2 — Validation preflight and the OAuth-mode client

### Goal & Outcome

Make `McpProvider` able to talk to a server using stored credentials, behind a
validation boundary that covers the mandatory spec checks rmcp omits.

- A provider configured for OAuth with valid stored credentials lists and
  renders prompts exactly like a bearer provider.
- A near-expiry token refreshes automatically and persists, with no user action
  and no possibility of two concurrent refreshes racing.
- A provider with no credentials, or whose refresh failed, reports a distinct
  "needs sign-in" status.
- A server whose metadata fails any mandatory check is refused with a specific
  error, before any credential is sent or browser opened.
- One slow or unreachable OAuth provider cannot stall a prompt sync or a send
  beyond the existing per-provider budget.

### Implementation Outline

Enable the `auth` feature on `rmcp`.

**Preflight (new, runs before anything else touches a provider).** One function
that both this milestone's client construction and M3's sign-in call. It must
validate *the metadata rmcp actually uses* — validating one copy and letting rmcp
rediscover another is decorative. Steps:

1. Probe the MCP endpoint unauthenticated; parse `WWW-Authenticate` for the
   `resource_metadata` pointer **and** any `scope` challenge. Fall back to the
   RFC 9728 well-known paths if the header is absent.
2. Fetch the protected-resource metadata. Require `resource` to equal the
   provider's canonical URL — exact comparison, against the normalized form from
   the conventions above, with both values in the error on mismatch. (rmcp
   discards this field entirely, which is why we parse it ourselves.)
3. Fetch the authorization-server metadata. Require HTTPS on
   `authorization_endpoint`, `token_endpoint`, **and** `registration_endpoint` —
   not merely on the issuer, since those three are where codes and tokens
   actually travel. Require the provider URL itself to be HTTPS (loopback
   excepted, for dev).
4. Require `code_challenge_methods_supported` to be present and contain `S256`;
   refuse otherwise. The spec's literal MUST covers absence; refusing a list
   without `S256` is the same call since S256 is the only method we can use.
5. Return the validated metadata (deserialized into rmcp's
   `AuthorizationMetadata`, which is `Deserialize` with public fields) plus the
   resolved scopes (see M3).

Install the result with `AuthorizationManager::set_metadata()` so rmcp does not
refetch. This only holds because we drive registration manually — `OAuthState::
start_authorization` rediscovers unconditionally, which is one of several reasons
M3 does not use it.

**Dual-mode transport (`mcp.rs`).** Bearer keeps the existing
`auth_header(bearer)` path verbatim. OAuth builds the same config without the
header and constructs the transport via
`StreamableHttpClientTransport::with_client(auth_client, config)`. Everything
downstream (`list_all_prompts`, `get_prompt`, `map_service_error`,
`extract_text`) is unchanged — this is a transport-construction branch, nothing
more.

**Session cache (`service.rs`) — the load-bearing decision.** `PromptService`
builds a fresh `McpProvider` per operation (`sync`, `render`), which is right for
bearer and wrong for OAuth: it re-runs discovery per render, and — because
refresh serialization comes from the `AuthClient` instance's internal mutex —
two instances for one provider can both refresh against a Clerk refresh token
that rotates on use, so each invalidates the other. The user gets bounced to
"sign in again" for something they didn't do.

So: cache one `AuthClient` per **`(provider name, canonical URL)`**, built lazily
via preflight → `AuthorizationManager::new(<the /mcp URL>)` →
`with_client(bounded reqwest client)` → `set_credential_store` → `set_metadata` →
`initialize_from_store()` → `AuthClient::new`. The base URL must be the full MCP
endpoint URL: rmcp uses it for discovery *and* as the RFC 8707 `resource`, and
tiddly's advertised resource includes the path.

Three constraints on that cache:

- **Single-flight per provider, never the map lock across I/O.** Holding the
  map's lock through discovery would serialize unrelated providers and defeat
  `sync`'s `join_all` fan-out (`service.rs:251`).
- **Every OAuth caller uses the cached client**, including `render()`. Its
  "builds fresh" doc comment is about the *prompt* cache and must not be read as
  license to construct a second `AuthClient`.
- **Invalidate** on provider removal, sign-out, sign-in, and URL change (the
  URL is in the key, so the last one is automatic).

**Timeouts.** Discovery currently escapes the ten-second provider budget
(`mcp.rs:65` wraps only connect + request) and rmcp's own client defaults to 30s
per request across several candidate endpoints. Inject a bounded reqwest client
via `with_client`, *and* wrap client-acquisition + token probe + connect +
request in the provider's total timeout.

**Status.** Add `NeedsAuth` to `ProviderStatus` and an `auth` field to
`McpProviderInfo`, so the UI can tell "bearer provider with no token pasted" from
"OAuth provider not signed in" — the affordances differ. `has_token` reports
*token* presence, never registration presence; a signed-out provider must not
render as credentialed.

Derive `NeedsAuth` from a proactive `AuthClient::get_access_token()`: it returns
typed `AuthorizationRequired` when credentials are absent or refresh failed, and
refreshes a near-expiry token once, ahead of that provider's listing call.

**The probe runs inside each provider's concurrent branch, not before the fan-out.**
For an OAuth provider it is not cheap — a cold client runs the full preflight
(three fetches) and a near-expiry token adds a token-endpoint round trip.
Hoisting it above `join_all` (`service.rs:269`) would let one slow provider delay
every sibling's start, breaking the isolation guarantee documented at
`service.rs:225-228` and the DoD bullet below.

**Known limitation to record in code:** a token still inside its expiry window
but revoked server-side fails mid-call and surfaces as generic `Errored`; the
next sync's probe reports `NeedsAuth` once refresh fails. Sub-classifying
mid-flight failures means reaching into rmcp's type-erased transport error — the
coupling the existing `ProviderStatus` comment argues against.

**`test_mcp_connection`.** The current pre-save probe takes a URL and bearer and
cannot authenticate an OAuth provider that doesn't exist yet. Keep it bearer-only
and add a **saved-provider probe by name** that runs against the cached client.
M4 wires it.

### Definition of Done

- Preflight negative tests against a fake server, one per gate: `resource`
  mismatch, `http://` authorization/token/registration endpoint, non-HTTPS
  provider URL, missing `code_challenge_methods_supported`, list without `S256`.
  Each must abort before any credential is sent.
- URL canonicalization: an uppercase scheme/host and an explicit `:443` both
  validate against a lowercase, default-port advertised `resource`; a trailing
  slash still fails, with both values in the message; a different host still
  fails.
- A test asserting **no second discovery request** is issued after
  `set_metadata` — this is what proves the boundary isn't decorative.
- Fixture-driven integration test (extend `crates/prompts/tests/mcp_server.rs`):
  an OAuth provider with pre-seeded credentials lists prompts and sends the
  expected `Authorization` header.
- A provider with no credentials reports `NeedsAuth`, contributes no prompts, and
  does not affect siblings in the same `sync` — the degrade-to-empty guarantee
  must survive.
- Concurrency/timeout: slow discovery on one provider doesn't delay a healthy
  sibling and completes within the provider budget; concurrent `sync` + `render`
  against one near-expiry provider produce **exactly one** token-endpoint hit;
  concurrent first-use constructs one client.
- Bearer-mode regression tests pass unchanged — the single most important signal
  here.
- Re-run `live_https_connection_establishes` (`--ignored`); it exists to catch
  exactly this class of reqwest feature regression.

## Milestone 3 — Browser sign-in and sign-out

### Goal & Outcome

- From Settings, a user signs in: the browser opens, they authenticate, the
  browser lands on a local success page, and Switchboard has working credentials.
- Sign-out clears tokens and returns the provider to "needs sign-in."
- Signing in again — after sign-out or after credentials expire — reuses the
  existing client registration instead of creating another one on the server.
- An abandoned or denied sign-in fails cleanly with a readable reason and leaves
  no partial state.

### Implementation Outline

**Where it lives.** `crates/prompts` (rmcp- and tokio-shaped), with browser
opening injected as a trait so tests can capture the URL instead of launching
anything. **The app already has an opener** — `open_external_url`
(`crates/app/src/lib.rs:918`) shells out to macOS `open` behind
`validate_external_url` (`commands.rs:3817`). Factor its body into a free
function and implement the trait over it. Do **not** add `tauri-plugin-opener`.

**Scope resolution (spec order, ours to compute).** In priority order:

1. A per-provider `scopes:` override from config, if set — the escape hatch for a
   server we can't otherwise satisfy.
2. The `scope` challenge from the initial 401's `WWW-Authenticate`, if present.
3. All of `scopes_supported` from the protected-resource metadata.
4. Otherwise **omit the scope parameter entirely.**

No built-in default list. A generic client has no basis to guess another
product's permissions, and rmcp's own fallback (the authorization server's
`scopes_supported`) would request `private_metadata` against Clerk. Record that
reasoning in the code — passing an empty scope list looks like an oversight
without it. Note the consequence: bypassing `start_authorization` also bypasses
`add_offline_access_if_supported`, so nothing silently appends `offline_access`
any more; a server that wants refresh tokens must advertise it (M5 makes tiddly
do so).

**The flow, in order.** Load-bearing: the PKCE verifier lives in an in-memory
state store *inside* the `AuthorizationManager`, so everything from
`get_authorization_url` through `exchange_code_for_token` must happen inside one
owned async operation. Do not split across two Tauri commands. We drive the
manager directly rather than through `OAuthState`, because `start_authorization`
rediscovers metadata unconditionally (defeating M2's preflight) and always
registers a new client (defeating reuse).

1. Bind `127.0.0.1:0`. The redirect URI must be known before registration.
2. Preflight (M2) → validated metadata + resolved scopes.
3. `AuthorizationManager::new(<the /mcp URL>)`, `with_client`,
   `set_credential_store`, `set_metadata`.
4. If the envelope has no `registration.client_id`:
   `register_client(name, "http://127.0.0.1/callback", &scopes)` — **port-less** —
   then **persist the returned client id to the envelope immediately, before the
   browser opens**. rmcp persists nothing itself, and a user who abandons the
   flow would otherwise orphan a registration and re-register next time.
5. `configure_client` with the stored client id and the **concrete**
   `http://127.0.0.1:<bound port>/callback`. This split is the whole trick — see
   below.
6. `get_authorization_url(&scopes)` (adds PKCE S256 and the RFC 8707 `resource`),
   open it with the injected opener.
7. Await the callback with a generous timeout — the user may be doing MFA. On
   timeout, tear down and return an actionable error.
8. `exchange_code_for_token(code, state)`, which validates state via the store,
   exchanges, and persists through our `CredentialStore`. Bound this with a
   timeout too: rmcp builds its own client for the exchange, so our injected
   client's timeout does not apply.
9. Invalidate the M2 session cache for the provider; trigger the usual background
   sync.

**Ephemeral port + port-less registration.** RFC 8252 §7.3 requires an
authorization server to allow any port for a loopback redirect. Tiddly's own CLI
relies on this: `cli/internal/auth/pkce_flow.go:182` binds `127.0.0.1:0` against a
registration whose redirect URI is port-less, with the comment "Clerk matches any
loopback port." Registering port-less and authorizing with the concrete port is
therefore what lets an ephemeral listener coexist with a reusable registration.
A fixed reserved port was considered and rejected: it buys nothing here and makes
sign-in fail whenever another instance holds the port.

**Callback listener.** Handles exactly one request: parse `code`/`state`, respond
with a small human-readable success page, shut down. `error`/`error_description`
in the query (consent denied) must surface as a readable failure, not a timeout.
The listener must always terminate when the flow returns, including on error —
tiddly's CLI does this with a short graceful-shutdown deadline then a hard close,
and the same discipline applies. A one-route hand-rolled responder over
`tokio::net::TcpListener` is the right size; a web framework in production
dependencies for one route is not. Do not log the query string.

**Service surface.** Sign-in and sign-out on `PromptService` keyed by provider
name, exposed through `crates/app` as Tauri commands via the existing `*_impl`
pattern. Sign-out clears the `tokens` block only (M1) and invalidates the cache.
`add_mcp_provider` takes the auth mode; changing its signature and the command's
wire shape is fine — internal API, one caller.

### Definition of Done

- Full-flow integration test against an in-process **fake authorization server**
  (protected-resource metadata, AS metadata, registration, authorize, token):
  sign-in completes, credentials land in the store, a subsequent list succeeds.
  The injected opener captures the URL; assert PKCE `code_challenge`, `resource`,
  and the resolved scopes on it.
- **Registration reuse**: sign-out then sign-in hits the registration endpoint
  zero times; two sign-ins on different ephemeral ports register once; a denied
  first attempt still leaves a reusable client id.
- Scope resolution: override beats challenge beats resource metadata beats omit;
  the omit case sends no `scope` parameter at registration or authorize.
- Error paths: `error=access_denied` produces a readable failure; a callback that
  never arrives times out with no credentials stored; a `state` mismatch is
  rejected; the listener is closed in every case.
- Sign-out leaves `has_token: false` and `NeedsAuth`.

## Milestone 4 — Settings UI

### Goal & Outcome

- Adding an MCP server, the user chooses between pasting a token and signing in
  with a browser.
- An OAuth row shows whether it is signed in and offers Sign in / Sign out.
- A provider needing sign-in is visibly distinct from one that is erroring, with
  the fix one click away.
- Test connection works for both modes, at the point in the flow where each can
  actually work.

### Implementation Outline

The add form is name / URL / optional bearer plus a pre-save Test. When OAuth is
selected the bearer field is irrelevant and the pre-save probe cannot
authenticate (M2), so the honest sequence is: add, sign in from the row, then
test. Make that evident rather than leaving a Test button that always fails.

Row rendering: the `· no token` hint is bearer-specific — use the new `auth`
field to pick the right affordance, and render `NeedsAuth` as its own status with
the sign-in action attached, not folded into error styling. Add the row-level

### Goal & Outcome

- Tiddly declares the scopes its MCP servers need, so a generic client asks for
  exactly those and nothing more.
- A developer can sign in to `https://prompts-mcp.tiddly.me/mcp` from Switchboard
  and use its prompts in a real send.
- Users can tell from the docs when to choose OAuth and when to choose a token.

### Implementation Outline

**Server change first (separate PR in `~/repos/bookmarks`).** Add
`scopes_supported` to the protected-resource metadata in
`backend/src/shared/mcp_oauth.py`'s metadata builder (`build_protected_resource_metadata`,
shared by both servers; `backend/tests/shared/test_mcp_oauth.py` asserts the
document by exact equality and will need updating). A module constant, not new
config — tiddly has no per-scope permission model to differentiate the two
servers on.

Deciding the list: `decode_clerk_jwt` (`backend/src/core/auth.py`) **never reads
`scope`** — it verifies signature/issuer/expiry, requires `client_id` on an
`at+jwt`, and identifies the user by `sub`. So the list is not "what tiddly's
authorization needs" (there is none) but "what Clerk needs to mint a token this
backend accepts, and nothing more." `offline_access` is load-bearing — without it
Clerk issues no refresh token, so authorization cannot outlive the ~24h access
token: once it expires, only a fresh browser sign-in gets a new one.
`openid` is the conventional inclusion and the one the ChatGPT check below turns
on. `profile`/`email` are probably unnecessary, since the backend reads neither
claim for OAuth tokens — verify first whether JIT user creation
(`clerk_jit_create_enabled`) needs an email on a first-time OAuth sign-in.

This is what makes Switchboard's client fully generic — with it published, no
tiddly-specific scope knowledge exists anywhere in Switchboard. Deploy before the
verification below; follow that repo's own conventions and test requirements.

## Risks

- **Refresh-token rotation.** Clerk rotates on use. One shared `AuthClient` per
  provider is what prevents concurrent refreshes from invalidating each other;
  its internal mutex does the work, but only across a single instance. Treat
  single-instance-per-provider as a correctness requirement, not an optimization.
- **Two live unknowns, both settled in M5**: whether Clerk accepts a port-less
  loopback redirect *through DCR* (fallback: re-register when the bound port
  differs — worse, but not broken), and whether a real refresh round-trip behaves
  as the fixtures do.
- **The `resource` parameter is missing on refresh** (see "Where `rmcp` stops").
  Inert against tiddly, latent against any audience-binding server. It is the
  first thing to suspect if a future OAuth provider works until roughly its
  token TTL and then 401s on everything.
- **Mid-flight revocation** reads as a generic error until the next sync — a
  recorded limitation (M2), not a bug.
- **rmcp upgrades** may change discovery, scope selection, or the auth error
  surface. The preflight exists because rmcp does not implement the spec's
  mandatory checks; re-verify the "Where rmcp stops" section on any version bump,
  and re-run the TLS smoke test.
