# Agent access: an MCP server for Switchboard

**Status:** proposed · **Revision:** 1 · **Created:** 2026-10-09

An MCP server inside the Switchboard app, so an external agent (Claude Code, Codex, Claude
Desktop) can run the same operations a user runs from the keyboard: create projects and agents,
send a message to one or more agents, wait for the replies, forward one agent's output to
others, run workflows, and read the conversation. The server listens on the Mac only. Hosting
it elsewhere is a later, separate decision with its own security design.

This document is the component inventory and the milestones. The product framing it extends is
`docs/system-design.md` §1 ("human-directed orchestrator"): an agent on the other end of MCP is
one more thing that can direct work, under the same rules as the user. The design it shares
pieces with is [`2026-09-29-remote-control.md`](2026-09-29-remote-control.md), the iPhone app;
§8 below says what the two share and how they merge.

## 0. Decisions

Settled before this plan was written. Each row changes a milestone.

| Question | Decision | Effect |
|---|---|---|
| Clients that must work | **Claude Code, Codex, Claude Desktop** | Claude Code and Codex connect to the local HTTP server directly. Claude Desktop reaches remote connectors from Anthropic's cloud, never from the Mac ([custom connectors](https://support.claude.com/en/articles/11175166-getting-started-with-custom-connectors-using-remote-mcp)), so it needs a local stdio process; v1 uses the [`mcp-remote`](https://github.com/geelen/mcp-remote) bridge, with an in-repo bridge as the contingency (M0 decides). |
| Transport | **Streamable HTTP on `127.0.0.1`, in-process** | A second process cannot drive projects this app holds (`instance.lock`, `project_locked`), so the server runs inside `desktop/src-tauri`. `rmcp` 1.7 and `axum` are already dependencies (dev-only in the app crate today; they move to regular dependencies). |
| Authentication | **Bearer token, generated by the app** | Stored in the app's secret store, shown in Settings, revocable by regeneration. `Origin` and `Host` are checked on every request (§4). |
| Off by default | **Yes** | Nothing listens until the user enables it in Settings. Disabling stops the listener immediately. |
| Tool surface | **Orchestration core** | Projects, agents, send, forward, wait, cancel, read conversation and outputs, workflows, saved prompts. Not in v1: git, preferences, MCP-provider administration, pins, attachments, archiving. |
| Destructive operations | **None** | No project deletion, no agent removal, no archiving. The desktop keeps those. |
| Busy recipient | **`on_busy` per send, default `refuse`** | `refuse` returns `agent_busy` and dispatches nothing (what workflows do). `queue` enqueues behind the running turn. Both are awaitable, because completion is tracked from the event stream, not from the dispatcher's completion handle (§3.2). |
| Waiting for results | **Bounded wait, called again until done** | `wait_send`, `wait_agent`, `wait_workflow` block up to `timeout_seconds` and return the current state either way; the caller loops. Progress notifications keep the client's idle timer alive. Defaults come from the M0 measurements. |
| After an app restart | **Answer from the journal** | The ledger is in memory. A `send_id` it does not hold is answered from `journal.jsonl`: `failed` or `cancelled` from an outcome marker, `started` with the outcome unknown from a `Send` record, else `unknown`. No new persistence. |
| Reply size | **Capped, pageable** | Text returned to a client is cut at `max_chars` (default 32,000) with a suffix stating the total; `offset` reads on. The full text stays on the Mac. |
| Desktop window | **Stays in sync through a backend→frontend round trip** | Before a send and after any agent or project change, the backend asks the window to load or refresh the project and waits for the acknowledgement (§5). The same mechanism the remote-control plan specifies for the phone (§5.8 there), widened to refresh. |
| Live user row for MCP sends | **Emitted by the dispatcher** | The compose bar draws its own user row, so the plain send path emits none. MCP sends pass `emit_user_message: true`, the path workflow sends already use. The remote plan's `SendOrigin` later replaces this flag; §8. |
| New project via MCP | **Creates no agents** | The desktop seeds one agent per installed harness; an orchestrator adds the agents it wants. |
| Model and effort values | **Harness-native strings, not validated against a catalog** | The registry already stores them as free text and a bad value fails the next turn with the harness's error. The quick-choice lists from the agent record and Settings are exposed so a caller can pick from known values. The desktop's picker catalog (`desktop/src/lib/agentSelection.ts`) is not moved to Rust in v1. |
| An agent inside Switchboard calling the server | **Documented, not enforced** | Agents inherit the user's MCP configuration. A send to itself is refused as `agent_busy` under the default; under `queue` it runs after the caller's own turn ends. README says to register the server at the orchestrator's scope, not user-global. |
| Workflow results | **Not returned by the run** | The run reports its status; the caller reads the last recipient's output with `read_agent_output`. Returning step outputs is a follow-up. |

## 1. Architecture

```
Claude Code / Codex ──HTTP──▶ 127.0.0.1:<port>/mcp
Claude Desktop ──stdio──▶ mcp-remote ──HTTP──▶   │
                                                 ▼
                                   axum: Host/Origin check, bearer token
                                                 ▼
                                   rmcp service: tools (desktop/src-tauri/src/mcp/)
                                                 ▼
                                   ops (desktop/src-tauri/src/ops/)
                                     ├─ *_impl in commands.rs / workflow_commands.rs
                                     ├─ Dispatcher
                                     ├─ SendLedger ◀── OpsLedgerEmitter (EventEmitter decorator)
                                     └─ desktop_sync ◀──▶ frontend (load-or-refresh round trip)
```

Three new modules, all in the app crate:

- **`ops`** — one function per operation, taking explicit ids and `&AppState`, built on the
  existing `*_impl` functions. This is the application layer the compose bar implements in
  TypeScript today: fan-out, sending a composed forward, recording outcomes, waiting. Every
  client that is not the window calls it. The MCP tools are thin wrappers; the remote-control
  plan's `RemoteBackend` implementation should become one too (§8).
- **`ops::ledger`** — the `SendLedger`: per-send, per-recipient status and reply text, fed by an
  `EventEmitter` decorator in the existing chain. Idempotent sends and `wait_*` read it.
- **`mcp`** — the listener, authentication, tool definitions, and the Settings commands.

Plus a frontend handler for the sync round trip and a project-list change event (§5).

What does not change: the dispatcher's actor model, the harness adapters, the journal format,
`config.yaml`'s existing keys, the IPC commands the window calls (two gain an explicit
`project_id` that the Tauri wrapper fills from the active project, so no frontend change).

## 2. Conventions every milestone follows

Set here so later milestones reuse them.

- **Explicit ids everywhere.** An `ops` function never reads `active_project_id`. Projects and
  agents are addressed by UUID. Names are for display; `list_agents` is how a caller maps one
  to the other.
- **One error type, stable codes.** `ops` returns `AppError`. The tool layer maps it to a
  closed set of snake_case codes that models can act on: `project_not_found`, `agent_not_found`,
  `agent_busy`, `source_busy`, `directory_missing`, `project_load_timeout`, `project_locked`,
  `prompt_needs_sign_in`, `prompt_too_large`, `send_unknown`, `run_unknown`, `mcp_disabled`,
  `invalid_argument`, `internal`. Codes that exist in the remote plan's §4 keep its spelling.
- **Tool results are JSON text.** Every tool returns one `text` content block holding a
  serialized JSON object. Errors are returned as a tool result with `is_error: true` and the
  body `{ "code": …, "message": … }`, not as a JSON-RPC error, because clients show tool
  errors to the model and some swallow protocol errors.
- **Text limits.** Any text an agent produced that leaves the Mac goes through one helper:
  `clip(text, offset, max_chars) -> { text, total_chars, truncated }`. Default `max_chars` is
  32,000; the suffix is `… [truncated, N chars total — read on with offset=M]`.
- **Nothing MCP does needs the window, except the sync round trip.** `ops` must be callable
  from a test with `AppState` built the way `commands.rs`'s tests build it
  (`state_with_project`, `MockHarnessAdapter`); the sync hook is a trait with a no-op test
  double.
- **Logging.** Every tool call logs its name, project and agent ids, and outcome at `info`.
  Prompt text and reply text are never logged.
- **Tests** use the repo's vocabulary: unit tests inside modules, fixture-driven integration
  tests with the mock harness, one optional live test named `live_claude_mcp_…`.

## 3. `ops` — the shared operations layer

`desktop/src-tauri/src/ops/`. Pure application logic over `AppState`; no `rmcp`, no Tauri
types beyond what `*_impl` already uses.

### 3.1 Operations

Listing, grouped. Each is a `pub async fn` taking `&AppState` and the arguments shown, returning
`Result<…, AppError>`.

**Read**

- `list_projects()` — `list_projects_impl` plus, per project, `status: busy | idle` computed
  the way the remote plan's §5.7 says: busy when any roster agent has pending work in the
  dispatcher or a workflow run is registered for it. Unopened projects are idle.
- `list_agents(project_id)` — `list_project_agents_readonly_impl` (works for unopened projects)
  plus `busy: bool` from the dispatcher, and the record's model, effort, and quick choices.
- `read_conversation(project_id, last_n_items, max_chars_per_item)` —
  `load_project_conversation_impl`, tail-cut to `last_n_items`, every text and tool output
  clipped. Returns the items in the shape the desktop renders (`ConversationItem`), so an agent
  sees user messages grouped per fan-out, agent turns, and outcome markers. Paging by cursor is
  the remote plan's `TranscriptWindow` (its M3); not built here.
- `read_agent_output(agent_id, offset, max_chars)` — the agent's latest completed answer: the
  ledger's captured text when it holds that agent's latest turn, otherwise the disk read the
  forward resolver uses (`load_agent_transcript` + `latest_completed_agent_text`), with the
  same failure note the resolver adds when the latest turn failed or was cancelled.
- `list_prompts()` and `list_workflows()` — the existing impls.

**Change**

- `create_project(name, directory)` — `create_project_impl`; seeds nothing.
- `rename_project(project_id, name)`.
- `create_agent(project_id, name, harness, model?, effort?)` — `create_agent_impl` after it
  takes a `project_id` (3.4).
- `rename_agent(agent_id, name)`, `set_agent_selection(agent_id, model?, effort?)`.

After each of these the operation runs the sync round trip (§5) so the window shows the change.

**Send**

- `send(project_id, recipients: [agent_id], body: Body, on_busy, send_id?) -> SendReceipt`
  where `Body` is plain text, or a saved prompt (`provider`, `name`, `args`) with optional
  appended text, composed exactly as the compose bar composes them (`render_prompt_impl`, then
  `combinePromptMessage`'s rule). Order, fixed:
  1. `ensure_loaded(project_id)` — the sync round trip. Nothing is dispatched if it fails.
  2. Validate every recipient is in the project's roster and the directory exists
     (`directory_missing`); render the prompt (`prompt_needs_sign_in` on `NeedsSignIn`).
  3. If `send_id` was supplied and the ledger holds it, return the stored receipt without
     dispatching (the idempotency rule from the remote plan's §5.5).
  4. Register the send in the ledger, then dispatch one recipient at a time through
     `send_message_impl` with the shared `send_id`, `emit_user_message: true`, and the chosen
     `OnBusy`. Under `refuse`, every recipient is checked for pending work first and the whole
     send is refused with `agent_busy` naming the busy agents, so a fan-out is all-or-nothing.
  5. Return per-recipient `{ agent_id, message_id, status: accepted | rejected { code } }`.
- `forward(project_id, sources: [agent_id], recipients: [agent_id], text?, prompt?, on_busy)`
  — `forward_message_impl` / `forward_prompt_impl` to compose the body (they open the sources'
  projects themselves and wait for a mid-turn source), then `send` with that body. The compose
  call is raced against the operation's wait budget (§3.3); on expiry it is cancelled with
  `cancel_forward_impl` and the operation fails with `source_busy`, telling the caller to
  `wait_agent` first. An `Invalidated` outcome (a source produced no forwardable text, or its
  turn failed) is returned as `invalid_argument` with the resolver's reason.
- `cancel_send(send_id)` — `cancel_send_impl` with the ledger's recipients; `cancel_agent(agent_id)`.

**Wait**

- `wait_send(send_id, timeout_seconds) -> SendStatus` — blocks until every recipient is terminal
  or the timeout passes; returns `{ done, recipients: [{ agent_id, status, text?, error? }] }`
  with `status ∈ accepted | running | completed | failed | cancelled | unknown`. Text is
  clipped (§2). Unknown `send_id` → the journal fallback (§0).
- `wait_agent(agent_id, timeout_seconds)` — `Dispatcher::wait_for_current_turn` with a timeout.
  Returns `idle` with the latest output, or `running`. This is how a caller waits for work it
  did not start (a user's send, a workflow's turn) before forwarding.
- `run_workflow(project_id, name, is_builtin, inputs, forward_sources?) -> run_id` —
  `ensure_loaded`, resolve forward fields the way the Tauri wrapper does today (that helper,
  `merge_workflow_forwards` in `lib.rs`, moves into `ops`), then `invoke_workflow_impl`.
- `wait_workflow(run_id, timeout_seconds)` — from the ledger's run entries (3.2): `running`
  with the current step, or the terminal status with the failed step and reason.
- `list_workflow_runs(project_id)`, `cancel_workflow_run(run_id)`.

### 3.2 `SendLedger` and `OpsLedgerEmitter`

**Why the event stream.** The dispatcher's completion handle exists only on the fail-fast
awaitable path, so a queued send has nothing to await, and the handle is consumed by one
caller. The per-agent event stream already carries everything the window uses to show
completion — `turn_start`, content, `turn_end`, `message_failed`, `message_cancelled` — for
every kind of send, queued or not. Reading it once, in process, gives one source of truth with
no dispatcher change. The decorator is the same shape as `WakeLockEmitter`
(`desktop/src-tauri/src/wake_lock.rs`): wrap the base emitter where `AppState.emitter` is
built in `lib.rs`, observe, forward unchanged.

**Entries.** `send_id → { project_id, created_at, recipients: [{ agent_id, message_id?,
turn_id?, status, text: TextCapture, error? }] }` and `run_id → { project_id, status, step,
reason? }`. Bounded: the 500 most recent sends and runs, and nothing older than 24 hours.
Captured text is kept whole in memory (one turn's answer; the dispatcher already holds the
same), clipped only on the way out.

**Correlation.** `ops::send` registers `(send_id, agent_id)` before calling the dispatcher,
because an idle agent can emit `turn_start` before `send_message_impl` returns the
`message_id`. Events resolve to an entry by `message_id` when the entry has one, else by
`(send_id, agent_id)` from the event. `message_failed` is the one event that can carry neither
(`send_id` is `None` before the journal write): it is held in a small orphan map keyed by
`message_id` for 60 seconds, and `ops::send` checks that map when the dispatcher hands back the
`message_id`. Events for sends the ledger never registered (compose-bar sends, workflow steps)
are ignored.

**Text.** `TextCapture` in `crates/harness/src/forward.rs` is the one rule for what counts as
an agent's answer (text blocks plus accepted findings reviews, no thinking, no tool output),
and it observes `AdapterEvent`. The decorator sees `NormalizedEvent` as JSON. Give `TextCapture`
a second observer over `NormalizedEvent` sharing the same arms, so the rule stays in one place,
rather than re-deriving it in the ledger.

**Waiting.** One `tokio::sync::watch` or `Notify` per ledger; `wait_*` re-checks on every
change and on timeout. Dropping a waiter costs nothing.

**Workflow runs.** The same decorator observes the `workflow:<project_id>` channel that
`ChannelProgressSink` (`desktop/src-tauri/src/workflow_commands.rs`) emits on, recording
`Started`, each step, and `Terminal`. Needed because `list_workflow_runs_impl` forgets a run
whose file retention deleted it (completed and cancelled runs), so without the ledger a caller
that looked away could never learn how a run ended.

### 3.3 Wait budget and progress

Every blocking operation takes `timeout_seconds` (default and maximum from M0; placeholders 30
and 300) and, when the client sent a progress token, sends a progress notification on a fixed
cadence (placeholder 15 s) through `RequestContext::peer.notify_progress`. Claude Code's HTTP
idle timeout is 5 minutes and a progress notification resets it; Codex's per-tool timeout is
what bounds the default. The maximum must stay under the smallest hard limit M0 finds, and the
tool descriptions must say "call again until `done`" in words a model follows.

### 3.4 Changes to existing code

- `create_agent_impl` and `attach_agent_impl` take `project_id`. The Tauri wrappers pass the
  active project, so the window's behaviour is unchanged. (`attach_agent` is not exposed over
  MCP in v1; it changes only so the two functions keep one shape.)
- `Dispatcher::send_message` takes `emit_user_message: bool` (the field already exists on
  `WorkPayload::Send`); `send_message_impl` takes it and the compose path passes `false`.
  This is the minimal form of what the remote plan's §5.8 does with `SendOrigin`; §8.
- `merge_workflow_forwards` moves from `lib.rs` into `ops` and the Tauri wrappers call it there.
- `AppState` gains the ledger handle and a `desktop_sync` handle (§5), with builders in the
  `with_*` style.

### 3.5 Tests

- Unit (ledger): registration before `turn_start`; `turn_start` arriving before the receipt;
  a `message_failed` with no `send_id` resolved through the orphan map; cancelled and failed
  terminals; text equals the forward resolver's text for the same event sequence (one fixture,
  both observers); bounds by count and age; a run's terminal recorded after its file is gone.
- Fixture-driven (`ops`, mock harness): fan-out of three under one `send_id` grouped once in
  the conversation; `refuse` with one busy recipient dispatches nothing and names the agent;
  `queue` behind a running turn completes and `wait_send` reports it; idempotent repeat returns
  the stored receipt; `wait_send` on an unknown id answers from the journal for each of
  `failed`, `cancelled`, `started`, `unknown`; `forward` with idle sources sends the composed
  body; `forward` with a mid-turn source past the budget cancels and returns `source_busy`;
  `wait_agent` on an idle agent returns its latest output; `run_workflow` then `wait_workflow`
  through to `completed`; a saved prompt that needs sign-in returns `prompt_needs_sign_in`;
  `directory_missing`; `create_agent` into a project that is not the active one lands in the
  right registry.
- Prove it: with `SWITCHBOARD_HARNESS=mock`, drive `ops` from a test binary and check the
  journal and registry files on disk, not only the return values.

## 4. `mcp` — the server

`desktop/src-tauri/src/mcp/`.

**Listener.** An `axum` router bound to `127.0.0.1:<port>` with the `rmcp`
`StreamableHttpService` nested at `/mcp`, started when the preference is enabled (at launch or
from Settings) and stopped with a graceful shutdown when disabled. The tool handler holds a
`tauri::AppHandle` and reaches `AppState` through it per request. The port is a `config.yaml`
key (§6); debug builds default to a different port than release so a dev instance and the
installed app can both listen.

**Authentication and origin checks**, as `axum` middleware in front of the MCP service (the
pattern in `crates/prompts/tests/oauth_client.rs`):

- `Authorization: Bearer <token>` compared in constant time; missing or wrong → `401`.
- `Host` must be `127.0.0.1:<port>` or `localhost:<port>`; `Origin`, when present, must be
  `http://127.0.0.1:<port>` or `http://localhost:<port>`; anything else → `403`. This is the
  DNS-rebinding defence the specification requires. MCP clients send no `Origin`; browsers do.
- The token: 32 random bytes, base64url, generated when remote access is first enabled, stored
  in the app's secret store (Keychain in release, the file store in debug) under one key, and
  regenerated from Settings. Settings shows it once per view with a copy button; nothing writes
  it to disk unencrypted. Clients keep their own copy in their configuration.

**Tools.** One `#[tool]` per `ops` operation in 3.1, same names, parameters as JSON schema
through `Parameters<T>`. Descriptions are the agent-facing documentation: they state the id
discipline, the `on_busy` choice, the "call `wait_*` again until `done`" loop, and the text
limits. Server `instructions` (the `ServerHandler` info) summarize the orchestration loop in a
paragraph.

**Lifecycle.** Disabling stops accepting connections and cancels in-flight tool calls
(their `RequestContext::ct`); it never cancels agent turns. Quitting the app ends everything.
The listener failing to bind (port in use) is a Settings-visible error, not a startup failure.

**Settings** (`desktop/src/lib/components/SettingsView.svelte`, a new section beside the MCP
providers section): a `Switch`, the port, status (listening on …, or the bind error), the
token with copy and regenerate, and ready-to-paste configuration for each client: the
`claude mcp add --transport http … --header "Authorization: Bearer …"` line, the Codex
`[mcp_servers.switchboard]` block, and the Claude Desktop `claude_desktop_config.json` entry
through `mcp-remote` (§7). Tauri commands: `mcp_status`, `mcp_set_enabled`,
`mcp_regenerate_token`.

**Tests.**

- Fixture-driven, in process: start the server on an ephemeral port against a mock-harness
  `AppState`, connect with the `rmcp` client (the `client` feature is already a dependency of
  `crates/prompts`; add it to the app crate's dev-dependencies with `cargo add --dev`), and run
  `list_projects → create_agent → send → wait_send` end to end; a wrong token is `401`; a
  request with a foreign `Origin` is `403`; a foreign `Host` is `403`; disabling mid-call ends
  the call and leaves the agent's turn running; a tool error arrives as `is_error` with a code.
- Unit: the error-code mapping is total over `AppError` (an unmapped variant is `internal`);
  `clip` at every boundary.

## 5. Desktop window sync

The window learns about projects and agents only through its own actions, and Tauri does not
replay events, so a turn dispatched for a project the window has not loaded is invisible until
reload, and an agent created by MCP never appears. The remote plan's §5.8 solves the first half
for the phone with a round trip; this section is that round trip, widened to cover agent and
project changes, under a name both callers share.

**Backend.** `desktop_sync::ensure_loaded(state, project_id) -> Result<(), AppError>`: emits
`desktop_sync_project { request_id, project_id }`, awaits the matching
`desktop_project_synced(request_id, result)` command for up to 10 seconds, then `ok`, the
frontend's error, or `project_load_timeout`. Behind a trait with a no-op test double so `ops`
tests need no window. `desktop_sync::projects_changed(state)` emits `projects_changed` with no
reply.

**Frontend** (`desktop/src/lib/state/workspace.svelte.ts`):

- A handler for `desktop_sync_project` that, without changing the selection:
  - if the project is not loaded: `ensureProjectLoaded`, then awaits the project's load chain
    until it is empty, exactly as the remote plan's `loadProjectForRemote` describes;
  - if it is loaded: re-fetches the roster, `registerAgent` + `addAgentToProjectRoster` for
    agents it did not have, `replaceAgentRecord` for records that changed (name, model,
    effort), and leaves the rest alone;
  - then acknowledges `ok`, or the error if the open or roster read failed. A failed hydration
    still acknowledges `ok`: nothing is in flight, so dispatch is safe.
- A handler for `projects_changed` that re-reads the project list through the existing
  registry read (`markRegistryMutated` and the read it triggers), so a project created over MCP
  appears in the sidebar.

**Known limitation, recorded not fixed.** A `message_failed` that carries no `send_id` (a
pre-journal failure) is matched by the window to its oldest pending compose send still waiting
for its receipt. An MCP send that fails pre-journal in that window — milliseconds — could show
as the user's send failing. The same limitation applies to phone sends in the remote plan.

**Tests.**

- Frontend: the handler loads without changing selection; acknowledges only after the load
  chain settles (hold the hydrate's IPC open and assert no acknowledgement); a loaded project
  with a new agent registers it and renders its card; a renamed agent updates in place; a
  failed hydration acknowledges `ok`; an open failure acknowledges the error;
  `projects_changed` adds the new project to the list. The remote plan's §5.11 frontend list
  is the model; the new-agent and renamed-agent cases are additions.
- Rust: a send with the stub acknowledging late is answered `project_load_timeout` and
  dispatches nothing.

## 6. Configuration and persistence

- `config.yaml` gains `mcp: { enabled: false, port: <default> }` with `#[serde(default)]`,
  following `auto_reading_mode` including the "an old file loads with it off" test.
- The bearer token lives in the secret store under one key. No other new files.

## 7. Client setup

What Settings shows, and what README documents.

- **Claude Code:** `claude mcp add --transport http switchboard http://127.0.0.1:<port>/mcp
  --header "Authorization: Bearer <token>"`. Recommend `--scope project` in the directory
  where the orchestrating session runs, so coder agents Switchboard launches (which run `claude`
  with the user's configuration) do not load these tools in every turn.
- **Codex:** a `[mcp_servers.switchboard]` block with `url` and the bearer token through

- **Claude Desktop:** a `claude_desktop_config.json` entry running `npx mcp-remote
  http://127.0.0.1:<port>/mcp --header "Authorization: Bearer <token>"` with whatever flag the
  current `mcp-remote` needs to allow plain `http` to localhost. M0 verifies this works; if it
  does not, the contingency is a small in-repo binary that speaks stdio to Claude Desktop and
  Streamable HTTP to the app (`rmcp` has both halves: `transport-io` and the client), and it
  is added as a milestone.

## 8. Relationship to the remote-control plan

Both plans need the same layer above `*_impl`. Building them independently and merging is
the agreed approach; this section is what the merge touches.

| Piece | This plan | Remote plan | At merge |
|---|---|---|---|
| Shared operations | `ops` in the app crate, called by MCP tools | `RemoteBackend` trait in `crates/remote`, implemented over `AppState` | The `RemoteBackend` implementation calls `ops`; `ops::send` is its `send_message` loop and recipient validation (remote §5.5). |
| Send ledger | `SendLedger`, event-fed, stores outcomes and text | `SendLedger`, in memory, stores accepted/rejected results | One ledger, this one; `send_receipt` reads its status. |
| Load round trip | `desktop_sync_project` / `desktop_project_synced`, load **or refresh** | `remote_load_project` / `remote_project_loaded`, load only | One pair of names, the refreshing behaviour. |
| Live user row | `emit_user_message: true` on MCP sends | `SendOrigin` on every send, always emitted, reducer de-duplicates | `SendOrigin` replaces the flag; this plan's sends carry `Mcp`. Add `Mcp` to the enum when it is introduced, because the value is journaled and an older build cannot read a value it does not know. |
| Conversation paging | `read_conversation` tail with `last_n_items` | `TranscriptWindow` with cursors and a byte budget | `read_conversation` takes the cursor form. |

Likely conflict sites: `commands.rs` (send path, `create_agent_impl`), `crates/dispatcher`
(`send_message`'s signature), `workspace.svelte.ts` (the load handler), `lib.rs` (emitter
chain, command registry). None is structural.

## 9. Security

**What's at stake** is the remote plan's §2 sentence, unchanged: a send runs with permission
prompts disabled, so whoever can call `send` can run anything on the Mac. The server is local
and off by default; its security work is making sure only a process the user configured can
call it.

| Threat | Defended? | By |
|---|---|---|
| A web page in the user's browser reaches the server (DNS rebinding, cross-site request) | Yes | `Origin` and `Host` checks; bearer token the page does not have; bound to `127.0.0.1` |
| Another user on the machine | Yes | Bearer token; the token is in the Keychain, never a world-readable file |
| Another process running as the user | No | Out of scope; such a process can already run the harness CLIs itself. The token in the client's own configuration file has the user's file permissions. |
| A client's model loops and burns quota | Partly | Settings toggle stops the listener at once; `refuse` by default means a loop cannot pile up queued turns; rate limiting is a follow-up |
| An agent Switchboard launched calls the server | Partly | Documented; `refuse` makes a self-send fail; scope the client configuration (§7) |
| `mcp-remote` (third-party, run through `npx`) sees the token | Accepted | It runs as the user, like any client; the in-repo bridge is the alternative if this is not acceptable |

**Disclosure.** README's new **Agent access** section opens with: *"An agent connected over
MCP has the same reach as the keyboard. Agents run without approval prompts, so any program
holding the token can run commands on your Mac. It is off by default; regenerate the token in
Settings → Agent access to revoke every client."*

**Review boundary.** The middleware (token comparison, `Origin`/`Host` rules), token
generation and storage, and the tool layer's input validation get a `/security-review` pass in
M3, separate from the feature review.
