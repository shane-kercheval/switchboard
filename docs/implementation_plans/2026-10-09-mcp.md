# Agent access: an MCP server for Switchboard

**Status:** implemented (all milestones complete as of 2026-10-14) · **Revision:** 47 · **Created:** 2026-10-09 · **Revised:** 2026-10-18

An MCP server inside the Switchboard app, so an external agent (Claude Code, Codex, Claude
Desktop) can run the same operations a user runs from the keyboard: create projects and agents,
send a message to one or more agents, wait for the replies, forward one agent's output to
others, run workflows, and read the conversation; and, from M5 on, read the accounts' usage
limits and each agent's context fullness, compact an agent, and fork one. The server listens
on the Mac only. Hosting it elsewhere is a later, separate decision with its own security
design.

The product framing this extends is `docs/system-design.md` §1 ("human-directed
orchestrator"): an agent on the other end of MCP is one more thing that can direct work, under
the same rules as the user. The design it shares pieces with is
[`2026-09-29-remote-control.md`](2026-09-29-remote-control.md), the iPhone app; §4 below says
what the two share and how they merge.

- **Revision 48 (2026-10-19)** — A reply still being written reads as running, and two of
  §0.1's merge items are settled (owner decisions).
  - `read_conversation` reported a Codex reply still being written as `failed`, with no
    reason: Codex's parser closes an unfinished last turn as failed, and nothing is
    journaled until the turn ends. Claude's erred the other way while a turn waited on
    background work: Claude writes the turn's first cycle, end-of-turn marker included, so
    it read as `complete`. A turn the ledger has seen start and not end now reads as
    `running`, with no reason, whatever its partial copy on disk says, and so does every
    later turn of that agent, because a compaction part-way through a turn splits it on
    disk and only the first piece carries the send. The ledger is read before the session
    files and again after them, so a turn that starts or ends during the read is still
    caught. `read_reply` reports such a send as `running`, and `read_latest_reply` leaves
    out the running turn and the pieces after it, so the three readers agree. A turn run
    outside Switchboard, such as a terminal resume, is unknown to the ledger and reads as
    before.
  - Not built: a ledger record of the turn that just ended, for the moment between
    Switchboard's `turn_end` and Codex writing its `task_complete`, should Codex write it
    after its terminal event. Nobody has observed that moment, and the adapter reads the
    whole rollout between Codex's terminal event and `turn_end`, so a write that lands
    before that read finishes is on disk by `turn_end`. `docs/harness-behavior.md` records
    the timing as unmeasured.
  - §0.1: the `message_failed` item is closed. Revision 27 announces a refused enqueue
    before reporting its failure (`Dispatcher::enqueue`), so the window matches the
    failure by `message_id` and never takes the user's own pending message for it. And
    `send_accepted` is emitted when a send is enqueued: the actor announces a send as it
    admits it to the agent's queue, whether the agent is idle or busy (`admit` in
    `crates/dispatcher/src/lib.rs`), so the phone's queued-sends follow-up uses it as it
    is. §4's "Queued sends visible" row says so.
  - Decided against for now: a conversation cache, because a read of the largest real
    project (168.6 MB of session files) took 0.31 s in an optimized build, nearly all of
    it parsing one 100 MB Codex rollout; and cursor paging, because no orchestrator's
    report asks for older items than the newest that fit.
- **Revision 47 (2026-10-18)** — Tool names that say what the tools do, a prompt reader, and
  step progress in `wait_workflow` (owner decisions, from orchestrators' reports).
  - Four tools are renamed, with no aliases for the old names: `read_send_output` is
    `read_reply`, `read_agent_output` is `read_latest_reply`, `set_agent_selection` is
    `set_agent_model_and_effort`, and `cancel_agent` is `stop_agent`. Every description
    and result had called the thing read a reply, and "output" read as a command's
    output; the old selection name said neither model nor effort; and the window calls
    the action Stop agent. The `ops` functions take the same names, so each tool still
    runs the operation of its own name. A cut's `read_with` now names `read_reply`, and
    a test checks that every cut names a tool that exists. The built-in orchestrator
    prompt named one of the four, `cancel_agent`, and now names `stop_agent`; a prompt the
    user saved that names any of the four must be updated by hand. The test that every
    tool a built-in prompt names exists now also checks names starting `stop_`, and the same
    scan now covers the server instructions and every tool description. Error messages also
    name the window's own commands, which are not tools, so a separate test checks them
    against a list of the retired names, which each later rename extends. The window's own
    commands keep their names. The milestone sections below describe what
    each milestone built and keep the names of the time; §0, §2, and §7 use the new ones.
  - `stop_agent`'s description opens with what it does: stop the agent's current turn
    and drop every message queued for it, as Stop agent does in the window.
    `cancel_send`'s one-reply form says it is what the stop control on that reply does in
    the window, so a user's "stop the reviewer" leads to the narrow action, not to the
    one that drops the user's queued messages. `create_agent` points to
    `set_agent_model_and_effort` for a later change.
  - `read_prompt` returns one saved prompt: its metadata as `list_prompts` gives it, and
    `template.text`, the template with its placeholders intact, for a built-in or local
    prompt. A prompt server (the user's tiddly server, for example) keeps its template
    and gives out only finished text through MCP's `prompts/get`, so its `template` is
    null and `template_note` says plainly that the template lives on the server and that
    passing `args` returns what a send would deliver. With `args` (`{}` for a prompt with
    none), any provider's prompt also returns `rendered.text`, through the same render a
    send uses, with its argument checks and errors (`invalid_argument`,
    `prompt_needs_sign_in`) and the call's wait budget, since a server's render is a
    network call. A prompt server's metadata exists only in Switchboard's cached copy of
    each server's prompt list, which lacks a server that needed sign-in or was unreachable
    at its last fetch, or has not been fetched yet; a send renders without consulting it.
    So with `args` the prompt renders as a send would whether or not the cache lists it,
    and when it does not, `arguments` is null (not an empty list, which would read as
    "takes none") and `listing_note` says why. Without `args` it reads the cache and
    nothing else, classifying a miss as the window classifies a saved prompt: missing
    (`invalid_argument`) only when the server's last fetch succeeded without it, and
    otherwise the server's state at that fetch, `prompt_needs_sign_in` when it needed
    sign-in. It never refreshes the cache, which would refetch every configured server
    and reload the window's prompt list on each read. Built-ins the user hid from
    `list_prompts` are read as a send reads them. Text over the result budget is cut evenly and each cut reported, with
    no call to read on (owner decision: a saved prompt is a few thousand characters).
    The text sits under `text` in each object because the budget cuts only fields of that
    name.
  - `wait_workflow` gives each agent of the current step, while the run is unfinished,
    the `send_id` of the run's newest send that reached it and, while Switchboard holds
    that send, its `status`, `activity`, and `recent_text` as `wait_send` reports them
    (`status` added by owner decision, so a missing `activity` is not ambiguous between
    waiting in line and finished). The step whose agents are working is usually a wait
    step, which made no send of its own; the newest send that reached the agent is then the
    send step's, and usually the turn a blocked wait step waits on, since a workflow sends
    to an agent again only once its earlier turn has finished. The field promises only the
    newest send that reached the agent, because the engine awaits an agent's turns oldest
    first. A recipient a failed step never offered the message to was not reached, so that
    send is skipped for it. Polls read only what Switchboard holds in memory, each send
    once however many of the step's agents it reached: after a restart, or once the send is
    pruned, the fields are absent. A finished run carries none.
  - `list_projects` leaves out archived projects unless `include_archived` is true, as the
    window's project list does until the user opens its archived view. **This changes the
    default for existing callers:** an orchestrator that listed every project now sees
    only active ones. An archived project's id still works in every other tool, and each
    listing still says whether it is archived. Archiving itself is still not offered. A
    folder may hold several projects, so `create_project`'s description asks the caller to
    check with `include_archived` for one the user already has for the folder before
    creating another, whose agents and history a new one would not have.
  - **An error code existing callers see changes** (owner decision): a prompt server that
    refuses the arguments it was given (MCP's invalid-params reply) is now
    `invalid_argument`, where it was `internal`, for `send`, `forward`, `fork_agent`, and
    `read_prompt`. `internal` told the caller nothing it could act on; the refusal is the
    caller's to fix, as a local prompt's missing argument already was. A workflow step that
    hits it is unchanged: its failure is the run's reason text, not a code.
  - The server instructions name every tool near the top, grouped by what the caller is
    doing (look, set up and tidy, start work, stop work, wait), from a group each tool
    must declare, so a new tool cannot be left out. Per-tool detail moved into the tools'
    own descriptions, where it already was: the list of tools taking `max_chars`,
    `fork_agent`'s `agent_busy_elsewhere` advice, and the rule for a workflow that is not
    invocable. The instructions are 3,555 characters, against Claude Code's cut at 4,096,
    which its MCP documentation still states (rechecked 2026-10-18; the research note's
    "Later observations"). The list moved up because Claude Code keeps only the start of
    instructions over its limit, and before v2.1.296 that limit was 2,048. A test now also
    keeps every tool description under 4,096, Claude Code's cut for a tool loaded up
    front; the longest, `wait_send`'s, is 2,516.
  - `wait_agent`'s result keeps its fields `output` and `output_unavailable`: renaming
    them would change a result's shape, which this revision does not.

- **Revision 44 (2026-10-18)** — An orchestrator reads a run's replies in one call and
  forwards a reply that is no longer an agent's latest (owner decisions, from orchestrators'
  reports).
  - `read_workflow_run` returns every reply a workflow run produced, in step order: the run's
    status, then each send with its step, label, `send_id`, `done`, and `source`, and each
    recipient as `wait_send` reports it, with its agent's name and, once it completed, its
    reply. An orchestrator had read a run's replies one `read_send_output` call at a time,
    and an agent's latest answer holds only its last step, so a reviewer's first round was
    easy to lose. It is a read, not a flag on `wait_workflow`, and does not wait: on a running
    run it gives the replies so far. Its size follows the rule every reply-carrying result
    follows, with no limit of its own: replies cut evenly, sends and recipients never dropped,
    each cut read on through `read_send_output`, and `max_chars` taken as elsewhere. Once
    Switchboard no longer holds the run (after a restart, or once pruned), a failed or
    interrupted run's file still answers with `sends_unavailable`, and a completed or cancelled
    run, whose file is deleted when it ends, is `run_unknown`; the replies stay in
    `read_conversation`. A send the ledger no longer holds while it still holds the run is
    read from the journal, where a recipient the step refused reads `not_dispatched`: only the
    ledger recorded why. That read costs one journal read and one session-file parse per
    recipient for each such send, a known cost left as is: a few extra reads for a run of a
    few sends, and reading each file once per call would mean reworking the reader `wait_send`
    uses after a restart. This is the follow-up the "Workflow results" row of §0 named.
  - `forward`'s sources, in `sources` and in a prompt's `forward_args`, may name a `send_id`.
    That reply is forwarded verbatim under the agent's usual label, whatever the agent has
    said since, without waiting on the agent, which may be busy with other work. A reply still
    to be sent (its send is being handed to its recipients one at a time), waiting in line, or
    running is refused at once with `source_busy`; each arises only for a send Switchboard
    follows live, so the advice is `wait_send` on that send, where `wait_agent` would return at
    once for an agent the send has not reached. One that failed, was cancelled, or never
    reached the agent is `invalid_argument`. So is one Switchboard cannot tie to the send: it
    may still be running (a message typed in the window), the app may have restarted while it
    ran, or Switchboard cannot tell which turn answered (owner decision: a reply matched by
    position is a guess the recipient could not tell from the agent's answer); the caller reads
    it with `read_send_output`, which says how it was matched, and sends its text itself. A
    send the agent did not receive in the source's project is `send_unknown`, as is a message
    the window sent whose reply has not started, which nothing on disk tells apart. The forward
    sends nothing on any of these, and the retry key is released. A reply already in hand
    needs no journal, so its project's is not read, and a damaged line there cannot block it.
    Without `send_id` a source behaves as before. `run_workflow`'s
    `forward_sources` take their own type without `send_id`: a workflow's forwarded inputs are
    read from each agent's latest completed answer when the run starts. The window's forwards
    and their request shapes are unchanged.
  - Both read a send the way `wait_send` does, through one function: the ledger's record while
    it holds the send, so a running reply reads `running`, and otherwise the journal, where a
    reply counts as completed only through a durable link to its send and `started` means the
    outcome could not be confirmed. A forward naming a reply therefore never sends one matched
    to its send by position, a guess that could pick the wrong turn.
  - The server instructions list `read_workflow_run` among the tools that take `max_chars`;
    `run_workflow` and `wait_workflow` point to it. The built-in orchestrator prompt's review
    loop reads a run's replies with it.
- **Revision 43 (2026-10-18)** — Fixes from two reviews of revision 42 (owner decisions).
  - A cancelled run cancels its own turns send by send rather than agent by agent. It had
    stopped whatever each agent with an unobserved turn was running, so an agent whose step
    reply ended while the run waited on another agent, and which then started a message the
    user had queued behind it, lost the user's message. Every cancel that ends a run reached
    it, for as long as the slower agent kept working: the window's run cancel,
    `cancel_workflow_run`, a whole-send `cancel_send`, and a single reply's cancel, from the
    window's stop on that reply or `cancel_send` with `agent_id`. A send-scoped cancel stops a
    turn only while it answers that send and drops the send if it is still waiting in line,
    so it also stops a run's message accepted behind another turn's post-reply drain, which
    the per-agent cancel left to run after the run ended. A reply that has ended and is
    draining is left alone either way.
  - A cancel of a workflow send, or of any one of its replies, that lands while the step is
    handing the message out stops the step offering it to anyone else and ends the run
    cancelled, also when the dispatcher's answer for that recipient was that it was busy.
    The run had ended failed there, held for dismissal, which blocks the project's next
    workflow; and after a cancelled reply, the step had kept offering the message to the
    rest, for the run's cleanup to cancel. The same holds when a later recipient's
    pre-dispatch check refuses after the cancel: the engine decides once, when the step
    stops, whether it was cancelled, and that one decision sets both the run's result and
    what the recipients never offered show (`cancelled`, not `workflow_step_failed`).
  - A step that could not get its message ready (its prompt did not render, an agent was
    unavailable, or a pre-dispatch check refused one) refuses the recipients it never reached
    with the new code `workflow_step_failed` and the step's reason, where they read
    `not_dispatched` with no reason. Recipients after a busy agent stay `not_dispatched`,
    which means an earlier recipient was refused. The tools' own sends differ: one that
    fails before dispatching anything is released and returns its error.
  - Between two turns, each agent's dispatcher actor now applies every command already
    waiting before it starts the next queued message, where it started the message first and
    read the commands during that message's turn. A turn stops reading commands once its
    stream ends, and a starting turn reads none until its message has reached the harness, so
    a cancel or removal of the next message that arrived as the turn ahead of it ended let the
    message reach the harness first: a cancelled run's waiting message started and was
    stopped at once, and the window's removal of a queued message failed. Applied between
    turns, a fail-fast send is refused while work is still queued, as it is while a turn
    runs, so a workflow step still fails on an agent with queued work. A forward that waits on
    its source's current turn and arrives in that gap no longer waits on the next queued turn:
    it reads the latest completed answer, as it does while a turn runs.
  - The `cancel_send` description says that in a workflow a cancelled reply stops the other
    recipients' replies too, and the `requested` outcome's comment no longer says it covers
    a send from before a restart, after which the cancel is refused.
- **Revision 42 (2026-10-18)** — A workflow's sends are held in the send ledger (owner
  decision, from an orchestrator's report). An orchestrator ran review-and-reconcile, took a
  send id from `wait_workflow`'s sends, and called `wait_send` on it while both reviewers were
  working; it answered `started` with `done: true` and `source: journal`, the reply meant
  for a send cut off by a restart. The ledger held only sends made through the tools, so a
  workflow's send always fell to the restart fallback, whose `done` is always true: the
  orchestrator's loop, which stops when `done` is true, would have stopped while the agents
  were still working.
  - The workflow engine's dispatch provider registers each send step's send before building
    its message, marks each recipient accepted (minting its `message_id`) just before
    offering it, records a busy agent as rejected, and settles the send when the step's
    dispatch ends. The dispatcher's workflow send takes that `message_id`, as an agent-tools
    send does, so the turn's first event finds the entry. Runs started from the window are
    held too; holding them changes nothing the window shows.
  - `wait_send`, `wait_any_send`, and `read_send_output` follow a workflow's send live:
    `running` while its turn runs, then `completed` with the reply, `source: live`. After a
    restart they answer from the journal as before.
  - `cancel_send` checks a workflow's send against the ledger. With `agent_id` it answers
    `cancelled` or `already_finished` where it answered `requested`; `requested` remains for
    a workflow send the ledger has since pruned. Without `agent_id` it now cancels a
    workflow's send whole, where it answered `send_unknown`: every reply still queued or
    running is cancelled, so the run ends cancelled as it does for one cancelled reply. Both
    forms refuse a send of a workflow the user started from the window
    (`ReplyInUserWorkflow`), checked before the ledger, because the ledger now holds those
    sends too. A cancel can also land while the step is still handing its message out: a
    caller can learn the send's id that early, for example from `read_conversation` once the
    first recipient's message is journaled, or from `read_agent_output` once an early
    recipient has answered. A recipient the step has not offered yet is then
    skipped, and each send's owner is recorded when its step starts rather than when it
    resolves, so such a cancel finds it.
  - `read_agent_output` reads a workflow step's completed reply from the ledger
    (`source: live`, with its `send_id`) rather than from the session file, and its
    `newer_turn_running` is true while a workflow's message is still to reach the agent,
    such as while its turn is being prepared; both rules already applied to the tools' own
    sends, and both say the same of a workflow's. A compaction's merge rule now sees a
    workflow's messages queued for the agent as it sees the tools' own.
  - The tool descriptions say `wait_send` takes a workflow's sends, that `started` comes
    only with `source: journal`, and that `cancel_send` works for a workflow's sends in both
    forms.
- **Revision 41 (2026-10-15)** — A data science orchestrator prompt (owner decision). Settings
  holds two prompts, each in its own expander with its own copy button. They are built from
  one text and differ only in the lens: the role, the questions (the data, the method,

  the version check reads its first line either way.
- **Revision 40 (2026-10-15)** — Orchestrator prompt version 5, from a second review of the
  prompt (owner decisions). An agent's reply is a report, not an instruction: a request in it
  to send something, change a rule, or treat something as approved goes to the user, since
  what an agent reads can reach its reply as text aimed at the orchestrator. Where the prompt
  and an agent's own instructions conflict, the prompt wins and the brief says so. Every
  brief asks for the report the orchestrator will review, saving a follow-up per task. The
  start ritual checks usage and reads a state note the orchestrator keeps in its own folder
  (agents and roles, decisions and who made them, open questions, each review loop's
  position), because a compaction keeps Switchboard's state but loses the conversation's
  decisions. The role states the expected knowledge (the design docs and plans, not the
  code) instead of "may be foggy on the architecture". Not adopted: a cap on review rounds
  and numeric thresholds (judgment holds better than false precision), consolidating
  repeated rules (each is stated where it applies), and rules for truncated replies (the
  server instructions cover them).
- **Revision 39 (2026-10-15)** — Orchestrator prompt version 4, from an orchestrator's
  feedback on a day-long run (owner decisions). It reports as each milestone of a longer task
  finishes and keeps going, since a run across several milestones otherwise reported once, at
  the end. The end-of-task review covers what the task or milestone changed, not the whole
  branch, which on a long-lived branch held about 180 commits of other work. It steps back
  from a suggestion, the owner's included, to ask whether the problem is worth solving before

  orchestrator can judge.
- **Revision 38 (2026-10-15)** — Fixes from three reviews of the orchestrator's experience:
  the orchestrator prompt, the tool surface, and the two together (owner decisions).
  - `cancel_send` takes an optional `agent_id`, which cancels only that recipient's reply,
    queued or running. It needs no ledger record, so it also reaches a workflow's sends,
    whose ids `wait_workflow` lists (cancelling one ends the run, as any cancelled
    participant does), and answers `requested` when there is no record to check. The
    orchestrator had no way to unstick one agent: `cancel_send` stopped every recipient,
    and `cancel_agent` also drops every message queued for the agent, the user's included.
  - `wait_send` gives activity and `recent_text` only for a recipient whose own turn runs. A
    recipient waiting in line showed the turn ahead of it, possibly the user's, as its own,
    so the 20-minute stuck rule could lead to cancelling the user's work.
  - `read_agent_output` carries `newer_turn_running`, since its answer is the agent's last
    finished one and said nothing when a newer turn was under way.
  - A call whose client sent no progress token gets a 45,000-character result budget by
    default instead of 100,000. Claude Desktop is the one measured client without one, and
    its Code tab saves a larger result to a file; the instructions had relied on the model
    knowing which client it runs in to pass `max_chars`.
  - The server instructions say a project's agents share its folder, and the "report and
    stop" list is corrected: a Claude or Antigravity usage limit arrives as `harness_error`;
    `project_locked` is added; `agent_busy_elsewhere` right after `fork_agent` is the fork's
    first reply holding its source, so wait and resend; a workflow that is not invocable (a
    `pause_for_user` or `for_each` step, or a parse error) is skipped, not a stop. They name
    the orchestrator prompt's version, so a stale pasted copy is noticed; a test checks the
    prompt's version and that every tool it names exists.
  - Descriptions: `run_workflow` points to `wait_workflow`'s sends instead of
    `read_agent_output`, which loses a reviewer's first round; `wait_send` explains
    `source: unknown` and a reply a restart cut off; `forward` documents a failed source's
    note; `remove_agent` carries the remove-only-your-own rule; `list_workflows` says what
    `invocable: false` means. Errors say what to do next (busy recipients, an agent not in
    the project, a built-in workflow named without `is_builtin`, a name where an id belongs).
    A workflow name that is a path is refused, and the tools that act or stop declare
    `destructiveHint` explicitly.
  - `review-and-reconcile`'s final step tells the worker not to change files in that reply,
    so fixes come after the reviewed change is committed.
  - After review:
    - A single-recipient cancel is recorded on the recipient, and the send checks it before and
      after each hand-off, as it does a whole-send cancel: a recipient not yet offered the
      message is skipped, and one offered meanwhile is cancelled once admitted (its turn may
      begin before it is stopped). A send whose every recipient was cancelled this way settles

## 1. Architecture

```
Claude Code / Codex ──HTTP──▶ 127.0.0.1:<port>/mcp
Claude Desktop ──stdio──▶ mcp-remote ──HTTP──▶   │
                                                 ▼
                                   axum: bearer token
                                                 ▼
                                   rmcp service: Host/Origin checks, tools (src/mcp/)
                                                 ▼
                                   ops (desktop/src-tauri/src/ops/)
                                     ├─ *_impl in commands.rs / workflow_commands.rs
                                     ├─ Dispatcher
                                     ├─ SendLedger ◀── OpsLedgerEmitter (EventEmitter decorator)
                                     └─ desktop_sync ◀──▶ frontend (sync round trip, notifications)
```

Three new modules, all in the app crate:

- **`ops`** (M1) — one function per operation, taking explicit ids and `&AppState`, built on
  the existing `*_impl` functions. This is the application layer the compose bar implements in
  TypeScript today: fan-out, sending a composed forward, recording outcomes, waiting. Every
  client that is not the window calls it. The MCP tools are thin wrappers; the remote-control
  plan's `RemoteBackend` implementation should become one too (§4).
- **`ops::ledger`** (M1) — the `SendLedger`: per-send, per-recipient status and reply text, fed
  by an `EventEmitter` decorator in the existing chain. Idempotent sends and `wait_*` read it.
- **`mcp`** (M3) — the listener, authentication, tool definitions, and the Settings commands.

Plus frontend handlers for the sync round trip, the change notifications, and announced MCP
sends (M2).

What does not change: the dispatcher's actor model, the harness adapters, the journal format,
`config.yaml`'s existing keys, and the IPC commands the window calls (some gain parameters that
the Tauri wrappers fill as today, so no frontend change). No stored data changes shape.

## 2. Conventions every milestone follows

Set here so later milestones reuse them.

- **Explicit ids.** An `ops` function never reads `active_project_id`. Every operation takes
  the `project_id` it acts on; agent operations take `(project_id, agent_id)` and check the
  agent belongs to that project (the forward resolver's ownership check, `resolve_source_ref`
  in `commands.rs`). Names are for display; `list_agents` maps one to the other.
- **Loading tiers.** Each operation opens the project only as far as it needs. Rationale:
  opening locks the project and needs the agent cache; the window round trip exists only
  because the window's first history load assumes no turn is running (remote plan §5.8), so
  only an operation that starts a turn needs it. Everything else must keep working when the
  window is slow or hung.
  - **Read** (lists, conversation, outputs, waits, cancels, workflow description and runs):
    open nothing, lock nothing. Reads use the unlocked store paths the existing read-only
    impls already use (`list_project_agents_readonly_impl`, and `load_project_conversation_impl`'s
    fallback to `open_project_from_store`). A missing working directory does not fail a read.
  - **Change** (create, rename, model and effort; dismissing a run): `open_project_impl`
    first, which is a no-op for a loaded project. Then a window notification the backend does
    not wait on (M2).
  - **Turn** (send, forward, run workflow): `open_project_impl`, then the blocking window sync
    (M2), then the operation. Nothing is dispatched if either step fails.
- **One error type, stable codes.** `ops` returns `AppError`. The tool layer maps it to a
  closed set of snake_case codes a model can act on: `project_not_found`, `project_not_loaded`,
  `agent_not_found`, `unknown_recipient`, `agent_busy`, `agent_busy_elsewhere`, `source_busy`,
  `directory_missing`, `desktop_unavailable`, `project_load_timeout`, `project_locked`,
  `prompt_needs_sign_in`, `prompt_too_large`, `send_unknown`, `run_unknown`,
  `workflow_run_requires_dismissal`, `workflow_already_running`, `request_in_progress`,
  `result_too_large`, `compaction_unsupported`, `no_session`, `fork_not_materialized` (M6),
  `fork_unsupported` (M7), `invalid_argument`, `internal`, and, on a workflow send's
  recipient only, `workflow_step_failed` (revision 43). `request_in_progress` is a retry that
  joined an in-flight request and ran out of budget: call again with the same key.
  `result_too_large` is a single item that cannot fit the budget even with its text removed:
  read it in pages. Spellings shared with the
  remote plan's §4 keep its spelling: `unknown_recipient` is a send or forward recipient not in
  the roster; `agent_busy_elsewhere` is `AppError::SessionInUse` (another process, such as a
  terminal resume, holds the harness session). M6 and M7 map the existing variants:
  `CompactionUnsupported` → `compaction_unsupported`; `CompactionSourceHasNoSession` and
  `ForkSourceHasNoSession` → `no_session`; `CompactionForkNotMaterialized` →
  `fork_not_materialized`; `ForkSourceBusy` → `source_busy`, including the Codex case where
  another program holds the parent's session, which the fork code reports as a busy source
  because the useful advice is the same (wait for the source); `SessionForkUnsupported` →
  `fork_unsupported`; `CodexForkNeedsRealHarness` → `internal`. Today the fork variants map
  to `invalid_argument` and the compaction variants fall to `internal`; the totality test
  gains all of them.
- **Tool results are JSON text.** Every tool returns one `text` content block holding a
  serialized JSON object. Errors are a tool result with `is_error: true` and the body
  `{ "code": …, "message": … }`, not a JSON-RPC error, because clients show tool errors to the
  model and some swallow protocol errors.
- **One budget per result.** `ops` returns full text. Each result type's budget rules (which
  text fields may be cut, which list may lose its oldest items, how a cut field is read on)
  live beside the type in `ops`, and the tool layer applies them through one helper that keeps
  the serialized envelope under the result budget (§0): 100,000 characters, for every client.
  A fan-out's recipients are never dropped, and their replies share the budget evenly (each
  long reply cut to the same length). A conversation keeps whole items, newest first, until
  the budget is full, and reports how many older items it left out; only a single item larger
  than the budget is cut. Ids, names, paths, statuses, and error messages are never cut. Each cut field is listed in the
  envelope with its path, total length, kept length, and the call that reads on
  (`read_reply` with the `offset` the cut ended at), or `null` when nothing can. The
  full text stays on the Mac.
- **Nothing MCP does needs the window, except the turn tier.** `ops` must be callable from a
  test with `AppState` built the way `commands.rs`'s tests build it (`state_with_project`,
  `MockHarnessAdapter`). The window half of `desktop_sync` is a trait whose test double
  acknowledges immediately (or late, or with an error, when a test asks); the backend half of
  every tier is real in tests.
- **Rationale goes into the code.** Every decision in §0 and every "why" paragraph in the
  milestones is carried into the code as a doc comment on the type or function that embodies
  it, in the style the dispatcher and `commands.rs` already use. A reader of the code must not
  need this document to know why the ledger reads events, why `refuse` stops at the first
  refusal, why sends run as their own task, or why the sync round trip waits. Chronology and
  milestone names stay out of the code (`AGENTS.md`); the reason goes in.
- **Logging.** Every tool call logs its name, project and agent ids, and outcome at `info`.
  Prompt text and reply text are never logged.
- **Tests** use the repo's vocabulary: unit tests inside modules, fixture-driven integration
  tests with the mock harness, one optional live test named `live_claude_mcp_…`. Long commands
  run in the foreground; every milestone ends with `make check` green.

### M1 — `ops` and the send ledger

**Goal.** A Rust-only application layer that does everything the compose bar does around a
send (fan-out, forward-and-send, outcome tracking, waiting) plus project, agent, prompt, and
workflow operations, callable without the window, for any project whether or not the window
has opened it.

Outcomes:

- A caller inside the app can create a project and agents, change an existing agent's name,
  model, or effort, and read an agent's output, for any project, including ones nobody has
  opened since launch.
- A caller can send one message to several agents and get each recipient's status and reply
  text back. A busy recipient known up front refuses the whole send; otherwise the send stops
  at the first refusal and says exactly which recipients ran.
- A send can opt into queuing behind a busy agent, and a queued send can be waited on too.
- Retrying a send with the same key never sends twice, even when the retries run concurrently
  or the first call was cancelled; a key reused for a different request is an error.
- A caller can forward agents' latest output, from this project or others, to agents in this
  project, with or without a saved prompt, composed exactly as the compose bar composes it.
- A caller can wait until an agent would accept a send, and read its latest output.
- Long replies are read in pages that stay on the same reply.
- After an app restart, waiting on an earlier send reports `completed` with the reply when
  the journal proves it, instead of hanging or erroring.
- A workflow can be described (every required input, including those derived from saved
  prompts), started with agents given by id, waited on, and, when it fails, dismissed.

**Outline.** `desktop/src-tauri/src/ops/`: pure application logic over `AppState`; no `rmcp`,
no Tauri types beyond what `*_impl` already uses.

*Operations.* Each a `pub async fn` taking `&AppState` and the arguments shown, returning
`Result<…, AppError>`. The tier from §2 is in brackets.

Read:

- `list_projects()` [read] — `list_projects_impl` plus, per project, `status: busy | idle`
  computed the way the remote plan's §5.7 says: busy when any roster agent has pending work in
  the dispatcher or a workflow run is registered for it. Unopened projects are idle.
- `list_agents(project_id)` [read] — `list_project_agents_readonly_impl` plus `busy: bool`
  (the `accepts_now` query below, negated) and each record's model, effort, and quick choices.
- `read_conversation(project_id, last_n_items)` [read] — `load_project_conversation_impl`,
  reduced to a compact shape for an orchestrating agent, tail-cut to `last_n_items`, then
  filled newest-first with whole items until the result budget is full: user messages grouped per fan-out (text, recipients, attachment labels);
  agent turns as their answer text (every text block, the same text a forward sends) with
  `send_id`, send correlation, and one status (`complete`, `running`, `failed`, `cancelled`)
  with the journal's outcome, reason, and failure kind folded in; a failed or cancelled
  marker only for a send with no reply; a `compacted` marker where an agent's context was
  compacted; and per agent its name, any load error, and a count of skipped transcript lines.
  Every item carries its time and the list is in time order. Tool calls, their output, edit
  diffs, thinking, and other harness bookkeeping are left out, and no tool summary replaces
  them: the agent's answer says what it did. The window's own shape cannot be used, because
  one agentic turn overflows the budget on its tool cards alone. A cut answer reads on
  through `read_send_output` with `read_from: transcript` from where it was cut, when the turn
  has a `send_id`. Paging by cursor is the remote plan's `TranscriptWindow` (its M3); not
  built here.
- `read_send_output(project_id, send_id, agent_id, offset, read_from)` [read] — one
  recipient's reply to one send: the ledger's full captured text when it holds text for that
  send and `read_from` is `auto` (the default), otherwise the agent's own transcript
  correlated to its journaled sends with the merge's per-agent classifier (one file read, the
  same matching the merged conversation does). `read_from: transcript` always reads the
  transcript, which is the copy `read_conversation` shows. The ledger's status wins when it
  holds the send; otherwise the journal's recorded outcome wins over the transcript's status,
  as in `wait_send`'s restart fallback; a journaled send
  with no reply pages empty (`failed`, `cancelled`, or `started`) rather than reading as
  unknown. The response says whether that match is a durable link or positional
  (`SendCorrelation`), so a caller knows how much to trust a positional match. Pages are sized
  by serialized length so none can exceed the budget. This is the stable way to page a long
  reply.
- `read_agent_output(project_id, agent_id)` [read] — the agent's latest completed answer, for
  turns the caller did not send (a user's, a workflow's): the ledger's text when it holds the
  agent's latest turn and it completed, otherwise the journal's typed outcome for a latest
  turn that failed or was cancelled (the resolver's note as text), otherwise the newest
  completed turn in the agent's own transcript, correlated to its send with the merge's
  per-agent classifier. The response carries that turn's `send_id` and correlation when the
  classifier assigns one, so a caller pages with `read_send_output`; it never guesses a
  `send_id` from the last journaled send, which would name a newer running turn.
- `list_prompts()`, `list_workflows()` [read] — the existing impls.
- `describe_workflow(project_id, name, is_builtin)` [read] —
  `describe_workflow_form_fresh_impl`: declared inputs plus arguments derived from the
  workflow's saved prompts, and compatibility. `list_workflows` alone omits the derived ones.

Change (each followed by a window notification, M2):

- `create_project(name, directory)` — `create_project_impl` (which loads and locks the new
  project); seeds nothing.
- `rename_project(project_id, name)`.
- `create_agent(project_id, name, harness, model?, effort?)` — starts from the user's
  per-harness defaults in Settings (default model, default effort, both quick-choice lists),
  as the desktop seeds a new agent, then applies the caller's model and effort.
- `rename_agent(project_id, agent_id, name)`,
  `set_agent_selection(project_id, agent_id, model?, effort?)` — an omitted axis is unchanged;
  an explicit `null` resets it to the harness default (a record with no model means "use the
  harness default", so a caller changing only the effort must not wipe the model). The
  quick-choice lists update themselves (core appends the current value). Read, merge, and
  write happen under one `registry_write` acquisition so a concurrent window edit is not
  undone.
- `dismiss_workflow_run(project_id, run_id)` — refuses unless the run's file classifies as
  `failed` or `interrupted` (`classify_run_file`, `workflow_commands.rs`), not merely "not
  live": a run leaves the live registry before retention deletes a completed run's file
  (`workflow_commands.rs:1352-1353`), so for a moment a completed run is neither. Then
  `abandon_workflow_run_impl`. Returns the failed step and reason, and logs them, because
  dismissal removes the window's record of why the run failed. Notifies the window with
  `runs_changed` (M2).

Send [turn]:

- `send(project_id, recipients: [agent_id], body: Body, on_busy, idempotency_key?) ->
  SendReceipt`, where `Body` is plain text, or a saved prompt (`provider`, `name`, `args`)
  with optional appended text. The rendered prompt and the appended text are combined by one
  Rust helper extracted from `forward_prompt_impl` (`commands.rs:4658-4664`, the existing copy
  of the frontend's `combinePromptMessage`), used by both.
  1. **Claim.** Repeated recipients are `invalid_argument` first. With a key, insert-or-join
     the ledger entry for `(project_id, key)` under the ledger lock, storing a hash of the
     recipients, body, and busy policy. A concurrent or later repeat with the same hash waits
     for and returns the original receipt; one whose budget ends first returns
     `request_in_progress` with the send id and leaves the key claimed; a different hash is
     `invalid_argument`. Without a key, a fresh entry. The server mints the `send_id` here,
     always; a caller never supplies the id the journal groups by.
  2. **Run as its own task.** Everything below runs in a spawned task; the caller awaits it.
     Cancelling the tool call or disabling the server never interrupts a send part-way, so
     every recipient reaches a real outcome and a retry with the key gets the receipt. The
     task needs an owned handle to the app state (a clone of the `AppHandle` in production;
     whatever the test owns in tests); how `ops` receives it is the implementer's choice.
     Release builds abort on a panic (`panic = "abort"` in the root `Cargo.toml`), so there is
     no recovery path for a send task that panics: after the restart the ledger is empty and
     `wait_send` answers from the journal. The task's settle guard covers debug builds and
     tests only.
  3. `open_project_impl`, then the blocking window sync (M2). Validate every recipient is in
     the roster (`unknown_recipient`) and the directory exists (`directory_missing`). Render
     the prompt (`prompt_needs_sign_in` on `NeedsSignIn`) and check the final body's size
     (`prompt_too_large`). A recipient the window reported a subscription failure for is
     `rejected { desktop_unavailable }` while the others are sent (as M2 specifies). Any
     request that ends with **nothing dispatched** — an error here, a forward's
     `source_busy`, every recipient refused — **releases the key**, so the same request can
     be retried (the remote plan's §5.5 rule for request-level errors). Everything before the
     first dispatch runs under the wait budget's deadline; the dispatch loop itself is never
     cut short.
  4. Under `refuse`: ask every recipient `Dispatcher::accepts_now` (below). If any says no,
     the whole send is refused with `agent_busy` naming them, nothing dispatched, key
     released. Then dispatch in order with `OnBusy::FailFast`. If a recipient is refused
     anyway (it became busy between the check and its own admission), it is `rejected {
     agent_busy }`, every later recipient is `not_dispatched`, and earlier accepted turns keep
     running: the workflow partial-dispatch rule (`workflow.rs:324-331`, and its test
     `partial_fanout_contention_does_not_cancel_accepted_sibling`). If that leaves nothing
     dispatched, the send is an error carrying the first refused recipient's own reason (a
     busy refusal names the agents, as the up-front refusal does), so the caller and a
     concurrent retry get one answer, and a recipient the window cannot hear never reads as
     busy. A recipient the window cannot hear is rejected on its own and never stops the
     loop; only a refusal from the dispatcher does. The up-front check runs under the wait
     budget, and only an agent that answers "no" is busy: a deadline that passes first (it can
     pass before an idle agent is even asked) fails the send with a timeout naming no one.
  5. Under `queue`: dispatch each with `OnBusy::Enqueue`.
  6. Each dispatch passes the `message_id` `ops` minted, after registering it in the ledger,
     and `emit_user_message: true`. M2 adds the announcement at acceptance.
  7. Return `{ send_id, recipients: [{ agent_id, message_id?, status, code? }] }` with status
     `accepted | rejected | not_dispatched`.
- `forward(project_id, sources: [{ project_id, agent_id }], recipients: [agent_id], text?,
  prompt?, on_busy, idempotency_key?)` — `forward_message_impl` / `forward_prompt_impl`
  compose the body (they open the sources' projects and wait for a mid-turn source), inside
  the same task, after the claim. The compose runs under the wait budget's driver, so a
  kept-alive caller gets progress while a source finishes; on expiry the compose is dropped
  (the resolver's guard releases its hold) and the operation fails with `source_busy` naming
  the sources still running, telling the caller to `wait_agent` first; a server shutdown
  during the compose is `internal`, never `source_busy`. `Invalidated` (a source produced no forwardable text, or
  its turn failed) is `invalid_argument` with the resolver's reason. Then the `send` steps
  above with that body.
- `run_workflow(project_id, name, is_builtin, inputs, forward_sources?) -> run_id` —
  `open_project_impl` and the window sync, then forward fields resolved the way the Tauri
  wrapper resolves them today (`merge_workflow_forwards`, which moves from `lib.rs` into
  `ops` and returns `AppError` instead of `String`), then `invoke_workflow_impl`. Agent-typed
  inputs, single and list, take agent ids at this boundary; the invocation converts them to
  the names the workflow engine validates against (`crates/workflow/src/invocation.rs:44-61`)
  **inside its own snapshot** of the roster and workflow, so a rename and name reuse between
  two reads cannot run the wrong agent. Other inputs pass through. After binding, every
  recipient the run's steps resolve to (slots and literal names alike) is checked against the
  window's `ReadyReport`; one with a failed subscription refuses the run with
  `desktop_unavailable`. The same rule is enforced again at dispatch, in the run's per-turn
  preflight, because a step may name its agent through a template expression
  (`{{ worker | lower }}`) that only the interpreter resolves; such a step fails with a reason
  saying the window cannot hear that agent. `WorkflowRunRequiresDismissal` maps to
  `workflow_run_requires_dismissal`.

Cancel [read]:

- `cancel_send(project_id, send_id)` — `cancel_send_impl` with the ledger's recipients that
  are accepted or running, and, for a send still preparing or dispatching (a caller can hold
  its id through `request_in_progress`), the send's own cancel: preparation stops at once, the
  dispatch loop checks the cancel before each dispatch and after each admission (cancelling
  that message through the dispatcher), recipients not yet sent become `cancelled`, and the
  send settles keeping its key. `send_unknown` if the ledger does not hold it; a queued send
  does not survive a restart. A workflow's send is held too, so this reaches it, and its
  cancelled replies end the run; a send of a workflow the user started from the window is
  refused, in both forms, from the origin recorded when its step started.
- `cancel_agent(project_id, agent_id)`, `cancel_workflow_run(project_id, run_id)`.

Wait [read]:

- `wait_send(project_id, send_id, timeout_seconds)` — blocks until every recipient is terminal
  or the timeout passes; returns `{ done, recipients: [{ agent_id, status, text?, error? }] }`
  with status `accepted | running | completed | failed | cancelled | rejected |
  not_dispatched` from the ledger, or, for a send the ledger does not hold, the restart
  fallback, within the call's finishing allowance: read the journal and each recipient's own
  transcript (unlocked), then a failed or cancelled `Outcome` record → `failed` / `cancelled`; else an `AgentTurn` with that
  `send_id`, `send_correlation: DurableLink`, and a completed status → `completed` with its
  text; else a `Send` record → `started`; else `unknown`. Only a durable link counts, and only
  with a completed status, because the dispatcher writes links for failed turns too
  (`crates/core/src/journal.rs:96-99`) and positional correlation is a guess. A reply with
  `done: false` carries statuses only, never reply text, so a client that must call again
  every 50 seconds (Claude Desktop) pays a few lines per call. A fallback that cannot finish
  in the allowance answers `done: false` with no recipients, and the caller calls again.
- `wait_agent(project_id, agent_id, timeout_seconds)` — returns `idle` with the latest output
  once `Dispatcher::accepts_now` is true, or `running` at the timeout. Between checks it waits
  on the ledger's per-agent signal (a turn-boundary event on that agent's channel), never
  re-polling in a loop: while an agent shuts down both dispatcher queries answer instantly,
  so a polling loop never yields and its timeout never fires. It observes once more at the
  deadline, so a shutdown that finished during the wait reads as `idle`. The output is read
  within the finishing allowance; when it cannot be, the reply is `idle` with
  `output_unavailable: true`, telling the caller to call `read_agent_output`. The tool
  description says `idle` is an observation; another caller can occupy the agent before the
  next send, which then returns `agent_busy`.
- `wait_workflow(project_id, run_id, timeout_seconds)` — from the ledger's run entries:
  `running` with the current step, or the terminal status with the failed step and reason.
  For a run the ledger does not hold, `list_workflow_runs_impl` (`failed` or `interrupted`
  from a retained file) or `run_unknown`.
- `list_workflow_runs(project_id)`.

*Dispatcher changes.*

- `Dispatcher::send_message` takes `message_id: Option<MessageId>`; `None` keeps today's
  internal minting (the compose path). Rationale: the actor can emit a send's first event
  before the caller has the id back, so the caller choosing it is what lets the ledger
  register before dispatch, with no orphan map and no fallback matching.
- `send_message_impl` takes `on_busy` (today it always passes `OnBusy::Enqueue`,
  `commands.rs:3651`) and `emit_user_message`; the compose path passes today's values.
- `Dispatcher::accepts_now(agent_id) -> bool`, answered by the actor with the same rule it uses
  to admit an `OnBusy::FailFast` send (`lib.rs:2571-2580`): true with no actor, true when idle
  with an empty backlog, true when the running turn has reached its terminal and nothing is
  queued, false otherwise and for a closing agent. Rationale: `has_pending_work` answers true
  for the whole turn including its post-terminal drain (`lib.rs:2645-2646`), so an up-front
  check built on it would refuse sends the dispatcher would accept, such as an immediate
  follow-up after `wait_send` reports done.

*`SendLedger` and `OpsLedgerEmitter`.* Why the event stream: the dispatcher's completion
handle exists only on the fail-fast awaitable path, so a queued send has nothing to await, and
the handle is consumed by one caller. The per-agent event stream already carries everything
the window uses to show completion (`turn_start`, content, `turn_end`, `message_failed`,
`message_cancelled`) for every kind of send, queued or not. Reading it once, in process, gives
one source of truth. The decorator is the same shape as `WakeLockEmitter`
(`desktop/src-tauri/src/wake_lock.rs`): wrap the base emitter where `AppState.emitter` is built
in `lib.rs`, observe, forward unchanged.

- Entries: keyed by `send_id`, also findable by `(project_id, idempotency_key)` and by
  `message_id`: `{ project_id, created_at, request_hash?, recipients: [{ agent_id,
  message_id?, turn_id?, dispatch, status, text: TextCapture, error?, failure_kind? }] }`
  (`dispatch` is the dispatch-time outcome the receipt reports; `status` moves on with the
  events); and `run_id → { project_id, status, step, reason? }`. Bounded: the 500 most recent
  **settled** sends and terminal runs (a send with dispatch unfinished or a recipient still
  running is never pruned by count), and nothing older than 24 hours, settled or not (the
  backstop against a terminal event that never arrives). A send is not `done` until its
  dispatch phase has finished. Queued work is unbounded in memory, as in the dispatcher.
  Captured text is kept whole in memory, budgeted only on the way out.
- Correlation: `turn_start`, `message_failed`, and `message_cancelled` carry `message_id`;
  `turn_end` and content carry the `turn_id` that `turn_start` announced. Events are parsed
  into their typed forms (`NormalizedEvent`, `MessageFailureKind`, the progress payload), so a
  renamed field breaks the build rather than failing silently; an unknown run status is
  ignored and logged, an unknown turn outcome ends the turn as `failed` because a turn end is
  always terminal. Events for `message_id`s the ledger never registered (the window's compose
  sends) are ignored, except that each agent's newest `turn_start` is noted so a reader can
  tell whether the agent's latest turn is one the ledger holds. A workflow step's send is
  registered by the engine's dispatch provider before the step builds its message, and each
  recipient's `message_id` is minted just before it is offered (revision 42).
- Text: `TextCapture` in `crates/harness/src/forward.rs` is the one rule for what counts as an
  agent's answer (text blocks plus accepted findings reviews; no thinking, no tool output),
  and it observes `AdapterEvent`. The decorator sees `NormalizedEvent` as JSON. Give
  `TextCapture` a second observer over `NormalizedEvent` sharing the same arms, so the rule
  stays in one place.
- Signals: one change notification for sends and runs, and one per agent for the events that
  can change admission (`turn_start`, `turn_end`, `message_failed`, `message_cancelled`,
  `agent_idle`; used by `wait_agent`). Content chunks do not wake waiters: the answer cannot
  change between turn boundaries. `wait_*` re-checks on every change and on timeout.
- Workflow runs: the decorator also observes `workflow:<project_id>`, where
  `ChannelProgressSink` (`desktop/src-tauri/src/workflow_commands.rs`) emits, recording
  `Started`, each step, and `Terminal`. Needed because a completed or cancelled run's file is
  deleted at its end, so without the ledger a caller that looked away could never learn how
  it ended.

*Wait budget.* Every blocking operation takes `timeout_seconds` (default 50) and a flag saying
whether the caller can be kept alive, which the tool layer (M3) sets when the client sent a
progress token. Without one, the wait is capped at 50 seconds; with one, at 3,600 seconds, and
the operation exposes a progress hook the tool layer drives every 60 seconds. Rationale, from
M0: Claude Desktop sends no token and cancels at 60 seconds; Claude Code aborts a call silent
for 300 seconds, and `rmcp`'s own session keep-alive ends a session silent for 300 seconds, so
a wait must never go silent that long; Claude Code backgrounds a long call and delivers its
result, so long waits are the intended use there; Codex fails at its own 300-second limit
whatever the progress, and the caller then retries shorter. The limits key on the progress
token rather than the client's name, because Desktop's reported name embeds the user's server
name and a wrong guess would fail silently. Every blocking operation also takes a cancellation
signal, which the tool layer wires to the server's shutdown (M3). One driver applies all of
this to every blocking phase — the waits' observations, a forward's compose, a retry joining
an in-flight send — with the deadline fixed when the call starts and one progress schedule
for the whole call. The steps that finish a call after its deadline — a wait's final
observation, `wait_agent`'s output read, `wait_send`'s journal fallback, naming the sources a
forward waited on — share one finishing allowance, the deadline plus 5 s, so a 50-second call
ends by 55 seconds, inside Claude Desktop's 60. A progress tick missed between steps is
skipped, not replayed, and overlapping steps never claim the same tick. `send` has no
caller-facing `timeout_seconds`: its budget is the default plus the keep-alive flag.

*Other changes to existing code.*

- `create_agent_in_project_impl` and `attach_agent_in_project_impl` take `project_id`; the
  existing `create_agent_impl` and `attach_agent_impl` become thin wrappers resolving the

### M2 — Desktop window sync

**Goal.** The window shows what another client did, as if the user had done it: a project it
had not opened, an agent it did not create, a change it did not make, and every MCP message,
queued or running.

Outcomes:

- An MCP message to a busy agent appears in the window as queued, like the user's own queued
  messages, and the same cancel button cancels it. When its turn starts, the row becomes the
  running turn without a duplicate.
- An MCP send into a project the window has not opened appears live (user row and reply)
  without a reload, and never duplicates history the window was still loading.
- An agent created, renamed, or re-configured over MCP appears or updates in the sidebar and
  compose chips without a reload; a project created over MCP appears in the project list.
- A workflow started over MCP shows its progress and result in the window, even a short one.
- If the window cannot listen to an agent's events, MCP sends to that agent are refused rather
  than running invisibly.
- The user's selection never changes because of an MCP operation.
- An orchestrator's model or effort change and the user's own change to the other setting
  both survive: the window's selection editor sends only the setting the user changed.
  Changes to the same setting resolve as last write wins.
- The round trip works while the window is hidden, or this plan records what makes it work.

**Outline.** Why a round trip: the window learns about projects, agents, and messages only
through its own actions, and Tauri does not replay events, so a turn dispatched for a project
the window has not loaded is invisible until reload, and an agent created by MCP never
appears. The remote plan's §5.8 solves the first part for the phone; this is that round trip
widened to refresh and readiness, under names both callers share.

Backend, in `ops::desktop_sync`:

- `ensure_ready(state, project_id) -> Result<ReadyReport, AppError>` (the turn tier): emits
  `desktop_sync_project { request_id, project_id }`, awaits the matching
  `desktop_project_synced(request_id, result)` command for up to 10 seconds, then the report,
  the window's error, or `project_load_timeout`. A guard removes the pending request when the
  waiting future is dropped (a send cancelled mid-round-trip, or the deadline), and an
  acknowledgement for a request id no longer pending is ignored with a debug log.
  `ReadyReport` lists the agents the window is listening to; `ops::send` rejects every other
  recipient with `desktop_unavailable`, and a workflow whose steps reach one is refused,
  matching the window's existing refusal to dispatch into a fork whose subscription failed
  (revision 12). The sync runs just before dispatch, under the call's finishing allowance.
- `roster_changed(state, project_id)`, `projects_changed(state)`, and
  `runs_changed(state, project_id)` (the change tier): emit `desktop_roster_changed
  { project_id }`, `projects_changed`, and `desktop_runs_changed { project_id }`, no reply.
  Correctness does not depend on them: the blocking sync before the next turn registers any
  new agent anyway. `runs_changed` makes the window re-read the project's runs after a run was
  dismissed over MCP, so it stops showing the failed run as blocking.

Announced sends (dispatcher and frontend): every MCP send, under `refuse` or `queue`, is
announced when the dispatcher accepts it. The dispatcher gains a per-send flag, set only by
`ops`, that makes the actor emit `send_accepted { message_id, send_id, text, at }` on the
agent's channel as it admits the item, so it precedes that send's `turn_start`. Workflow sends
do not set it and are unchanged. When `SendOrigin` arrives (§4), the flag keys off the origin
instead. The window turns it into the same pending entry and
queued row it creates for its own sends, and registers the recipient with the completion
tracker as the compose bar registers its own, one recipient per announcement (revision 33);
`turn_start` flips it to running; `message_cancelled`
and `message_failed` resolve it as they resolve the window's own (matched by `message_id`, which
the window now holds); the start-time `user_message` finds the existing row instead of adding
one, by de-duplicating on `(send_id, agent)` as the remote plan's §5.8 specifies. The queued
row's cancel button already calls `cancelSend(send_id, [agent])`, which works for any send.
Like the window's own queued messages, a queued MCP message is not journaled and does not
survive an app restart. This is the remote plan's first follow-up (`send_accepted` at enqueue)
for MCP sends; §4.

Frontend (`desktop/src/lib/state/workspace.svelte.ts`):

- `desktop_sync_project`, without changing the selection:
  - not loaded: `ensureProjectLoaded`, joining the first hydration to the load chain as the
    remote plan's `loadProjectForRemote` describes (a second `hydrateProject` call returns
    `"skipped"` and would not wait);
  - loaded: re-fetch the roster; `registerAgent` + `addAgentToProjectRoster` for new agents;
    `replaceAgentRecord` for changed ones;
  - in **both** branches, acknowledge only when the load chain is empty, every agent's
    `registerAgent` has settled, and `subscribeProjectWorkflows` has resolved (it is
    started without being awaited today, `workspace.svelte.ts:985`); report the agents
    whose listener is registered;
  - acknowledge the error if the open or roster read failed. A failed hydration still
    acknowledges: nothing is in flight, so dispatch is safe.
- `desktop_roster_changed`: if the project is loaded, the same roster refresh, no
  acknowledgement; otherwise nothing (the roster is read at load).
- `projects_changed`: `loadWorkspace()` (`workspace.svelte.ts:479`) re-reads the project
  list. (`markRegistryMutated` only bumps a counter.)
- `send_accepted`: the announced-send handling above.
- Partial selection updates: today the window saves an agent's whole selection from its own
  copy of the record, so a model or effort change made over MCP a moment earlier is silently
  reverted by the user's next save of the other setting. The `set_agent_selection` command
  takes the model and effort as independent, optional changes (omitted means unchanged,
  `null` means reset, the `ops` convention) and applies them through
  `update_agent_selection_impl`, which merges under the registry lock; the selection editor
  sends only the setting the user changed.

### M3 — The server and Settings

**Goal.** An MCP server a user turns on in Settings, that only a holder of the token can
reach, exposing the M1 operations as tools.

Outcomes:

- The user enables agent access in Settings, sees the port, the token, and ready-to-paste
  configuration for each client, and can regenerate the token to cut every client off.
- A Claude Code session configured with that token can do everything M1 lists.
- A request without the token, or from a web page, is refused.
- Disabling stops the listener at once, even with clients holding open connections; an
  in-flight wait ends; agent turns and in-progress sends keep running. Re-enabling on the same
  port works immediately.
- A port already in use is shown as an error in Settings, not a startup failure.

**Outline.** `desktop/src-tauri/src/mcp/`.

- Listener: an `axum` router bound to `127.0.0.1:<port>` with the `rmcp`
  `StreamableHttpService` nested at `/mcp`, started when the preference is enabled (at launch
  or from Settings). The tool handler holds a `tauri::AppHandle` and reaches `AppState`
  through it per request. Debug builds default to a different port than release, so a dev
  instance and the installed app can both listen.
- Host and origin checks are `rmcp`'s, configured: `with_allowed_hosts(["127.0.0.1:<port>",
  "localhost:<port>"])` (its default list allows any port) and
  `with_allowed_origins(["http://127.0.0.1:<port>", "http://localhost:<port>"])` (its default
  disables origin checks). Requests without `Origin` pass, which is what MCP clients send;
  browsers always send one. This is the DNS-rebinding defence the specification requires.
- Bearer check: the only middleware of ours, in front of the service (the pattern in
  `crates/prompts/tests/oauth_client.rs`): `Authorization: Bearer <token>` compared in
  constant time; missing or wrong → `401`.
- Disable: cancel the config's `cancellation_token`, which ends every session and open stream,
  then shut `axum` down. Rationale: `axum`'s graceful shutdown waits for open connections,
  and an MCP session can hold an event stream open indefinitely (`rmcp` keeps it alive every
  15 s), so shutting `axum` down alone can hang and leave the port bound. Every blocking tool
  also races the same shutdown token through the M1 cancellation signal, because M0 found that
  `rmcp` does not cancel a tool call when its client goes away, so ending a session cannot be
  relied on to end the call. Sends continue because they run as their own task (M1).
- Session keep-alive: keep `rmcp`'s 300-second default. Clients whose idle session expired
  reconnect and re-send on their own (M0), and the wait rules (M1) keep any call from going
  silent that long. `rmcp` 1.7 answers Claude Code's `server/discover` with 422 and Claude
  Code falls back to `initialize`; recheck when `rmcp` is upgraded.
- Token: 32 random bytes, base64url, generated when agent access is first enabled, stored in
  the app's secret store (Keychain in release, the file store in debug) under one key, and
  regenerated from Settings. Settings shows it with a copy button. Clients keep their own copy
  in their configuration.
- Tools: one `#[tool]` per M1 operation, same names, parameters as JSON schema through
  `Parameters<T>`. The agent-facing guidance is one set, for every client (§0):
  - The server `instructions` describe the orchestration loop in a paragraph: list, send,
    wait, read, forward.
  - Each tool's description states its own rules: the id discipline; the `on_busy` choice and
    the stop-at-first-refusal rule; `idempotency_key`; the "call `wait_*` again until `done`"
    loop; that `idle` is an observation; that queued messages are visible on the desktop; and
    the result budget: any result may cut long text, with a link that reads on when one is
    given, and only `read_send_output` pages a reply in full; `read_conversation` returns
    whole items newest-first and says how many older ones it left out.
  - Every tool declares `_meta["anthropic/maxResultSizeChars"]` of 100,000, so Claude Code
    shows a result up to the budget directly instead of saving it to a file.
  - The `wait_*` descriptions carry the per-client hints: in Claude Code, ask for a long
    timeout (the call moves to the background and its result arrives on its own); in Codex,
    stay under 300 seconds unless the user raised `tool_timeout_sec`; otherwise use the
    default. The server enforces the limits in M1's wait budget, so ignoring a hint degrades
    to more calls, never to a failure the caller cannot recover from.
  - Blocking tools pass "can be kept alive" to `ops` when the client supplied a progress
    token, and send a progress notification every 60 seconds through
    `RequestContext::peer.notify_progress`.
- Configuration: `config.yaml` gains `agent_access: { enabled: false, port: <default> }` with
  `#[serde(default)]`, following `auto_reading_mode` including the "an old file loads with it
  off" test (revision 14 explains the name). Nothing is written into a working directory.
- Settings (`desktop/src/lib/components/SettingsView.svelte`, a new section beside the MCP
  providers section): a `Switch`, the port, status (listening on …, or the bind error), the
  token with copy and regenerate, and the three client snippets (M4). Tauri commands:
  `mcp_status`, `mcp_set_enabled`, `mcp_set_port`, `mcp_regenerate_token`.
- Dependencies: `rmcp` and `axum` become regular dependencies of the app crate through `cargo
  add`, keeping the versions the lockfile pins; the `rmcp` `client` feature joins the app
  crate's dev-dependencies for the end-to-end test.

**Done when:**

- Fixture-driven test, in process: start the server on an ephemeral port against a

  create_agent → send → wait_send` end to end. Also: a wrong token is `401`; a foreign

### M5 — Usage limits and context fullness

**Goal.** An orchestrator can see how much of each account's limits is left and how full each
agent's context is, so it can choose a model and effort for the work and the quota at hand,
and compact an agent at the right time (M6). Reads only; no window change.

Outcomes:

- `get_usage` returns, for each harness account the app has a reading for, every limit window
  with the share used, when it resets, and when the reading was taken. Codex's is fetched
  fresh on request when it can be.
- `list_agents` reports each agent's context: tokens in use, the window size, and the
  fraction, from the agent's newest finished turn with a usage record or a newer compaction,
  the same rule as the sidebar's context bar.
- Both answer without the window and at a read's cost: no project is opened, an agent's
  session file is read at most once per app run beyond the reads the app already makes, and

### M6 — Compaction

**Goal.** An orchestrator compacts an agent whose context is filling, sees the compaction
finish, and the window shows it exactly as a compaction started with its own Compact button.

Outcomes:

- `compact_agent(project_id, agent_id, idempotency_key)` queues a compaction for a Claude or
  Codex agent, behind whatever the agent is doing, and returns a `send_id` that `wait_send`
  and `cancel_send` understand.
- The window shows the compaction row, queued then running, with its cancel button, and
  fetches the recap marker when it finishes.
- Refusals carry codes: `compaction_unsupported` (Antigravity, whose `/compact` is answered by
  the model with a claim of success while nothing is compacted; harness-behavior §3.9),
  `no_session` (the agent has not replied yet, so there is nothing to summarize), and
  `fork_not_materialized` (a Claude fork before its first message: a compaction must not be
  the turn that performs the fork).

**Outline.**

- `ops::compact`, in order: `open_project_impl`; the three gates above, which need only the
  agent record and the project folder, so an unsupported harness or a missing session is
  refused at once rather than after a wait for the window; the window readiness round trip,
  because a compaction is a turn; then `compact_agent_impl`. Not gated on idle: it queues
  behind running and queued work, as the Compact button's does.
- Ledger. The compaction is registered as a one-recipient entry before dispatch, so
  `wait_send` reports `completed`, `failed`, or `cancelled`, `cancel_send` cancels a queued
  one, and the ledger's per-agent wake-ups cover it. `Dispatcher::compact_agent_with` beside
  `compact_agent`, the `send_message_with` pattern, so the ledger's `message_id` is the one the
  actor emits, and the announcement below is sent. A compaction emits no reply text, so the
  recipient's `text` is empty. After an app restart it reports `unknown`: nothing journals a
  compaction, because the journal is the user's side of the conversation, and that stays.
- Window. Today the window knows a turn is a compaction only from an entry it created itself
  when its own Compact button was pressed (`dispatchCompaction` in `index.svelte.ts`); a turn it did
  not start "is never a compaction", so an orchestrator's would render as an ordinary reply,
  and the recap marker would not be fetched until the project reloads. The fix is in the
  announcement: `send_accepted` gains `kind`, `"compaction"` for this and absent for a message
  (additive on the wire, `#[serde(default)]`, a TS optional), and `admitAnnouncedSend`
  registers a pending entry of that kind with no user row, the same entry the Compact button
  creates. From there the existing paths apply: `turn_start` resolves the entry as a
  compaction (its own row, no user message), the terminal hook receives `kind: "compaction"`
  and re-reads the project for the recap marker, and a queued one that is cancelled disappears
  (decision 8 in `reducers.ts`). `turn_start` itself is unchanged.
- Idempotency: `idempotency_key`, as for `send`. And one rule against pile-up, because a
  compaction always queues and §5 promises that a looping client cannot pile up queued turns:
  when the agent's newest unfinished ledger entry, by the time it was admitted to the agent's
  queue, is a compaction not asked to cancel, the call returns that entry's receipt instead
  of queuing another, whatever its key, and the ledger associates the new key with the
  reused receipt. Admission time, not registration time: an entry is registered at its
  claim, before preparation (prompt rendering, the window round trip), so a message
  registered first can be admitted after a compaction registered later; the ledger records
  the admission when it marks the recipient accepted at dispatch, and orders by that. A
  request that merges into a compaction still preparing, which has no receipt yet, joins its
  claim as a same-key repeat does, and receives what the first caller receives: the receipt,
  or the error that released the key. Checked and decided under the ledger lock, so two
  calls arriving at once queue one. If an orchestrator's message was admitted behind that
  compaction, a new one queues after the message, as promised and as the window's own rule
  works (`compactionAvailability.ts`, which checks the newest queued action). The check
  stays in the ledger rather than the dispatcher's queue: only the dispatcher knows the full
  order, but a dispatcher check would turn an enqueue into an awaited round trip to the
  agent's actor and, for a compaction the window queued, would find no receipt to return.
  Known limit, recorded rather than solved: the ledger holds only what orchestrators and
  workflows queued, so work queued from the window's compose bar is not seen. A compaction queued from the window's Compact
  button can get an orchestrator's behind it, and a window message queued behind an
  orchestrator's compaction lets a second request merge into the first, which then runs
  before the message; the orchestrator sees that from `context` afterwards and compacts
  again. Nothing is lost or duplicated either way. Rare, involves the user directly, and the
  window guards its own side.
- Live tests `live_claude_mcp_compact` and `live_codex_mcp_compact`, driving the server from
  the in-process `rmcp` client the offline tests use, with real Switchboard agents (the
  harness crate's live tests already cover each harness's compaction; what is new is the path
  from real session files into M5's figure and `read_conversation`'s marker, and a real
  orchestrating client would only re-test tool calling, which M4 covers): a two-message
  conversation of one-word replies, `compact_agent`, `wait_send` completes,
  `read_conversation` shows the compaction marker, and `list_agents` reports the marker's
  figure (not "smaller than before": a summary can outweigh two one-word exchanges).
- README gains a line under Agent access; the tool description tells the orchestrator to
  read `context` from `list_agents` to decide when, and that the compaction waits behind the
  agent's current work.

**Done when:**

- Fixture-driven through the server: compact a mock-harness agent and `wait_send` reaches
  `completed`; on a busy agent the compaction queues and runs after the reply; `cancel_send`
  cancels a queued one and `wait_send` says `cancelled`; an Antigravity agent gets
  `compaction_unsupported` and an agent without a session `no_session`, both without a

- Window, component-level: a `send_accepted` with `kind: "compaction"` produces the

### M7 — Fork

**Goal.** An orchestrator branches an agent's conversation to ask a side question or go down
a rabbit hole, without disturbing the original, and the window shows the branch as it shows
its own forks.

Outcomes:

- `fork_agent(project_id, agent_id, text | prompt, idempotency_key)` creates `<name>-fork`
  (`-fork-2` and so on when taken; `crates/core` names it) holding the source's conversation
  so far, sends it the message, and returns the fork's record and a `send_id` for
  `wait_send`.
- The window shows the fork in its own pane with its earlier conversation, whether the window
  is open or opened later, without changing what the user is looking at.
- The source is untouched. A fork of a busy source is refused (`source_busy`), a source that
  has not replied yet (`no_session`: there is no conversation to branch), and a harness that
  cannot fork (`fork_unsupported`).

**Outline.**

- Always with a message. A Claude branch exists only through its first turn (Claude has no
  copy-a-session operation; the branch is made by that turn's `--fork-session`), so Claude
  needs one anyway; one rule for both harnesses is simpler than two; and the orchestrator's
  uses start with a message. The Codex-only fork without a message (the agent card's) is not
  offered.
- `ops::fork`, in order: claim the `idempotency_key`; `open_project_impl` (`fork_agent_impl`
  needs the project open in the backend); `fork_agent_impl` (which refuses a busy source up
  front and, for Codex, runs `codex exec fork` while holding the parent's session lock;
  `codex` is resolved on the login-shell PATH as the window's call resolves it); the window
  readiness round trip, carrying the fork (below); then the message through `ops::send`'s own
  path, whose dispatch already handles a Claude fork's first turn (the dispatch context copies
  the parent's session when the record carries `forked_from_session`, and `busy_fork_source`
  re-checks the parent at dispatch). The whole operation runs as one task, as a send does, so
  a client that hangs up mid-call cannot stop it between creation and send; the task listens
  to the server's stop signal as a send's does (a child of the call's cancel token), so turning
  access off after the fork exists leaves it with nothing sent rather than starting a turn.
- One retry lifecycle, because the ledger's claim today resolves to a send receipt and
  releases the key whenever nothing was dispatched, which can neither keep a created fork nor
  stop a retry from making a second one. The claim resolves to a typed receipt holding the
  fork and the send's outcome. The key is released only while no fork exists. Once it does, a
  repeat with the same key and request: re-runs only the send part if it never dispatched (a
  refusal before dispatch, the window's deadline), under the same claim, and updates the
  receipt; returns the receipt if the send dispatched; and never resends a message cancelled
  while preparing, which settles as cancelled and keeps its key, as a send's does. Concurrent
  repeats join one attempt. A different key makes a second fork. Two of the ledger's claim
  rules change for a fork-carrying claim, and only for it: `claim` gains a resume outcome
  beside `Fresh` and `Joined` (when the claim holds a fork whose send never dispatched, the
  first repeat takes the send over and resets the result slot, and later repeats join that
  attempt), and a failed preparation keeps the entry and the key instead of calling
  `release`, which today deletes both, including on the error path a server stop takes. The
  failed preparation is recorded in the receipt as a rejected send with its error, so a
  `wait_send` on it returns at once, and the repeat mints a fresh `send_id` for the resent
  message and returns it in the updated receipt, as a plain send's retry does: the ledger
  never reopens a finished entry, and an unfinished one would make waits hang. On that
  resume the key moves from the rejected entry to the new one: the ledger's cleanup drops a
  key together with the entry carrying it, and the rejected attempt, finished and older, is
  dropped first, which would otherwise let a later same-key retry make a second fork. A
  repeat that joined before the resume joins the new attempt and gets its result: it is the
  same request under the same key, so no earlier result is preserved for it. The tool
  description gives the same-key rule for recoverable preparation failures: retry after
  fixing the cause. Cancellation returns the cancelled receipt, and a failed admitted turn
  is observed through `wait_send`, never automatically rerun by `fork_agent`. Reuse the
  send's internal dispatch code without calling public `ops::send` to claim the key a second
  time, and perform only the one fork-carrying readiness round trip.
- Window. A Codex fork is an ordinary record (its session already holds the conversation, and
  the record carries no provenance), so from a roster refresh the window cannot tell it from a
  new agent; it would register it, leave it unplaced or, in a project with no saved layout,
  drop it into the one pane beside its parent (showing every inherited message twice), and
  show its earlier conversation only after a project reload. A Claude fork carries
  `forked_from_session`, and the existing hooks load its history after its first reply
  (`installForkHistoryRefresh`) and arm the "history is coming" cue on open
  (`seedPendingForkHistory`). So the readiness request the send already makes carries the
  fork: `ensure_ready(project_id, fork: Option<{ fork_id, source_agent_id }>)`, ids only, the
  `desktop_sync_project` payload and the waiting-request fetch gaining the same optional
  field, and no second request pair, since the readiness request already has the deadline,
  the replay of requests that arrived before the listener, and the duplicate-answer guard.
  In `syncProjectForTurn`, after `ensureProjectLoaded` and `refreshProjectRoster` (so the full
  roster is present and the pane layout is reconciled against it, never against the fork
  alone), a carried fork runs what the window's own Fork runs after creation
  (`registerForkInOwnPane` without the create), on the fork's current record found by id in
  the roster it just refreshed, never a creation-time record, so a retry cannot revert a
  rename made between attempts, and a fork removed between attempts is not restored (the
  handler then places nothing and answers): register, add to the roster, place in a visible
  empty pane or a new one. Not revealed: `revealPane` would make the fork's pane the
  maximized one in focus mode, and its justification ("an explicit action with an immediate
  result") is the user's own Fork, not an orchestrator's; M2's rule for background work is
  that it never changes what the user is looking at, so a new pane may start minimized.
  Placement is idempotent by fork identity, because a retry carries the fork again and the
  handler of a timed-out request keeps running in the window: it is skipped only when the
  fork already sits in a pane without its source (a plain roster refresh can have dropped it
  beside its parent, which today's code fixes by making a new pane, and "already in a pane"
  would wrongly skip that case); a per-session set would not survive a window reload. The
  check runs immediately before the move, with no `await` between them: two handlers can be
  at this point at once, and the reused sequence awaits `registerAgent` before placing, so a
  check made before that wait would let both pass and each make a pane. Then
  for Codex: mark it an eager fork and queue its history read only if the fork has nothing
  running or queued, else leave it to the existing idle hook, because the read must not
  overlap its first reply (the reread rule from #127: a reply caught half-written shows
  twice); for Claude: arm the cue. The readiness answer then waits for the queued read as it
  waits for every queued history read (`settleProjectLoads`), so the send starts after it.
  That read rereads the whole project, so a large project can miss the 10-second deadline:
  the call then fails with `project_load_timeout` and the retry (above) succeeds once the read
  has finished, the shape a slow first load has today. M7 measures the reread on the largest
  local project and records it; if it exceeds the deadline, a fork's readiness request gets a
  longer one, beside `SYNC_DEADLINE`, still inside the call's budget. If the window fails or
  times out, the fork exists and the tool reports it with the send's error; no fallback
  announcement is sent (the roster-refresh placement above is the bug placement exists to
  prevent), and the retry places it. The fork shows after any later roster refresh in any
  case, and a Codex fork's history after a project reload.
- Pane placement for other agents an orchestrator creates (`create_agent` leaves them in no
  pane when the project has a stored layout) is unchanged here; noted for the owner.
- Live tests `live_claude_mcp_fork` and `live_codex_mcp_fork`, driving the server from the
  in-process client with real Switchboard agents, as M6's do: a two-message source of
  one-word replies, `fork_agent` with "reply with the single word ack", `wait_send` completes,
  `read_conversation` for the fork shows the inherited messages and the reply, and the
  source's conversation is unchanged. The Codex one runs the real `codex exec fork`.
- README gains a line under Agent access, with the pile-up: forks stay until the user removes

## 4. Relationship to the remote-control plan

Both plans need the same layer above `*_impl`. Building them independently and merging is the
agreed approach; this section is what the merge touches.

| Piece | This plan | Remote plan | At merge |
|---|---|---|---|
| Shared operations | `ops` in the app crate, called by MCP tools | `RemoteBackend` trait in `crates/remote`, implemented over `AppState` | The `RemoteBackend` implementation calls `ops`; `ops::send` is its `send_message` loop and recipient validation (remote §5.5). |
| Send ledger | `SendLedger`: event-fed, outcomes and text, keyed by server `send_id` and `(project_id, idempotency_key)` | `SendLedger`: accepted/rejected results keyed by the phone's `send_id` | One ledger, this one. The phone's device-minted `send_id` becomes its `idempotency_key`; whether the phone also keeps it as the journal `send_id` is the open item in §0.1. |
| Partial fan-out | Stop at first refusal, per-recipient results | Per-recipient results, partial rejection tested | Same contract. |
| Window sync | `desktop_sync_project` / `desktop_project_synced` (load or refresh, readiness; from M7 it can carry a fork to place), plus `desktop_roster_changed`, `projects_changed` | `remote_load_project` / `remote_project_loaded`, load only | One set of names, this behaviour. |
| Queued sends visible | `send_accepted` for MCP sends, emitted as the actor admits each to the agent's queue, which is when it is enqueued | First follow-up: `send_accepted` at enqueue | One event, already emitted at enqueue (revision 48); the phone's sends use it too. |
| Live user row | `emit_user_message: true` on MCP sends, de-duplicated by `(send_id, agent)` | `SendOrigin` on every send, always emitted, same de-duplication | `SendOrigin` replaces the flag; MCP sends carry `Mcp`. Add `Mcp` to the enum when it is introduced: the value is journaled, and an older build cannot read a value it does not know. |
| Conversation paging | `read_conversation` tail with `last_n_items` | `TranscriptWindow` with cursors and a byte budget | `read_conversation` takes the cursor form. |

Likely conflict sites: `commands.rs` (send path, `create_agent_impl`), `crates/dispatcher`
(`send_message`'s signature, the actor's admission arm), `workspace.svelte.ts` (the load

## 5. Security

**What's at stake** is the remote plan's §2 sentence, unchanged: a send runs with permission
prompts disabled, so whoever can call `send` can run anything on the Mac. The server is local
and off by default; its security work is making sure only a process the user configured can
call it.

| Threat | Defended? | By |
|---|---|---|
| A web page in the user's browser reaches the server (DNS rebinding, cross-site request) | Yes | `rmcp`'s `Host` and `Origin` checks; a bearer token the page does not have; bound to `127.0.0.1` |
| Another user on the machine | Only while the app holds the port | Bearer token, held in the app's Keychain entry and in each client's configuration: `~/.claude.json` and `claude_desktop_config.json`, both private to the user, and for Codex an environment variable the setup tells the user to keep in an owner-only file (revision 19). While the app is quit or access is off, another account can listen on the port and collect the token from the next client that starts, since a client cannot check who answers (revision 16). Holds fully on a single-user Mac |
| Another process running as the user | No | Out of scope; such a process can already run the harness CLIs itself |
| The token committed to a repository | Yes, by setup | Settings and README give only private-scope configuration; never `.mcp.json` |
| A client's model loops and burns quota | Partly | The Settings toggle stops the listener at once; `refuse` by default means a loop cannot pile up queued turns; rate limiting is a follow-up |
| Agents Switchboard launches get the tools | Partly | The folder rule (M4); `refuse` makes a self-send fail |
| `mcp-remote` (third-party, run through `npx`) sees the token | Accepted | It runs as the user, like any client; the in-repo bridge is the alternative if this is not acceptable |

**Disclosure.** README's **Agent access** section opens with: *"An agent connected over MCP
has the same reach as the keyboard. Agents run without approval prompts, so any program holding
the token can run commands on your Mac. It is off by default; regenerate the token in Settings
→ Agent access to revoke every client."*

**Review boundary.** The bearer middleware, the `rmcp` `Host`/`Origin`/cancellation
configuration, token generation and storage, and the tool layer's input validation:
`/security-review` in M3.

## 7. Where agent access differs from the window

An orchestrator acts for the user but cannot see the window, so some of its actions are
deliberately narrower than the user's own. This is the record of every difference and why.
Before adding or changing a tool, compare it with the window's action and add a row here. The
"the orchestrator's actions against the window's" tests in `desktop/src-tauri/src/ops/tests.rs`
run each matching action both ways and check they end the same.

| Action                                | In the window                                                                         | Through the agent tools                                                                                                                                      | Why                                                                                                                           |
| ------------------------------------- | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| Message an agent that is busy         | Queues behind the running reply                                                       | Refused by default; `on_busy: queue` queues                                                                                                                  | The orchestrator cannot see the pane, so stacking work is opt-in                                                               |
| Forward from an agent still replying  | Waits as long as it takes; the cancel stops the whole forward                         | Waits up to the call's time limit, then fails with nothing sent; cancelling its last remaining recipient stops the whole forward, as the window's cancel does | A tool call cannot wait without limit: clients end long calls                                                                  |
| Cancel one agent's reply              | The stop control on a reply cancels that agent's reply to that message               | Same (`cancel_send` with `agent_id`), but refused for a message the user typed or a workflow the user started                                                | The orchestrator stops only what it started                                                                                    |
| Cancel a whole message | The compose bar's stop cancels every running and queued message in one click | `cancel_send` cancels one send per call, and only one made through the tools or by a workflow started through them; cancelling a workflow's send ends its run, as stopping one of its replies in the window does | The orchestrator stops only what it started, one message at a time |
| Stop an agent entirely                | Stop agent: cancels its reply and drops everything queued                             | Same (`stop_agent`), reserved by the prompt and its description for when the user asks                                                                     | It would drop the user's queued messages; who queued each is known only to the agent's actor, so this is held in text, not code |
| Remove an agent                       | Cancels whatever it is doing, then removes it                                         | Refused while the agent has work running or queued, or while a workflow runs in the project; workflows cannot start in the project meanwhile                 | It cannot see what it would destroy, and removal is permanent                                                                  |
| Cancel a workflow run                 | Any run                                                                               | Only a run started through the tools                                                                                                                         | Same as cancelling a reply                                                                                                    |
| Compact an agent                      | Queues behind the agent's work                                                        | Same                                                                                                                                                         | —                                                                                                                             |
| Fork an agent | Refused while the source is busy; a Codex agent can also be forked from its card without sending anything | Refused while the source is busy; the fork always carries a message | A Claude fork exists only once its first turn runs, and the orchestrator forks to ask something, so it always has a message |
| Forward an earlier reply | Forwards each source's latest answer, waiting for a turn in flight | Same by default; a source may name a `send_id` to forward that reply instead, without waiting, refused if it is unfinished or did not complete | An orchestrator moves on between steps, so the answer it wants (a reviewer's first round, a report since followed by other work) is often no longer the latest |
| Read a workflow run's replies | Each reply shows under its step in the transcript | `read_workflow_run` returns them all at once, in step order | The orchestrator cannot scroll the transcript, and an agent's latest answer holds only its last step |
| See account usage | The usage meter is always on screen and refreshes after each Codex turn | `get_usage` on request, which reads a Codex account; a finished wait carries the last stored reading, compacted, without reading one | An orchestrator decides at the end of each step, and a read per wait would cost up to half a minute and repeat on every poll |
| Notice an agent that has gone quiet   | "No response" after 60 seconds of silence; the user decides                           | The same silence count, and the prompt's rule to act after 20 minutes with no tool call open                                                                 | It acts unattended, so its threshold is conservative                                                                           |
| List projects | The project list shows active projects; archived ones are on their own tab | Same: `list_projects` leaves archived projects out unless `include_archived` is true; an archived project's id still works everywhere | — |
| Read a saved prompt | The prompt preview shows a built-in or local prompt's template, or a prompt server's description and arguments; the composer previews a rendering | Same: `read_prompt` returns the template, or for a prompt server a note that the server keeps it, and with `args` the rendering a send would deliver | — |

Changes made for agent access that also apply to the window: a removed agent can never be
started again (its dispatcher slot is marked removed), the window drops an agent another client
removed and shows a removal that deleted the agent but failed to save as a banner, and a
workflow start is refused for a moment while an agent is being removed from the project or
when an agent was deleted since the start read its roster.
