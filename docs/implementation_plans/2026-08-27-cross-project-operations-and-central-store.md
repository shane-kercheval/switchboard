# Cross-project operations and the central project store

> Revised 2026-08-27 across two reviewer rounds. Round-1 changes from the first draft: directory records moved into the fail-loud store catalog (was: workspace.yaml) with a startup legacy preflight; attachments became store-wide with preserved dispatched paths (was: per-project, rewritten on move); the session lock became fail-closed (was: fail-open); the forward picker's menu became read-only (was: lazy-open on expand); `ForwardSource` carries project identity; M4 gained a two-project quiescence gate and pin semantics.
>
> Round-5 (2026-08-27, post-M0): M0 ran — store-wide attachments are viable on all testable harnesses and Antigravity needs no `--add-dir`, so the cwd-local fallback and `.git/info/exclude` path are dead and removed from scope. **M0.5 added: remove Gemini support entirely**, before M1, because the CLI is auth-dead for individual accounts and cannot be tested live or manually. Per-harness reasoning throughout was narrowed from four harnesses to three — note that M4's same-directory-only constraint now rests on Claude alone, and the decision was re-justified rather than assumed to survive.
>
> Round-4 changes (targeted corrections): the fork-parent lock key derives from the record's own `forked_from_session`, **not** from `busy_fork_source` — that function returns the parent only when it is *busy*, so keying off it would have locked the parent only when the turn was already being refused; M4's maintenance flag is checked at `DispatchContextFactory::preflight` too (round 3 wrongly excluded it, reopening the check/enqueue race that preflight documents itself as closing); flags now clear only on successful completion or recovery; the §3.5 citation was corrected to the mid-turn-fork finding (that probe found the parent file is *not* corrupted — the earlier "torn copy / truncated history" phrasing conflated it with a separate probe and contradicted the doc); one stale DoD line updated from "dismissal" to per-source skip.
>
> Round-3 changes (all refinements, no reversals): M4's intent record covers in-app failures as well as crashes, with a process-wide move mutex, per-move intent files under `moves/`, and recovery-failure blocking exactly the two affected projects; the migration marker became **per legacy source** rather than global (a global one breaks in both directions once the tool skips unavailable directories) and the global notice dismissal was replaced with a per-source skip so write-suppression can't be lifted while migration input is still needed; the session lock also acquires a materializing fork's **parent** key; store-wide GC runs once per session plus on project delete; the forward wire type requires `project_id` with the frontend upgrading old drafts; `DispatchContextFactory::preflight` is named to distinguish it from the workflow-side `preflight`.
>
> Round-2 changes, all corrections to round-1 material: **M4 gained a durable move-intent record with idempotent steps** — round 1's "re-running the move heals" was demonstrably unsound and is explicitly retracted; forward sources became a wire-level `{agent_id, project_id}` reference (round 1 said "open the source project" without saying how the backend could know which one); the session-lock handoff became an RAII permit returned from `preflight()` (round 1's shape was impossible — `build()` runs before `preflight()`); store-wide attachment GC stays caller-driven and fail-closed on read errors (a backend startup sweep would have deleted every unsent draft's attachments on each launch); the legacy-migration notice keys on positive evidence plus a completion marker with a persisted dismissal (round 1's condition could wedge the app for a user with directories but no projects); M4 pin **pruning was removed** as unsafe; one function name corrected.

> Round-6 (2026-08-29, during M2.3): **store-wide attachments reversed — staging stays per-project.** The store-wide design's only beneficiary was M4's agent move; its cost was turning project delete from `remove_dir_all` into an all-projects reference sweep, moving the blast radius of a GC bug from one project to every project, in the operation whose failure mode is deleting data the user still wants. M4 accepts a documented limitation instead (a moved agent's old attachment files are collected from the source; recorded paths are untouched, so correlation is unaffected). The copy-on-move mitigation is recorded but deliberately not built. M0's probe is not invalidated — it established that store-wide *would* work, not that it was needed.

**M0 is complete** (attachment probe — result in its section below). **M0.5 removes Gemini support** and lands before the rest, shrinking every later milestone's per-harness surface. Switchboard supports three harnesses from M0.5 onward: Claude Code, Codex, Antigravity.

Four related capabilities, in dependency order:

1. **Cross-project forwarding** — forward another project's agent's latest output into the current project's compose (M1).
2. **Central project store** — move all Switchboard-owned per-project state out of `<directory>/.switchboard/` into the user-global config dir (M2).
3. **Duplicate setup** — copy an agent's or a whole project's *configuration* (fresh sessions, no history) into another/new project (M3).
4. **Move agent** — relocate an agent, with its history, between projects that share a working directory (M4).

M0 is a decision-gate probe that must run before M2 is designed in code.

**The whole plan ships as one PR**; each milestone is a commit (sub-steps within a milestone may be their own commits). Do not open per-milestone PRs. After finishing a milestone, stop, summarize, and wait for review before starting the next — but the branch stays open throughout.

## Decisions settled in discussion and review (do not re-litigate; do not silently deviate)

These cannot be recovered from the codebase — they are the discussion's and review's output:

- **The store moves to the user-global config dir**, under the existing `config_dir()` resolution (`crates/app/src/lib.rs`). No new root, no new env var: release → `~/Library/Application Support/switchboard/`, debug → `switchboard-dev[-<port>]` via the existing `SWITCHBOARD_CONFIG_DIR` / `make dev` machinery. The dev/release separation requirement is satisfied entirely by inheritance.
- **The original rationale for directory-local state is gone.** The M1-era plan intended directory-level `config.yaml`/`workflows/`/`prompts/` to be git-tracked; workflows and prompts have since moved user-global, and everything remaining under `.switchboard/` is gitignore-required runtime data. Record this rationale in the new store type's module doc — it is the answer to "why did this move?"
- **Load-bearing mappings never live in reset-to-empty state.** The `directory_id → path` records that resolve every agent's cwd are part of the fail-loud, versioned store catalog — *not* `workspace.yaml`, whose documented corrupt-file behavior is "reset to empty and allow overwrite." `workspace.yaml` keeps only replaceable view-state (hidden directories, archived projects, ordering). Mixing the two is what would let one bad parse strand every project and destroy the only copy of the mappings.
- **Migration is a standalone tool, not an in-app compatibility path.** A checked-in Rust binary reusing `switchboard_core`'s parsers (never a shell/Python reimplementation of the JSONL/YAML round-trip). Behavior is **copy → validate → optional cleanup**: originals are untouched until an explicit `--cleanup` after successful validation. The app's legacy awareness is the startup preflight plus the add-directory check (M2.4) — no code path reads the old layout as a store.
- **Migrate into the release root only.** The dev store starts empty and is treated as scratch. This removes the common route to the cross-build same-session hazard; the session lock (M2.3) covers the rest.
- **A shared, non-isolated, fail-closed session lock replaces the cross-build protection the move deletes.** Today the directory-local `instance.lock` incidentally prevents a dev build and the installed app from driving the same project (both resolve the same file). Central per-build stores are disjoint, so that protection vanishes. The replacement locks the thing actually at risk — the *harness session* — at a fixed path that ignores dev isolation. It is required, not optional (see `same-session-parallel-invocation.md`), and therefore **fails closed**: a lock that cannot be acquired — contention *or* I/O failure — refuses the turn. A protection against session-file corruption that degrades to a warning is not a protection.
- **Directory identity becomes a stable id.** The store catalog maps `directory_id → path`; projects reference the id. Re-pointing a moved repo becomes a one-field update (already a planned affordance per system-design §3). The canonical path remains a secondary lookup key — `state.directories` and `Directory::at` canonicalization stay as they are.
- **Attachments stay per-project, at `<store>/projects/<id>/attachments/`.** An earlier revision moved them to a store-wide `<store>/attachments/`; that is **reversed**, and the reversal is the more important half of this entry because the reasoning that produced it was sound and still led to the wrong trade.

  The store-wide case rested entirely on one later feature — moving an agent between projects. With per-project staging, a moved agent's history references a file that stays behind in the source project, and the move rewrites journals, so the source's reference-GC collects that file on its next project load. Store-wide dissolved that: no operation would ever change where a referenced file lives.

  **What it cost was paid in the wrong place.** Deleting a project goes from `remove_dir_all` on the project root — trivially correct, no way to get it wrong — to a reference sweep that parses every project's journal and requires the frontend to declare every unsent draft. And a bug in that sweep goes from destroying one project's files to destroying every project's. That is the wrong direction to move risk in the operation whose failure mode *is* deleting data the user still wants, and it buys nothing at all until agent moves ship.

  **So: accept a limitation instead.** A moved agent's older attachments are collected from the source project shortly after the move. The recorded path in the journal is untouched, so send↔turn correlation is unaffected — only the *file* goes. Consequences, in full: that agent's historical attachment thumbnails render broken in its transcript, and if the agent is asked to re-read one of those files it reports the file as missing. Both degrade visibly and locally; neither corrupts history or affects any turn that does not reach for an old attachment.

  **The mitigation, identified and deliberately not taken now:** the move could copy referenced attachment files into the target project and rewrite `Send.attachments[].path` while preserving `dispatched_path` — exactly what the migration tool already does, with machinery that already exists. That keeps per-project storage, `remove_dir_all` delete, and per-project GC all intact, at the cost of the move touching files (and duplicating a fan-out file referenced by both a moved and a remaining agent, which is harmless because each project's GC sees its own reference). Reach for this if the broken-thumbnail limitation proves annoying in practice; do not build it pre-emptively in the milestone already described as the riskiest.

  `dispatched_path` is retained regardless — migration relocates files once, and that rewrite is what would otherwise break historical send↔turn correlation, which reconstructs the exact dispatched prompt text including footer paths.

  M0's probe (agents can read files staged outside their cwd) is **not** invalidated by this reversal; it answered "can we," and per-project staging under the store root is also outside the cwd. It simply no longer decides anything.
- **Gemini support is removed entirely (M0.5), before anything else is built.** It cannot be tested — the CLI is auth-dead for individual accounts (harness-behavior G26), so neither `make test-live-gemini` nor manual verification can run, and access requires a business/enterprise account nobody here has. An adapter that cannot be exercised is not supported code: it is 4,000+ lines of Rust plus a frontend surface that every subsequent change must keep compiling, with no way to know whether it still works. Removing it shrinks M1–M4's per-harness surface before they are written, which is why it goes first. **Switchboard supports three harnesses after M0.5: Claude Code, Codex, Antigravity.**
- **"Clone" is banned vocabulary; the features are "duplicate setup" and "move."** A history-preserving clone is not uniformly implementable: Claude forks materialize only as a real turn (harness-behavior §3.5), Codex forks need the unwired app-server, Antigravity has no user fork. M3 therefore copies configuration and mints fresh sessions, for all three harnesses uniformly. History-preserving clone is out of scope, permanently unless the harness landscape changes.
- **Move is scoped to projects sharing one working directory.** Claude sessions are cwd-namespaced (`encode_cwd`, harness-behavior §3.5b) — a cross-directory move breaks `--resume` for them. Note this rationale *narrowed* with Gemini's removal (it was the second cwd-namespaced harness) and now rests on Claude alone; the decision stands anyway, because same-directory move is uniform across all three harnesses, covers the primary use case (multiple projects per repo), and the alternative is a harness-conditional move surface. Cross-directory move (even for the cwd-independent Codex/Antigravity) is deferred — do not build it.
- **Browsing is side-effect-free; activation happens on commitment.** Cross-project pickers list rosters through a *read-only* registry read (no `instance.lock`, no cache mutation). The real `open_project` — which locks and loads — runs only when the user picks, which is also where a `ProjectLocked`/corrupt-registry error has a sensible surface. This pattern is established in M1 and reused by M3's target picker.
- **"Remove directory" is reframed, not preserved.** With a central store, the catalog entry's only load-bearing job is the `directory_id → path` mapping that resolves an agent's cwd. So: a catalog entry is never deleted while any project references it; the user-facing "remove" becomes *hide* (view-state in `workspace.yaml` — drops it from pickers and the empty-directory list, projects unaffected). Cleanup happens through the existing project archive/delete affordances. Rationale to record in code: deleting the mapping would strand every project under it with no cwd to dispatch into.

## M0 — Attachment readability probe (decision gate) — ✅ **DONE 2026-08-27**

> **Result: store-wide attachments are viable; no `--add-dir` change is needed.** Claude (2.1.247), Codex (0.149.0), and Antigravity (1.1.21) all read an attachment staged wholly outside the agent's cwd. Antigravity — the predicted failure, because `--add-dir <cwd>` scopes its file tools — **passes without a second `--add-dir`**. Gemini was indeterminate rather than failing — auth-dead for individual accounts (harness-behavior G26), so its in-cwd control failed identically and the probe could not distinguish. **That indeterminacy is now moot: M0.5 removes Gemini.** Full table and the caveat that this holds *because* the adapters spawn unsandboxed: `docs/harness-behavior.md` §3.7. Tests: `live_<harness>_attachment_outside_cwd_is_readable`.
>
> **Also surfaced, not part of M0's question, recorded in harness-behavior §5:** Gemini's trusted-folders gate prints `Approval mode overridden to "default" because the current folder is not trusted`, i.e. it silently downgrades the `--yolo` the adapter depends on. Observed but effect-unverified (auth dies before tool use). It is superseded by M0.5 and kept only as history.
>
> **Consequences for the rest of the plan:** fallback B and the `.git/info/exclude` path are dead — delete them from scope rather than carrying them; the Antigravity adapter needs **no** arg change. The store-wide branch this probe unblocked was **later reversed** (see the attachments decision above) — the probe established that store-wide *would work*, not that it was needed, and per-project staging is also outside the cwd. M4 therefore accepts a documented attachment limitation instead of inheriting a store-wide GC. The `dispatched_path` preservation in M2.1 is still required — migration relocates files once, and that rewrite is what would break historical send↔turn correlation.

Small, one-session milestone; compressed structure.

**Goal.** Determine empirically whether all four harnesses can read a staged file located *outside* the agent's cwd (under the Application Support root), because that decides the attachment design for **both M2 and M4**: if staging must stay cwd-local, M4's move must handle attachment relocation after all (the fallback's per-directory staging keeps paths stable within a directory, which same-directory moves preserve — but verify that reasoning against the fallback actually chosen). The current guarantee ("inside cwd is the only location readable by all four" — attachments plan) predates the current maximum-autonomy spawn flags and must be tested, not assumed.

**What to do.**

- For each harness, run a variant of the existing `live_<harness>_attachment_*` pattern: stage a small text file in a temp dir *outside* the project cwd (simulating `~/Library/Application Support/switchboard/attachments/`), reference it by absolute path in the prompt footer, assert the agent echoes its content.
- For Antigravity additionally probe: (a) bare (outside-workspace read under `--dangerously-skip-permissions`), and (b) with a second `--add-dir <staging-dir>` — `--add-dir` is load-bearing for workspace scoping there (`crates/harness/src/antigravity/mod.rs`), so (b) is the expected fix if (a) fails.
- These are throwaway probes unless they become permanent: if the store-wide location is adopted in M2, convert them into the permanent live tests for the new staging location (named `live_<harness>_attachment_…` per the AGENTS.md naming rule).

**Definition of done.** Results recorded in `docs/harness-behavior.md` (per-harness: readable / readable-with-flag / not readable, CLI versions probed) **before** any further work — findings go into docs immediately, not held in a branch. A one-line decision (store-wide / store-wide+`--add-dir` / fallback B) recorded there and referenced by M2 and M4. Cost discipline per AGENTS.md: tiny prompts, cents total.

## M0.5 — Remove Gemini support

Numbered `M0.5` rather than renumbering M1–M4: four rounds of review reference the existing numbers, and preserving that traceability is worth more than tidy sequence.

### Goal & Outcome

Delete the Gemini harness from Switchboard entirely — adapter, tests, fixtures, frontend surface, and live docs — leaving three supported harnesses: Claude Code, Codex, Antigravity.

- Gemini no longer appears anywhere a user can see it: not in the create-agent harness picker, not in Settings → "Supported CLIs", not in status probes, not in transcript attribution.
- The workspace builds, lints, and tests green with `HarnessKind::Gemini` gone, `crates/harness/src/gemini/` deleted, and no `gemini` identifier left in shipping code.
- `make test-live` covers three harnesses; `make test-live-gemini` is gone.

**Why now, and why not "just leave it":** the adapter cannot be exercised — the CLI rejects individual accounts (G26), so neither live tests nor manual checks can run, and no one here has the business account that would restore access. Untestable code is a liability every later milestone pays for: M1–M4 each carry per-harness branches that would have to keep compiling against an adapter no one can verify. Deleting first makes those four milestones smaller.

### Implementation Outline

**The compiler is the checklist.** `HarnessKind` matches in this codebase are deliberately exhaustive with no `_` arms — the enum's own doc says the arms are "written out per variant rather than collapsed so that adding a harness remains a deliberate decision." Deleting the variant therefore turns every affected site into a compile error. Lean on that rather than grepping: fix compile errors until clean, then grep for stragglers in strings, docs, and test names.

Order:

1. **Core** — drop `HarnessKind::Gemini` and its arms in the five capability methods (`supports_model_selection`, `supports_effort_selection`, `effort_requires_model`, `supports_refresh`, `supports_session_fork`). Preserve each method's *general* rationale while deleting the Gemini-specific clauses; several read as cross-harness comparisons ("Gemini is the lone holdout") that become false rather than merely stale.
2. **No registry-compatibility path — this is a pure deletion.** A `registry.jsonl` line with `"harness": "gemini"` will no longer deserialize and will surface as `CoreError::CorruptJsonl`. A typed removed-harness error was considered and **dropped on the owner's confirmation that no Gemini agent exists in any user's registry** — building a migration path for zero records is the speculative work this plan's principle forbids. Add nothing here; if a stray record ever appears, the fix is deleting one line from a JSONL file.
3. **Harness crate** — delete `src/gemini/` (adapter, parser, session_file, skills, config), `src/bin/fake_gemini.rs`, `tests/gemini_adapter.rs`, and `tests/fixtures/gemini/`. Remove Gemini arms from shared harness code (`resume.rs`, the adapter registry, tool-facet mapping) and the Gemini live tests in `tests/live.rs`.
4. **Dispatcher / app** — remove `AppState::gemini_adapter`, its construction, the `adapter_for` arm, the auth/install probe, and Gemini cases in `live_end_to_end.rs` (including the M0 probes added for it).
5. **Frontend** — remove the variant from `types.ts` and every consumer: `harnessDisplay`, `harnessAvailability*`, `agentSelection`, `CreateAgentForm`, `HarnessStatusList`, reducers, and their tests. The wire-format union is the source of truth; deleting the member surfaces the sites via `svelte-check`/`tsc` the same way the Rust compiler does.
6. **Build/docs** — drop `test-live-gemini` from the Makefile and `LIVE_PKGS` filters. Update **only the live docs**: `system-design.md` (§9 capability matrix and every four-harness claim), `harness-behavior.md` (its Gemini rows/gaps — including G26 and the new §3.7 row and §5 trust note, which become historical), `README.md` harness list and limitations, `AGENTS.md`, `harness-update-review.md`.

**Documentation scope — read this before touching `docs/`:** past implementation plans are **historical records, not living docs**. Roughly thirty files under `docs/implementation_plans/` mention Gemini, including a whole `2026-05-12-v1-m3-gemini-adapter.md`; `docs/research/archive/` is explicitly frozen. **Do not edit or delete any of them.** They describe what was true when written, and rewriting them destroys provenance. Only the five live docs listed above change.

**The UUID-version asymmetry goes away with Gemini.** `HarnessKind`'s doc records a "UUID-version asymmetry (load-bearing)": Claude Code mints session ids as v7 like the rest of Switchboard, while **Gemini alone** minted v4, because Gemini's session filenames use the id's first 8 hex chars and same-millisecond v7s collide there (`project.rs`'s comment ends "Localized to Gemini"). Delete the v4 arm with the variant and delete the asymmetry paragraph — there is no remaining harness it describes, and Claude/Antigravity id minting is untouched. (An earlier draft of this plan said to *keep* v4 generation as a deliberate non-change; that was written from a partial read of the comment and is wrong — v4 was never the general case.)

### Definition of Done

- Workspace compiles with no `gemini` identifier in shipping code (`grep -ri gemini crates/ src/` returns only intentional historical mentions, if any); `make check` green, including the browser suite.
- `make test-live` runs and passes for Claude, Codex, Antigravity; no Gemini target remains.
- Frontend tests updated, not deleted, where they enumerated harnesses (the three-harness assertions still prove the picker/status surfaces work).
- Live docs updated per the scope rule above; historical plans and `docs/research/archive/` untouched — a reviewer should see zero diff under `docs/implementation_plans/` other than this file.
- README states three supported harnesses, with one plain-language line on why Gemini was dropped (individual-tier access withdrawn upstream), per the README's user-facing register rules.

## M1 — Cross-project forwarding

### Goal & Outcome

Extend the existing ↪ Forward picker so the user can forward *another project's* agent's latest output into the current project's send.

- The compose bar's Forward picker (and the prompt composer's and workflow composer's per-field pickers — the component is shared by all three) gain a **Projects** section at the bottom: `Projects ▸ <project> ▸ <agent>`.
- Browsing the submenu is free of side effects — it neither loads nor locks the projects it lists, and a locked/corrupt project shows as unpickable rather than throwing from a hover.
- Picking a cross-project agent adds a source chip labeled with project *and* agent (e.g. `backend-api · reviewer` — project first, matching the backend's qualified names), and the send composes exactly like a same-project forward: hold until the source's in-flight turn settles, then compose latest completed output, any-empty-invalidates. A local agent *known* to have no forwardable output is disabled in the direct pickers rather than annotated; pane selection deliberately stays warning-based (the expanded chips carry the warning), with the backend as the enforcement point either way.
- A cross-project chip **persists**: it survives project switches, Git-view toggles, and app restarts, and still resolves at dispatch — including when the source's project was never opened this session.
- A source whose turn just failed forwards the failure note (existing behavior), correctly read from *that source's own project journal* — on **every** forward surface, including workflow forward-fields.
- Only projects in **available** directories are offered (an unavailable directory's journal and cwd can't be read pre-M2; after M2 this restriction can be lifted, but that is M2's concern, not M1's).

**Scope boundary (explicit assumption from the discussion):** this extends the existing *latest-output* forward. A per-message "forward this exact message" action on transcript rows is a different feature with a different data contract and is **out of scope**. If the user asks for that, it's a new plan.

### Implementation Outline

Backend first, frontend second — the backend changes are correctness fixes that stand alone.

1. **Fix the single-journal assumption — in both resolvers, via one shared helper.** `resolve_all_sources` reads one journal from `sources.first()`'s project and applies it to every source; `resolve_workflow_forwards` has the *identical* defect (one journal from the first forward-field source). With mixed-project sources either consults the wrong journal, so `latest_turn_failure_note` misses a failure and silently forwards a stale older answer — the exact failure mode the function exists to prevent, and in the workflow surface the hardest to notice. Fix: extract a group-sources-by-owning-project journal read as one helper and consume it from **both** functions. Do not fix one and prop-gate the picker for the other — a per-consumer Projects section is an inconsistency users will report as a bug. Preserve the existing contracts: `try_join_all` registering all waits up front, declared order preserved, fail-loud on corrupt journal. This is a genuine bug fix worth landing as a standalone first commit.
2. **The wire carries a source *reference*, not a bare agent id — this is what makes cold resolution possible at all.** Forward sources currently reach the backend as `Vec<AgentId>` (`expandForwardSources` discards everything else). For a project never opened this session, `agents_by_id` holds nothing, so an agent id alone does not tell the backend which project to open — the only fallback would be scanning every registry in every directory. Change the wire shape to a source reference carrying both ids:

   ```
   { agent_id, project_id }
   ```

   Thread it through all three forward paths (manual, prompt-argument, workflow field). The backend opens the **declared** project (the real `open_project_impl`, idempotent), reads the agent, and **verifies the record's actual `project_id` matches the declaration** — a mismatch is a stale draft naming an agent that has since moved (M4) or been re-created, and must be refused rather than silently trusted. **`project_id` is required on the wire — there is no legacy-id union.** The only backward-compatibility surface is *persisted frontend drafts* (the app ships its own frontend; there are no third-party IPC clients), so the **frontend parser upgrades an old bare-id draft** — defaulting it to the draft's own project — before it ever reaches IPC. Keeping the wire type unambiguous is worth more than an untagged union that would have to guess. This makes dispatch-time resolution the single choke point for every path that can reach the backend with a foreign agent — a chip picked this session, a chip restored after restart, a direct IPC call — without any frontend surface having to pre-open anything.
3. **Read-only roster command for the menu.** A new command that lists a project's agents via a pure registry read — `Directory::open_project` is already documented as a no-mutation read (it's how `enumerate_all_projects` works) followed by `list_agents` on the returned handle, **without** taking the `instance.lock` or inserting into `projects` / `agents_by_id`. **This display/activation split is the shared convention: menus read; picks activate.** M3's target-project picker reuses exactly this command. Errors degrade per row: a project whose registry can't be read renders unpickable with a reason, never a thrown error from a hover.
4. **Frontend: Projects submenu in `ForwardSourcePicker.svelte`.** Data: the already-available flat project list (filtered to available, excluding the current project), agents fetched via the read-only roster command on submenu expand (with a small session cache). Picking calls the activation path (real open); a `ProjectLocked` or corrupt-registry failure refuses the pick with a message at the pick site — that is the error's home, not the hover.
5. **`ForwardSource` carries project identity, and `expandForwardSources` stops discarding it.** The persisted DTO gains the owning `projectId` and project display name (absent ⇒ current project, so existing drafts restore unchanged); the expansion that feeds the backend now yields the (2) source references rather than bare ids. `reconcileForwardSources` — which currently drops anything not in the current roster, silently deleting foreign chips on every remount — keeps foreign sources: refresh their display names via the read-only roster when the project is readable, retain them as-is otherwise (the backend in (2) is the validator; an actually-deleted agent fails the send with a clear message rather than vanishing beforehand). The project name on the chip and in the held-forward "waiting for …" row comes from this DTO.
6. **Labeling and copy.** Wherever a forward source is named and the agent is not in the recipient project, append the project name: source chips, the held-forward row in `UnifiedTranscript`, and the backend-composed invalidation reasons (the grouping in (1) has both source-project and agent context in hand). The held-forward store is already keyed by *recipient* project and the forward already renders in the recipient's transcript — that stays.
7. **Readiness classification** (`agentReadiness` — the "this source is empty and would block the send" pre-warning): computed from the read-only path where cheap; where it isn't, show no readiness marker for a foreign agent rather than a wrong one.

Edge cases identified in discussion and review:

- Sources spanning N projects in one forward must produce N journal reads, not N×M.
- A cross-project source's project being closed/removed mid-hold: the existing invalidation path handles a failing `lookup_agent`; verify the error surfaces as an invalidated forward, not a hung hold.
- Pane sources are recipient-project-local and unaffected (panes expand to agent ids in the frontend before the backend call — unchanged contract).

### Definition of Done

- Unit tests on the shared journal-grouping helper through **both** consumers: mixed-project sources where one source's *own* journal records a failure — assert the failure note is forwarded (fails against today's code) via `resolve_all_sources`, and assert the workflow completed-only path rejects/notes it via `resolve_workflow_forwards`; N sources across two projects → each resolved against the correct journal.

## M2 — Central project store

### Goal & Outcome

All Switchboard-owned per-project state lives under the user-global config dir. Working directories contain **nothing** of Switchboard's.

- Layout: `<config-dir>/` gains `projects.jsonl` (global index), `directories.jsonl` (the catalog: `directory_id → path`), `locks/` (session locks — release root only, see the session-lock section), and `projects/<project-id>/{config.yaml, registry.jsonl, journal.jsonl, pins.jsonl, attachments/, sessions/, runs/, instance.lock}`. The per-project inner layout is **unchanged** — attachments included, per the reversal recorded in the attachments decision above. There is no store-wide `attachments/`.
- `workspace.yaml` shrinks to view-state (hidden directories, archived projects, ordering) and keeps its best-effort load posture; **no required fields are added to it**, so an un-migrated file still parses. The catalog and index are fail-loud and versioned.
- **An existing user who launches the upgraded app without migrating loses nothing and is told what to do**: a blocking migration notice, not an empty project list — and their old `workspace.yaml` is never overwritten while the notice stands.
- Projects survive working-directory deletion. A project whose directory is missing still lists, renames, archives, deletes; dispatch/file-search/terminal/Git are unavailable until the path is re-pointed (re-point = update the catalog entry's path — the affordance stable ids exist for; a minimal "edit path" on the directory entry is in scope, since without it a survived project is unusable).
- Deleting a worktree no longer destroys journals; users delete projects via the app's existing delete (which already never touches the working directory).
- No `.gitignore` entry needed in any repo (attachment fallback B, if forced by M0, uses `.git/info/exclude`).
- Attachment thumbnails still render in the running app (webview asset scope updated — see M2.5).
- A dev build and the installed app cannot concurrently drive the same harness session (M2.3), and a turn that cannot obtain that guarantee is refused with a clear message rather than allowed through.
- Existing users run one migration command; originals are preserved until an explicit cleanup.

### Implementation Outline

Order is load-bearing: core storage first, then app wiring, then the lock, then migration + legacy handling, then attachments/frontend/docs. One PR; these are the commits.

**Every commit builds and passes `make check`.** That is what makes each one reviewable on its own and keeps `git bisect` usable across a milestone that rewrites the storage layer. The one place this constrains the order is M2.1/M2.2: deleting from `Directory` in M2.1 would break `commands.rs`, which still calls `init` / `has_switchboard`, so M2.1 is **purely additive** and every removal lands in M2.2 alongside its updated callers (noted again in both sections).

**M2.1 — Core: `Store` replaces `Directory`'s project ownership.**

- New type in `switchboard_core` (module doc carries the "why we moved" rationale from the decisions section) owning: the global `projects.jsonl` index, the `directories.jsonl` catalog (`{directory_id, path}`; append on add, rewrite on re-point; **entries are never deleted while a project references them** — record why), and project-root resolution (`<store-root>/projects/<id>`). **No store-wide attachments dir** — staging stays per-project under the project root (see the attachments decision); if a `Store::attachments_dir` was added before the reversal, remove it rather than leaving an unused path for someone to wire up later. Index and catalog share the existing append-on-create / rewrite-on-mutate semantics and the atomicity/orphan postures documented on `Directory::create_project` / `rename_project` / `delete_project` — port those doc comments, they encode hard-won crash-consistency reasoning. Both files are versioned (a schema marker, checked fail-loud like `ProjectConfig.version`). `ProjectSummary` gains `directory_id`.
- Constructed from an explicit root path — core never resolves `config_dir()` itself (same injection posture as `switchboard_prompts`). **This injected-root pattern is the shared convention: `AppState` gains a required store root, the migration tool takes it as a flag, the session-lock root (M2.3) follows it, tests pass a `TempDir`.** Unlike `workspace_path: Option<PathBuf>`, the store root is *required* — project persistence cannot degrade to no-op.
- **`Directory` is left untouched in this commit.** Its shrink — down to canonicalized-path identity and cwd validation for dispatch, with `Directory::init`, `has_switchboard`, the directory `config.yaml` (a version-only placeholder), and the old-layout-only `paths.rs` constants deleted rather than deprecated — moves to **M2.2**, which updates the `commands.rs` callers in the same commit. Doing it here would leave M2.1 non-compiling, so neither `make check` nor a reviewer could evaluate it. Deleted, not deprecated, still holds; only the commit it lands in changes. The two layouts coexist for exactly one commit and nothing reads the new one yet.
- `Project` is nearly untouched (paths already `root`-relative; `directory` resolved via `directory_id` at load; `attachments_dir` stays `root`-relative and needs no change). `create_on_disk` takes the store's projects dir — its signature already separates cwd from metadata root.
- `Attachment` gains an optional `dispatched_path` (serde-default `None` ⇒ same as `path`): **prompt reconstruction uses `dispatched_path ?? path`; rendering and GC use `path`.** Rationale to record on the field: the surplus-case send↔turn correlation reconstructs the exact dispatched text (see `align_surplus_candidates`'s doc comment), so the path that was *sent* must survive even when the file's storage location changes. Migration is the only writer of a divergent `dispatched_path`.
- `meta_sidecar_path` / `turnmeta_sidecar_path` in `switchboard_harness` change signature to take the project root directly — they currently re-derive the `.switchboard` layout inside the harness crate, which is layout knowledge that doesn't belong there and would now be wrong. ~7 call sites.

**M2.2 — App: workspace simplification and lookup collapse.**

- **Carries M2.1's deferred `Directory` shrink** (see above): the deletions land here, with their `commands.rs` callers rewritten onto the store in the same commit, so both commits build.
- **The session-id collision scans read registries, not projects.** Take **one `list_projects()` snapshot** — the index alone, never `list_projects_resolved` — locate the target's `ProjectEntry`, take `target_id` from `entry.directory_id`, filter Claude candidates by that id, and read each matching registry with `Store::read_project_registry(&entry)`. `registry.jsonl` lives at `<store-root>/projects/<id>/`, so the scans never need a resolved working directory; that is the same reason `list_project_agents_readonly` loses its `directory` parameter, applied to the same kind of read. Two sources are forbidden and both are tempting: `ProjectConfig.directory_id` is recovery-only and bypasses `directory_map`, the only thing that detects a duplicated or missing id, so an ambiguous directory would silently scope the scan to a subset instead of refusing; and `list_projects_resolved` reads the catalog, which reintroduces the store-wide failure this design removes. Take the collision error's project name from `ProjectEntry.name`: `rename_project` commits config-then-index, so the index is what the user is looking at and the error should match.
- **Directory-resolution health is an eligibility check on the attach *target*, not part of the scan.** The target needs a live cwd to dispatch, so refuse the attach when *its* directory is missing or ambiguous, naming the repair. An unrelated project's damaged catalog row must never block it — that separation is the whole point of the catalog-free scan.
- **`enumerate_all_projects` and `enumerate_directory_projects` are deleted, not ported.** Their only call sites are the three collision scans (`commands.rs:2617/2644/2684`), which no longer load projects. They are also named in prose at `commands.rs:2359–2363`, `2635`, `2736`, and `6117` — backticked, not intra-doc links, so deletion leaves those dangling silently rather than failing the build. Per the scoping-rationale requirement below, `2359–2363`'s cwd-namespaced-vs-globally-unique explanation must move to the new call sites rather than being deleted with its host.
- **Route every *other* multi-project read through `Store::list_projects_resolved` + `Store::open_resolved`, not a loop over `open_project`.** This covers `list_projects_impl`; what survives of `open_resolved` after the bullets above is dispatch-shaped, which is where requiring a resolved directory is correct. `ResolvedProject` is a snapshot, so build it and consume it inside the same `registry_write` hold; a re-point between snapshot and open would otherwise resolve the old working directory. The per-id method re-reads the whole index *and* the whole catalog for one project, so a loop is N full parses of each; the batch method reads both once and resolves every row against an in-memory map. An unresolvable `directory_id` is one unresolved row, never a failed call.
- **The wire row carries a structured directory status, not `available: bool`.** Four states — `resolved_available`, `resolved_path_unavailable` (catalog row exists, cwd moved/deleted/unmounted), `catalog_missing`, `catalog_ambiguous` — derived from `DirectoryResolution` plus the existing path check. Flattening here would discard the distinction at the only place a human sees it, and recovering it in M2.5 would mean a second backend-and-wire change. The three failure states have different causes and different repairs: `resolved_path_unavailable` is the ordinary moved-folder case, `catalog_ambiguous` is corruption fixed by the same re-point, and `catalog_missing` is corruption repaired by re-binding the identity to a user-chosen path (M2.2). The frontend may render all three identically until M2.5 decides the copy — the requirement here is that the information survives the boundary.
- **The read-only roster stops requiring a resolved directory — a behavior change, not a port.** `list_project_agents_readonly_impl` currently gets `ProjectNotFound` from `open_project`, which also resolves the catalog, so a project with a damaged directory row cannot list its roster today. Moving it to `Store::list_project_agents(id)` keeps the `ProjectNotFound` (that method checks index membership) and drops the cwd requirement: browsing a roster genuinely needs no working directory.
- **The re-point affordance repairs a directory identity, not one project.** The command takes a **project id**, not a path: the identity is not something the user has, and the two states worth repairing (`catalog_ambiguous`, `catalog_missing`) have no single path to name. `repoint_directory` moves every project referencing that id and collapses a duplicated id to a single row. `catalog_missing` is repaired by **binding** rather than re-pointing: the identity already exists and the projects already reference it, so restoring the lost row is not inventing an identity. (An earlier revision of this bullet refused it on the opposite reasoning; that reasoning was wrong, and migration validation cannot help — it stops the *tool* producing the state, not a partial restore or sync conflict producing it later.) `Store::bind_directory` refuses an id that still resolves and a path another identity holds. The UI must say so — a user re-pointing from one project's error is moving all of its siblings too. It is also an **uncertain-commit** operation: quiesce and drain before the call, re-read the catalog on **both** `Ok` and `Err`, and rebuild project and actor state from the observed path. Never restore the pre-call state on `Err` — the write may have landed, and believing the error is what leaves the app dispatching into the old directory. If the post-write re-read also fails, leave those projects unloaded and refuse dispatch.
- **Re-pointing a directory is a lifecycle operation, not just a catalog write.** `Project.directory` is snapshotted at open and is the dispatch cwd, so the repair is incomplete until the app: refuses or quiesces turns and workflow runs against the old path, drains the dispatch-context factories holding the old `Project`, drops the affected entries from `state.projects`, and reloads against the new path before dispatch resumes. Evicting the loaded-project map alone is insufficient — a running actor keeps its own handle. The situation that prompts a re-point is precisely the one where the project is already open.

- `workspace.rs`: entries lose `cached_projects` (and the four cache methods + `knows_project`); what remains is view-state — hidden set, archived set, ordering. Load stays best-effort *because nothing left in it is load-bearing* (state this in the module doc — it is the invariant that makes best-effort safe). Serde ignores the removed field, so old files parse.
- `commands.rs`: `find_project_in_directories`, `find_directory_for_project`, `enumerate_all_projects`, `enumerate_directory_projects` collapse into store-index/catalog lookups. `list_projects_impl` loses its entire cache-vs-fresh branch: rows come from the index; `available` now means "the *directory* resolves," computed per row from the catalog entry's path.
- **`list_project_agents_readonly` loses its `directory` parameter** (added in M1, after this section was written). Today it takes the owning directory as a locator and validates it against the path-keyed `state.directories` before reading `<dir>/.switchboard/projects/<id>/registry.jsonl` — a path-based lookup that exists only because projects live under directories. Under the store the registry resolves from the project id alone (`<store-root>/projects/<id>/registry.jsonl`), so the parameter is not merely redundant but misleading: it invites a caller to think the directory is authoritative for the read. Delete it. The M1 code already anticipates this in a comment at its `ProjectNotLoaded` arm ("churn ahead of the central store removing this path-based lookup entirely") — that comment goes with the parameter. This is a **wire change**: the TS wrapper in `api.ts`, the exact-payload-key assertion in `ComposeBar.test.ts`, and `CrossProjectBase.projects` in `ForwardSourcePicker.svelte` (whose entries carry `directory` solely to feed this call) all shed it. Do this here rather than in M3: M3's target-project picker reuses this exact command, so the shape has to be right before a second consumer depends on it.
- Session-uniqueness scans (`check_claude_session_id_unique` per-directory; Codex/Antigravity workspace-wide) keep their exact scoping semantics — only the enumeration source changes (index filtered by `directory_id` / whole index). The scoping rationale comments (cwd-namespaced vs globally-unique ids) must survive.
- **`agents_by_id` insert detects cross-project conflicts.** Where the cache currently inserts last-wins, an insert whose `AgentId` already maps to a *different* `project_id` surfaces a typed conflict instead of silently shadowing. This is load-bearing for M4's crash posture (an interrupted move leaves the agent in both registries; this check is what makes that anomaly visible and user-fixable rather than silent), but it lands here because it is a store-integrity property, not a move feature.
- "Remove directory" → hide, per the settled decision above. `remove_directory_impl`'s drain machinery survives only where still needed (project delete); hiding a directory stops nothing and touches no project.
- The `.switchboard` exclusion in the file-search walker is deleted.
- Test migration is the bulk of this milestone (~33 `AppState::new` sites, ~125 `TempDir` fixtures, ~20 tests asserting literal `.switchboard/` paths — **counts predate M1, which added tests in exactly these files; treat them as a floor**). Build one test fixture helper (state + temp store root + temp cwd) early in this commit and convert call sites to it, rather than threading a second `TempDir` through each test by hand.

**M2.3 also closes the lifecycle-generation residual.** M2.2 narrowed it to the interval between its pre-enqueue generation check and the dispatcher creating the actor. Have the factory capture the project's generation when it is built and re-compare it at turn start, refusing a stale one; that closes it completely and removes the residual note in `AppState::project_generation`.

> **Built in `preflight()`, not `build()` — a correction to this paragraph as first written.** The original text called for making `build` fallible, on the reasoning that `build` is where the stale `Project` snapshot is used. But `preflight` already runs *later* than `build` (`crates/dispatcher/src/lib.rs`: build at the top of `run_turn`, preflight below it) and is already fallible with a refusal path that emits `MessageFailed` and fires the completion handle. Putting the check there covers strictly more — anything `build` would have caught, plus the interval between the two — with no second refusal path to keep in sync, and no change to `build`'s signature. `build`'s stale `cwd` is never reached, because the refusal happens before the journal write and the spawn. The session lock still requires the `preflight` return-type change described below; that part is unaffected.

**M2.3 — Shared session lock (cross-build). This commit changes a dispatcher trait — it is cross-crate, not app-local.**

- A per-turn advisory lock at `<lock-root>/locks/<key>.lock`, where `<key>` is a **fixed-length hash of the canonically serialized `(harness, session locator, cwd-namespace)` tuple** — never the raw locator: Codex thread ids are arbitrary strings (`SessionLocator::Codex`'s doc says so explicitly), so a raw id in a filename is a path-validity and length hazard. The cwd component is included for **Claude only** (its ids are cwd-namespaced, so id alone over-locks; Codex thread ids and Antigravity conversation uuids are globally unique) — reuse the existing per-harness scoping rationale. Pre-M0.5 this clause covered Gemini too; if you are reading a version of the codebase that still has Gemini, it belongs in the cwd-namespaced group.
- **A materializing fork must also lock its parent's key.** A Claude fork's first dispatch reads the **parent's** session file to materialize while carrying its own freshly generated UUID — so keying only on the dispatching agent locks a key nobody contends on while touching the file that is contended. Acquire the parent's key **in addition to** the agent's own (not instead of — the fork writes its own file too), in a deterministic key order.
  - **Derive the parent key from the fork's own `forked_from_session`** (plus harness and cwd namespace), **not** from `busy_fork_source`. That function answers a different question and returns the parent *only when the parent is busy* — its doc states it returns `None` for "not a fork, already materialized, parent gone, or **parent idle**." The idle case is exactly the dispatch that proceeds and therefore needs the lock, so keying off it would invert the coverage: the parent would be locked only when the in-process guard was already refusing the turn. "Parent gone" is the same trap in the other direction — it returns `None` because *our* process isn't writing that session, while the file is still on disk, still read by the fork, and possibly live in the other build. Keep `busy_fork_source` for its friendly in-process refusal; it is not load-bearing for locking.
  - The hazard this closes is harness-behavior §3.5's **"Forking while the parent is mid-turn"** finding. Cite that precisely and do not overstate it: that probe found the parent file is **not** corrupted and the child is valid JSON. The harm is a semantically incomplete snapshot — a synthesized `"No response requested."` stub in place of the parent's in-flight answer, which the branch then permanently lacks, plus a merge-misattribution risk. (Do not conflate this with the separate "interrupting a fork's first dispatch" probe, which looked for partial child files and never observed one.) §3.5 closes by naming the residual it accepts — the mid-turn fork gate is "a look, not a lock, so a concurrent automation or a bare-CLI writer on the same session can still slip through" — and the cross-build instance is precisely that writer. This lock closes that residual.
- **Lock root**: injected through `AppState` alongside the store root (same convention), with the production default resolved **unconditionally to the release config path** by a small function deliberately *not* going through `config_dir()` — comment: the whole point is that dev and release builds contend on the same file, so this root must never inherit dev isolation. Tests inject a `TempDir`; without injection the DoD's contention tests would acquire real locks under the developer's live `~/Library/Application Support/switchboard/locks/` and contend with a running app.
- **Ownership — `DispatchContextFactory::preflight()` returns an RAII turn permit.** (Name the trait at every mention: a separate workflow-side `preflight` exists in `workflow.rs` / `workflow_commands.rs`, and M4 refers to it for the maintenance-flag check — two different functions, same word.) Neither existing hook can carry the guard as-is: `DispatchContextFactory::build()` is infallible and its `DispatchContext` is destructured field-by-field in `run_turn` (a guard not bound there drops immediately), and `preflight()` returns `Result<(), String>` with no way to hand back a handle. Note the call **order**, which rules out the obvious alternative: `build()` runs *first* (`crates/dispatcher/src/lib.rs:1527`) and `preflight()` *later* (`:1572`), so any "preflight acquires, build carries it" scheme is impossible — preflight hasn't run when the context is constructed. The shape: change `preflight()`'s return to `Result<TurnPermit, String>`, an opaque RAII type owning the lock `File`; `run_turn` **binds** the returned permit locally for the rest of the turn, so `File`-drop releases on every terminal, cancellation, drain, and panic path with no mutable "pending guard" state on the factory. Acquisition happens inside `preflight()` as one step (a separate check-then-acquire has a TOCTOU hole). This siting is deliberate and already matches preflight's documented role — it is the freshest judgement available, after the PATH wait and immediately before the fail-closed journal write, so a refused turn leaves no durable trace. Factories with no session to lock return a no-op permit. Contention / I-O failure propagates through `preflight()`'s existing error path as a typed, user-visible dispatch failure ("this session is in use by another Switchboard instance").
- **The key is a cross-build protocol, and must be pinned as one.** Golden-vector tests fix the expected digest per harness for fixed inputs. Without them the suite only asserts keys relative to each other, so a refactor of the component order, length prefixes, harness tags, or the schema constant can change every key while every test passes — and two separately-installed builds silently stop protecting each other, with no error anywhere. **Any future bump of the schema constant is a protocol break, not a version stamp:** it must ship a transition acquiring both the old and the new key until the compatible-build floor has moved.
- **Fail-closed.** Acquisition failure of any kind refuses the turn. Do not soften to warn-and-proceed: the lock guards against concurrent mutation of one harness session file (data corruption, per the research doc), and the codebase already accepts "can't persist ⇒ refuse the turn" for the send journal. Record this rationale at the acquisition site.
- An agent with no locator yet (first Codex/Antigravity turn) has no session to contend on — skip, and rely on the post-capture uniqueness scan as today.

**Deferred out of M2.3, both recorded as M2.5 requirements** (see that section): the refusal's failure *classification*, and the project-scoped admission claim. Neither is user-visible today; both become so with work M2.5 owns.

**M2.4 — Migration tool + legacy handling.**

- New small workspace binary crate reusing `switchboard_core` types for every read/write. Behavior: read the old `workspace.yaml`; for each available directory, **copy** `<dir>/.switchboard/projects/*` into the target store (attachments included, staying inside each copied project root), create catalog entries with newly-minted `directory_id`s, merge index entries stamping them, rewrite each copied journal's `Send.attachments[].path` to the new location **while setting `dispatched_path` to the original** (the correlation contract above), drop `instance.lock` files, validate (parse-clean registries/journals, id uniqueness, session-locator uniqueness), print a report. **Originals untouched by default; `--cleanup` deletes `<dir>/.switchboard/` only after successful validation.** Unavailable directories are reported and skipped (re-run later — copy semantics make re-runs safe).
- **Unsent compose drafts are deliberately *not* migrated — the frontend drops dead attachment chips instead.** A draft holds absolute paths to staged files, and it lives in the webview's machine-local storage, which a CLI tool cannot read or rewrite. So after `--cleanup` a restored draft would show a chip pointing at a deleted file and, worse, *send* successfully — handing the agent a path that no longer exists (the footer is path-in-text, so nothing downstream validates it). Rather than teach the tool about frontend storage, make the frontend tolerate a missing staged file: **on draft restore, drop an attachment chip whose path no longer exists**, with a brief notice naming what was dropped. That is correct independent of migration — a staged file can also vanish to a manual delete, an interrupted GC, or a `--cleanup` run between sessions — so it is a durability fix that happens to cover this case, not migration special-casing. The check belongs with the other restore-time reconciliation in the compose bar (alongside `reconcileForwardSources`, which solves the same "a persisted reference outlived its referent" problem for forward sources). Implemented in M2.5's frontend bullet; recorded here because the migration is what makes it load-bearing.
- **Every project the tool lands carries its owning `directory_id` in its own `config.yaml`.** `ProjectConfig.directory_id` is a recovery record: it is what lets a repair rebuild the project index and see which projects share a directory identity after `projects.jsonl` and `directories.jsonl` are lost together. Copied legacy configs arrive with the field absent (`None` — the old layout implied ownership by path), so the tool must stamp it as part of the copy, and validation must reject a landed project left `None` or disagreeing with its index entry. Nothing reads the field at runtime; a stale copy is only detectable here, which is why validation belongs in this tool rather than on the load path (a redundant copy must never be able to block opening a project that is otherwise fine). It does **not** recover `directory_id -> path` — reconstructing those paths needs the tool's own report or the user re-pointing each id.
- **An unindexed project root is always ambiguous — recovery is the default, deletion is never automatic.** A `projects/<id>/` directory with a `config.yaml` and no index row has two possible histories: an orphan from `create_project`'s documented append-failure path, or a project whose index row was lost. **Index presence does not distinguish them** — truncation at a line boundary, a partial restore, a sync conflict, or an incomplete hand edit all leave a parse-clean index missing rows. So: discover every unindexed root, parse its self-description, and present recovery or quarantine as the default; delete only on explicit per-project confirmation, showing the exact root. If the index is absent entirely, bulk reconstruction is the operation and cleanup must not run at all. This is what keeps the cleanup bullet above from firing on the same evidence the `directory_id` recovery record exists to serve — the wrong branch there deletes every project a user still has.
- **Duplicated `directory_id`s are this tool's to avoid.** The catalog is the only place a duplicate can arise (ids are minted fresh and re-points preserve them), so bulk catalog writes are the realistic source. Validation must reject a catalog with two rows for one id; a store that ships one degrades every affected project to unresolved until the user re-points it.
- **Orphan cleanup is a repair action, not a side effect.** `Store::delete_project` refuses while the index is missing, so removing a project directory whose index entry is gone belongs here: name the missing-index condition explicitly, show the exact root being removed, require confirmation, and quarantine rather than unlink where practical.
- **The tool must have exclusive use of the target store.** It is a second process writing the release store by design, and the store's index and catalog are read-modify-write files for the whole install — the app's release single-instance guard says nothing about a separate utility. Acquire an advisory lock the running app also holds (or an equivalent exclusive-use protocol) and refuse with "quit Switchboard before migrating" rather than racing it. Distinct from M2.3's session locks, which guard harness sessions, not store mutation.
- **`dispatched_path` is write-once.** Set it only where it is currently `None`. A re-run that writes the now-relocated `path` over an existing value destroys the original irrecoverably, and silently — the failure surfaces later as a duplicated transcript entry. This is what makes the required re-run idempotency actually safe.
- **Target root is an explicit `--target-root` flag defaulting to the release path, printed and confirmed before writing.** Do not resolve via `config_dir()`: a debug-built tool would silently target `switchboard-dev`, violating the migrate-to-release-only decision.
- **Startup legacy preflight (the primary trigger — existing users never re-add directories).** Keyed on **positive evidence, per legacy source**, never on absence:
  - The tool records **each migrated legacy source individually** (canonical path + the `directory_id` it was assigned), not one global "migration done" flag. A global flag is wrong in both directions, because the tool legitimately skips unavailable directories: a global flag would suppress the notice forever when a skipped directory later comes back, and no flag at all would re-warn about directories already migrated without `--cleanup`.
  - The notice shows when a known directory has a **non-empty** `<dir>/.switchboard/projects/` **and** is absent from that migrated set. Do **not** key it on "store index is empty" — that conflates "un-migrated" with "has no data," and two ordinary states satisfy it with nothing to migrate (directories added but no project ever created; a migrated store whose last project was deleted).
  - **Re-runs reuse the previously assigned `directory_id`** for an already-recorded source. Minting a fresh id on re-run would orphan the projects migrated on the first pass.
  - **No global dismissal.** The escape hatch is per-source: a "skip this directory" action writes a marker for that source, which is the same shape as a successful migration and cannot mask a different directory. Write-suppression on the old `workspace.yaml` is keyed on "any non-empty legacy source is neither migrated nor skipped" and is **not** lifted by hiding the banner — a global dismissal that resumed writes would let the app rewrite the file into its new view-state-only shape and destroy the directory paths the migration tool needs as input. Once every source is migrated or skipped, writes resume normally.
  - The notice names the tool and how to run it (`cargo run -p <crate>` from a checkout — the current handful of users all work from the repo). The old file needs no schema change to stay readable (M2.2 adds no required fields), so this is purely detection-and-hold.
- Secondary trigger: adding/initializing a working directory that contains a non-empty `<dir>/.switchboard/projects/` returns the same typed error naming the tool. No read-both-layouts fallback anywhere.

**M2.5 — Attachments, asset scope, frontend, docs.**

- **`MessageFailed` gains a cause discriminant, and policy refusals stop being classified as adapter failures.** `run_turn`'s refusal path currently fires `FailureKind::AdapterFailure` for a *policy* refusal, and `MessageFailed` carries no cause at all, so the frontend hardcodes `adapter_failure`. That deferral was proportionate while refusals were rare internal gates. M2.3 shipped one that fires during ordinary Fork use and is documented in the README as expected behaviour, so its only machine-readable signal now says the CLI crashed. Add the discriminant, branch on it in the reducer, and cover session-in-use, busy-fork-parent, and project-under-maintenance. Nothing user-visible depends on it until differentiated retry or error UI exists — which is why it is here and not in M2.3 — but that UI cannot be built without it.
- **The directory-repair affordance requires a project-scoped admission claim first.** M2.3 narrowed the lifecycle-generation race to the span between `preflight`'s check and the subprocess existing. Delete bounds that span (it awaits every actor's full stop before removing anything), so today's worst case is a subprocess that starts and is cancelled. Re-point does not bound it — a turn admitted just before would dispatch into the directory the project no longer uses — and re-point becomes reachable exactly when this affordance ships. So: a claim that turns hold from admission through spawn and that lifecycle operations wait behind, landing with the affordance, not after it. **Note for whoever builds it:** the claim is a non-`File` token, which is the recorded trigger to revisit `TurnPermit`'s deliberately concrete shape (`crates/dispatcher/src/lib.rs`) — either make the permit opaque or split admission and session permits.

- **Staging is unchanged: per-project `<store>/projects/<id>/attachments/`.** M0 cleared store-wide staging as *viable*, and the decisions section above records why it was nonetheless reversed. Nothing to build here. Antigravity needs no second `--add-dir` (M0). Fallback B (cwd-local under `.git/info/exclude`) is dead — do not carry it.
- **Reference-GC stays exactly as it is: per-project, caller-driven.** Nothing to build. A file survives if *this* project's journal or an unsent compose draft the caller declared references it; the caller must declare `draft_attachments` because drafts live in the frontend's machine-local storage and the backend cannot see them (`load_project_conversation_impl`'s doc comment states the contract). Project delete remains `remove_dir_all` on the project root, which takes the attachments with it — no sweep, no reference analysis, no way for a delete to reach another project's files.

  **Recorded because it was nearly given up:** the store-wide design required replacing this with an all-projects sweep — fail-closed on any journal read error, run once per session and on delete, with the frontend declaring every project's drafts in one call. That is materially more machinery in the one operation whose bugs destroy user data, and the reversal above is what avoids it. If store-wide staging is ever revisited, that sweep and its two postures (fail-closed on read error; unlink failure warns but never fails a load) come back with it.
- **Webview asset scope** (`crates/app/tauri.conf.json`, `assetProtocol.scope`): the current glob is `**/.switchboard/projects/*/attachments/*`, which the new layout no longer matches — without this change every attachment thumbnail silently renders broken, and **no automated suite can catch it** (every frontend test mocks `convertFileSrc`; Rust live tests prove the *agent* reads the file, not the webview). New scope: `**/store/projects/*/attachments/*`, which covers both roots (`switchboard` and the `switchboard-dev*` per-port variants `make dev` generates) without enumerating them, and is no broader than the old glob — one path segment substituted, the `projects/*/attachments/*` tail unchanged. Record that reasoning here and in the commit message, since JSON carries no comments.
- **The repair affordance and its copy.** All three failure states are repairable from the project row; the UI must state that a repair moves **every** project sharing that directory before the user confirms (`ProjectListing.directory_id` is what makes the sibling set computable). Decide the copy per state — `resolved_path_unavailable` and `catalog_ambiguous` are re-points, `catalog_missing` is a bind — and decide what the user sees after hiding the directory they are currently working in (today the view clears; keeping them on it needs the active project tracked separately from the filtered list).
- Frontend: copy in `CreateProjectForm.svelte` / `WelcomeScreen.svelte` (no more "creates a `.switchboard/` folder"); `workspace.svelte.ts` remove→hide semantics; the FE project-list model already carries a directory label and needs only the availability-meaning update. **Restored compose drafts drop attachment chips whose staged file no longer exists** (per M2.4's decision above) — one existence check per chip at restore, mirroring `reconcileForwardSources`' posture of pruning a persisted reference whose referent is gone rather than carrying it to a failing send.
- Docs: system-design §3 directory-layout section rewritten (the "self-contained directory travels with its repo" framing is replaced by "store is user-global; the catalog maps id→cwd"); AGENTS.md cross-cutting-invariants filesystem bullet; README gains a migration note.

### Definition of Done

- Core `Store` tests port the `Directory` suite's crash-consistency cases (orphan dir on failed append, config-ahead-of-index on failed rename, delete idempotency, corrupt index/catalog surfacing fail-loud — **not** empty-and-overwrite) — these encode the atomicity contracts and must not be dropped in the port.
- App tests: project CRUD + open/lock against a temp store root; missing-directory project still lists/renames/archives/deletes and refuses dispatch with a clear error; re-point path restores dispatch; dangling `directory_id` surfaces cleanly; `agents_by_id` cross-project conflict surfaces typed; **upgrade-without-migration launch shows the notice and leaves the old `workspace.yaml` byte-identical**; **a workspace with directories but zero projects launches clean (no notice)**, as does a post-migration store whose last project was deleted; a per-source skip persists across launches and suppresses only its own source; legacy add-directory refusal.
- Session-lock tests (against an injected temp lock root): contention refuses the turn pre-spawn; lock-dir I/O failure refuses (not warns); hostile/oversized Codex thread id yields a valid fixed-length path; Claude same-uuid-different-cwd does *not* contend; **a materializing fork contends on its parent's key** — including when the parent is **idle** and when the parent agent has been **deleted**, the two cases `busy_fork_source` reports as safe (regression for deriving the key from the wrong source) — and releases both; guard released on completed, failed, cancelled, and drained turns.
- Migration tool: integration test migrating a fixture old-layout tree (2 directories × 2 projects, attachments, sidecars) into a temp store root — ids/timestamps/locators preserved, attachment `path` rewritten with `dispatched_path` preserved, originals untouched, report accurate, re-run idempotent **and reusing the recorded `directory_id`**; `--cleanup` only after validation. Skipped-source lifecycle: an unavailable directory is skipped and recorded as *not* migrated → still notices later when it returns; a migrated-without-`--cleanup` directory does **not** re-notice; a per-source skip suppresses only that source; `workspace.yaml` writes stay suppressed while any source is unresolved and resume once all are migrated-or-skipped.
- Correlation regression: a migrated attachment-bearing `Send` still exact-matches the harness-recorded footer text through `dispatched_path`.
- `list_project_agents_readonly` resolves a roster from the project id alone — no directory argument anywhere in the chain — with the frontend exact-payload-key assertion updated to match (the guard that caught the last wire-signature drift).
- A restored draft whose staged attachment file has been deleted drops that chip and notices it, rather than sending a path the agent cannot read.
- GC: no new tests — the existing per-project suite still covers the shipped behaviour (keeps a file referenced only by an unsent draft the caller declared; removes orphans). The store-wide cases drop out of scope with the reversal.
- Live: attachment tests re-pointed at the new staging location pass for all three harnesses (`make test-live` before merge — adapter-relevant change).
- **Manual verification (required — no automated coverage exists):** run the app, drop an image attachment, confirm the thumbnail renders in the transcript; repeat in a `make dev` instance (dev-root scope variant).
- `make check` green. Known limitation recorded in plan-completion notes: archived-ness and the store are per-install (unchanged posture, now global).

## M3 — Duplicate setup (agent and project)

### Goal & Outcome

- **Duplicate agent setup into…**: from an agent's row actions, pick a target project (any project, any directory — fresh sessions have no cwd coupling); a new agent appears there with the same name (disambiguated on collision), harness, model, effort, and profiles, a **fresh session**, and empty history.
- **Duplicate project setup**: from a project's row actions; a new project (name disambiguated, e.g. `-copy` suffix under the existing name-validation charset) in a chosen directory, containing setup-duplicates of every agent.
- UI copy must say "setup" and make "starts a fresh conversation" explicit — the vocabulary decision exists to prevent the user expecting history to come along.

### Implementation Outline

- Core: one new `Project` registration path that takes a source `AgentRecord` and re-mints identity — new `AgentId`, fresh `session_locator` per the harness's existing rules (Claude pre-generates a UUID; Codex/Antigravity `None` until runtime capture), `forked_from_session: None` (this is not a fork — no conversation lineage, so recording provenance would be a lie). Copies: name (disambiguated via the same canonicalized-uniqueness walk `derive_fork_name` uses — reuse/generalize that helper rather than inventing a second disambiguator), harness, model, effort, profiles. Copies nothing else. **Explicitly not copied** (state this in the method doc): journal, pins, sessions sidecars, attachments, runs, queued work, pane layout (frontend view-state; a follow-up if ever wanted — do not build it now).
- Rationale to record in the code (method doc): duplication mints fresh sessions because (a) shared locators violate the same-session-parallel-invocation guard, and (b) history-carrying duplication is not uniformly implementable across the three harnesses (fork asymmetry, harness-behavior §3.5) — a Claude-only history clone was considered and rejected as a non-uniform surface.
- Project duplicate composes: create project (existing path) + duplicate each agent into it. Per-agent registration is append-based and already serialized under `registry_write`; a mid-way failure leaves a valid partial project — surface the error, leave the partial (consistent with the codebase's no-destructive-rollback posture), and say so in the error copy.
- App/frontend: two commands; the target-project picker reuses M1's read-only-roster / activate-on-pick split; row actions follow the existing inline hover-revealed convention.

### Definition of Done

- Core tests: duplicate re-mints id + locator; profiles/model/effort copied; name collision disambiguates; Codex/Antigravity duplicates start locator-less; duplicating into the same project works (it's just "copy this agent's setup").
- App test: project duplicate with a mixed-harness roster; partial-failure leaves a valid, listable partial project.
- Component tests: picker flow (browse does not activate; pick does); the "fresh conversation" copy is present (asserting copy exists is cheap insurance on the vocabulary decision).
- Docs: system-design §3 project-lifecycle list gains duplicate; README one-liner ("duplicating copies setup, not conversation history — history can't be copied uniformly across harnesses" — user-facing phrasing per the README's rules).
- `make check` green.

## M4 — Move agent between projects (same working directory)

### Goal & Outcome

- From an agent's row actions: **Move to project…**, offering only sibling projects (same `directory_id`). The agent — same identity, same session, full history *including pinned messages* — now lives in the target project: its transcript renders there (past failed/cancelled markers included), and its next turn dispatches and journals there. **Attachment images from before the move do not survive it** — see the accepted limitation at the head of this milestone.
- Refused unless **both projects are fully quiescent**: no turn in flight and no queued sends for *any* agent in either project, and no active workflow run in either project. Running work is never cancelled to make a move happen — the move refuses and the user retries when things are idle.
- During the (brief) surgery, both projects refuse new turn starts; afterwards everything resumes normally.
- The source project's transcript no longer shows the moved agent's turns; its pins on that agent's replies move too.
- If the app crashes mid-move, the next launch completes the move automatically before either project opens — the user sees a finished move, not a half-moved agent. Any anomaly that somehow escapes recovery is surfaced on open, never silently resolved.

### Implementation Outline

This is the riskiest milestone — it performs multi-file surgery on state that other agents write concurrently. The hazards below came out of discussion and review; each needs deliberate handling, not incidental behavior.

**A move does not touch attachment files, and that is an accepted limitation rather than a solved problem.** Attachments are per-project (see the attachments decision above, which reverses an earlier store-wide design). A move rewrites journals — the moved agent's records leave the source and are appended to the target — so the source project's reference-GC finds the agent's staged files unreferenced and collects them on its next project load. `Send.attachments[].path` is **not** rewritten, so send↔turn correlation is unaffected; only the file goes.

The user-visible result: a moved agent's older attachment thumbnails render broken, and asking it to re-read one of those files gets a file-not-found from the agent. Neither corrupts history, and neither affects any turn that does not reach for an old attachment. **This must appear in the README's limitations list when Move ships** — it is a "why doesn't this work" a user will hit, and it is a Switchboard limitation, not a harness one, so lead with the symptom.

If it proves annoying, the mitigation is recorded in the attachments decision: have the move copy referenced files into the target and rewrite `path` while preserving `dispatched_path`, the way migration does. Do not build it pre-emptively.

- **Quiescence gate — both projects, not just the moved agent.** Journal appends (`ProjectJournal::record_send`/`record_outcome`) take no shared lock: any agent in either project completing a turn while the move rewrites a journal file would have its record silently lost to the pre-rewrite copy. So the gate is:
  1. A per-project maintenance flag, checked in **all three** places the mid-turn fork gate checks — `send_message_impl` (send admission), the workflow-step preflight in `workflow.rs` (workflow admission), and **`DispatchContextFactory::preflight` (authoritative turn-start)**. The third is not optional and not redundant: without it there is a check/enqueue race — a send passes admission, the move then sets the flag and observes an empty queue, and the send lands in the queue afterward and starts mid-surgery. Closing exactly that race is the documented purpose of the start-moment preflight ("the caller's pre-enqueue check answered a question that may have gone stale while this item sat in the backlog… it bounds that queue race"), so it is the one check that must not be skipped. Refusal there leaves no durable trace, which is the behavior a blocked turn wants.
  2. The move refuses unless both projects have zero in-flight turns, zero queued sends, and zero active workflow runs — the workflow condition matters because a run can hold a *future* step targeting the currently-idle agent.
  3. Flags are set for both projects *before* re-verifying quiescence (closing the check-then-act window), and are cleared **only on successful completion of the move or of a recovery** — never on an arbitrary error path, which would re-enable dispatch into half-moved state (see the recovery bullet: a failed recovery deliberately leaves both projects blocked).

  Record the rationale: the gate exists for the *other* agents' journal writes, not the moved agent's.
- **Identity**: the `AgentId` and `session_locator` are kept (it's a move). `project_id` changes via a new dedicated `Project`/registry method, following the existing mutate-in-place-then-recache convention (`rename_agent` precedent) — `AgentRecord`'s doc comment currently declares `project_id` immutable; update it to name this method as the single sanctioned mutator.
- **Crash recovery: a durable move-intent record plus idempotent steps.** A first draft of this plan relied on "each file write is atomic, so re-running the move heals." That is **false**, and the reasoning is worth recording because it is the trap: individually atomic writes do not make a multi-file operation atomic, and "single-process" says nothing about what happens *after* that process dies. Concretely — a crash before the commit point makes a re-run re-append already-copied journal records (duplicate messages in the target); a crash *after* it leaves journal/pin/sidecar residue in the source with **no trigger to ever finish**, because the agent row you would re-run the move from now lives in the target; and the open-time conflict check could itself block opening the project the repair needs. So:
  - **Intent record**: before any surgery, write one small durable file naming `{agent_id, source_project, target_project}` under a `moves/` directory, **one file per move** (never a fixed name — the quiescence gate is per-project and does not stop two moves across *different* project pairs from clobbering a shared filename). Delete it after the last step. It records *what* is in flight, not how far it got. Recovery drains every file in the directory.
  - **Idempotent steps**: every step is written so re-running it is a no-op when already applied (append only what the target lacks; rewrite-without-X is naturally idempotent; sidecar/pin moves check existence). The journal dedup key is **`(variant tag, turn_id)`** — every current `JournalRecord` variant carries a `turn_id` and there is at most one of each per turn, which is what makes "append only what's missing" implementable. `JournalRecord` is `#[non_exhaustive]`; state this key explicitly so a future variant without a `turn_id` is forced to define its own identity rather than silently duplicating. Because every step is idempotent, **no phase tracking is needed** — recovery re-drives the whole sequence.
  - **Startup recovery** runs before either named project opens (and therefore before the conflict check can wall it off), completing the move from whatever state it finds. This ordering is load-bearing — state it in the code.
  - **In-app failures use the same machinery — the intent record is not crash-only.** A filesystem error mid-surgery must not fall through to the ordinary error path, because that clears the maintenance flags and lets dispatch resume against half-moved state. So: a **process-wide move mutex** serializes moves (they are rare and user-initiated; serializing costs nothing and removes the concurrent-move question entirely); and once the intent record exists, **any** failure triggers immediate in-process recovery **while both projects remain blocked**. If that recovery also fails, the two projects stay blocked with a distinct repair-required error naming the intent file — the app does not silently re-enable dispatch into an inconsistent pair. A startup recovery that fails does the same: those two projects refuse to open, everything else works, and the next launch retries. Scope the blocking to the two named projects only, never the whole app.
  - Keep the ordering appends-before-rewrites, target-before-source: (a) append moved records to the **target journal**, (b) copy sidecars, (c) append to the **target registry**, (d) rewrite the **source registry** without the record — the commit point — (e) rewrite the **source journal** without the moved records, (f) move pins, (g) remove source sidecars.
  - M2.2's `agents_by_id` conflict check remains as the belt-and-braces detector for anything recovery somehow misses (e.g. an intent file lost to disk failure) — it must surface, never silently pick one.

  This is a bounded mechanism — one file, existence checks, one startup pass — not a transaction framework, and it is earned by the milestone's full-history promise.
- **Journal surgery**: the moved agent's `Send` / `Outcome` / `TurnLink` records move via `switchboard_core::journal` types — never string-level line filtering — preserving original order and timestamps. Why move rather than leave-and-treat-as-attach: leaving records behind loses failed/cancelled outcome markers and leaves the source journal referencing an agent its registry no longer has. Edge: a fan-out `send_id` that included the moved agent and others now spans two journals — each project renders its own copy grouped by `send_id`, which is correct per-project behavior; note it in the method doc so nobody "fixes" it into cross-journal dedup.
- **Pins move with the agent.** Pin keys embed identity (`agent:send:<send_id>:<agent_id>` — see `src/lib/messageIdentity.ts`): pins whose key carries the moved agent's id move to the target's `pins.jsonl`; `user:send:<send_id>` pins move only when the send moved entirely (the moved agent was its sole recipient) and otherwise stay in the source (the user's message legitimately still renders there for the remaining recipients); keys that don't parse under the known format are retained untouched (forward compatibility). **The move partitions pins; it does not prune them.** An earlier draft pruned pins pointing at rows no longer present — that is unsafe and unnecessary: a missing or transiently unresolvable session file degrades to an *empty* transcript rather than an error (`load_transcript_impl`), so "no row" is not evidence the pin is dead, and a prune run during a move would silently destroy an agent's entire pin set with no undo. Orphan pins are inert — one line in `pins.jsonl`, rendering nothing. If orphan cleanup is ever wanted it is its own change, gated on a *successful* transcript load. The key-partitioning helper lives **app-side**, mirroring `messageIdentity.ts`'s format — core is not taught pin-key semantics. Record the user-pin asymmetry in the same method doc as the `send_id`-spans-two-journals note.
- **Sidecars**: `sessions/<agent-id>.meta.json` / `.turnmeta.jsonl` move with the agent (paths are project-root-derived).
- **Dispatcher/actor lifecycle**: the per-agent actor's dispatch-context factory captures the owning project at actor creation — after a move it would journal into the *old* project. Under the quiescence gate, shut down the agent's actor via the existing drain machinery (`drain_agents_then_release_locks` path; draining an idle actor cancels nothing) before the file surgery; the next send lazily recreates the actor against the new project. Verify against the actual actor-creation code; if the factory turns out to read the project live, the drain is still the safe choice — say so in a comment rather than relying on the subtlety.
- **Operation ordering overall**: gate + verify quiescence → drain the moved agent's actor → surgery in the commit order above → update `agents_by_id` and both projects' in-memory state → clear maintenance flags → emit whatever refresh events the existing agent-remove/register paths emit. `registry_write` held where the existing conventions demand it (no `.await` under the guard — the drain happens before taking it).

### Definition of Done

- Concurrency tests: a turn completing for a *different* agent in the source project during a gated move → its journal record survives (regression for the append-loss hazard; fails without the gate); dispatch attempts against either project during surgery are refused with the maintenance error; move refused for in-flight / queued / active-workflow in either project.
- Recovery tests — **injected failure after every step** (a)–(g), run twice: once as a *crash* (recovered at startup) and once as an *in-app error* (recovered immediately with both projects still blocked). Each asserts: recovery completes the move, the result is equivalent to an uninterrupted move, and no journal record, pin, or sidecar is duplicated. Plus: recovery runs before either project opens; a second pass over an already-complete move is a no-op; recovery failure leaves exactly the two named projects blocked with the repair-required error while other projects open normally, and retries next launch; two intent files in `moves/` are both drained; the `agents_by_id` conflict check still surfaces typed if an intent record is missing entirely (the belt-and-braces path).
- Race test: a send admitted just before the move sets its maintenance flag is refused at turn start rather than running during surgery (this is what the `DispatchContextFactory::preflight` check exists for; it fails if the check lives only at admission).
- Core tests: journal filter/append round-trip preserving order and timestamps; step idempotence in isolation (re-applying each step changes nothing); pin partitioning (agent-reply pin moves; fan-out user pin stays when recipients remain, moves when sole-recipient; unparseable key passes through; **pins are never deleted** — including when the agent's transcript loads empty); sidecar relocation.
- App tests: post-move dispatch journals into the target (regression for the stale-factory hazard — fails if the actor isn't recreated); source transcript excludes, target includes, the moved history through the real hydration path (the merge partitions on journal contents); moved attachment-bearing turns still render and still correlate (paths unchanged by design — assert exactly that).
- Component test: the move picker offers only same-directory siblings; a second move attempt while one is in progress is refused (the move mutex).
- Docs: system-design §3 agent-lifecycle note; README line for the user-visible rule ("agents can move between projects in the same folder; moving across folders isn't supported because two of the harnesses tie a conversation to its folder").
- `make check` green.

## Deferred / out of scope (recorded so they aren't re-derived)

- **Cross-directory agent move** (all harnesses): Claude would require writing into the harness's private session store with falsified per-record `cwd` fields; Codex/Antigravity would work but shipping a harness-conditional move surface isn't worth it yet.
- **History-preserving clone**: not uniformly implementable (fork asymmetry); revisit only if Codex's app-server fork gets wired.
- **Restoring Gemini** (M0.5): only if an eligible account exists *and* someone can run `make test-live-gemini` against it. Re-adding an adapter nobody can exercise recreates exactly the liability M0.5 removed. Note two things would need re-probing first, both recorded in `harness-behavior.md`: the §3.7 out-of-cwd attachment row (never established for Gemini) and the §5 trusted-folders gate that silently downgrades `--yolo`.
- **Per-message forward** from transcript rows: different data contract than latest-output forwarding.
- **Forwarding from unavailable-directory projects**: becomes possible post-M2 (journal is central, harness files are under `~`); enable only if wanted — the M1 available-only filter is one predicate.
- **Pane-layout duplication** in M3.
- **Phase-tracked / rollback-capable move recovery for M4**: the *phased* form was considered and rejected — with idempotent steps there is nothing for phases to buy. What is **in** scope (see M4) is the minimal form: one intent record + idempotent steps + a startup completion pass. The earlier "no durable recovery at all; re-running heals" position was **wrong and is not to be reinstated**: individually atomic writes don't make a multi-file operation atomic, and a crash after the commit point leaves source-side residue with no trigger to finish it.
