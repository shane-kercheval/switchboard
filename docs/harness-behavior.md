# Harness behavior & Switchboard handling — canonical reference

The single lookup surface for **how each harness behaves in the scenarios Switchboard cares about, how our adapter/frontend currently handles it, and where the gaps are.** Built 2026-05-27 from a code+research audit of all adapters and the frontend.

**How this relates to the other docs:**
- **system-design §9** is the *design-level* capability matrix (native / derived / unavailable per capability) and the process model. It stays the canonical design statement; this doc is the *operational* companion (observed shapes → our handling → gaps).
- **`docs/research/archive/<harness>-cli-observed.md`** are the *captured-in-time provenance* — the raw probes (actual strings, exit codes, fixtures) behind the cells here. They are frozen (no longer updated) and live under `research/archive/`; treat **this** doc as the lookup surface and the archived `-observed` files as the evidence it cites: [claude](research/archive/claude-code-cli-observed.md), [codex](research/archive/codex-cli-observed.md), [gemini](research/archive/gemini-cli-observed.md), [antigravity](research/archive/antigravity-cli-observed.md).

>
> **Gemini CLI support was removed on 2026-08-27.** Google withdrew Gemini CLI access for individual accounts (see **G26**), which made the adapter impossible to exercise — neither `make test-live-gemini` nor a manual check could run — so the adapter, its tests, and its frontend surface were deleted. Switchboard supports **three** harnesses: Claude Code, Codex, Antigravity.
>
> **Gemini rows, gaps, and sections below are retained as history, not as current behavior** — the same treatment this doc gives resolved gaps and superseded probes. Read any Gemini cell as "what was true when the adapter existed." Do not treat them as describing shipping code. If Gemini support is ever restored, two things are *unestablished* and must be probed first: its §3.7 out-of-cwd attachment behavior (never measured) and whether the `--skip-trust` the adapter passed still fully answers its workspace-trust gate (§5).

**Legend:** ✅ handled correctly · ⚠️ partial / stale · ❌ gap. "Displayed where" distinguishes the **transcript** (per-turn) from the **sidebar** (per-agent) from a **project banner** (startup auth probe).

## 0. Claude slash-leading messages

For a Claude agent, an ordinary Switchboard send always targets the model. The prompt picker still opens when `/` is typed into an empty composer; its literal fallback inserts `/<query>` into the message rather than dispatching or discarding it. The fallback is absent when the toolbar opens the prompt picker, because that path has no user-entered slash to reconstruct. Paste and every other edit path can also create the same draft, so the correctness boundary is dispatch, not keyboard handling.

Claude Code 2.1.223 intercepts some bare slash-leading `-p` positionals locally (`/plugin`, `/context`, and unknown single-token commands) and emits a zero-token assistant envelope with `message.model:"<synthetic>"` and no text deltas. Switchboard therefore prefixes one transport-only ASCII space to every Claude prompt whose first character is `/`; the journal/transcript keep the exact user text. This was live-verified with `/plugin`, while path-shaped inputs such as `/shanekercheval/path/to/something` already reached the model without the workaround. The tradeoff is deliberate: user-invoked Claude skills, custom commands, and MCP prompts are also bypassed through the ordinary composer and require a future explicit command action. Codex treats the tested inputs as model text. Gemini retains its native headless command preprocessing.

**Antigravity changed sides @ agy 1.1.11/1.1.12** — it now answers read-only slash commands in print mode instead of passing them to the model, so a user message beginning `/usage`, `/context`, or similar would have been silently intercepted and answered by the CLI. Switchboard opts out structurally rather than by escaping: every Antigravity dispatch passes **`--disable-slash-commands`**, which restores "the user's text is model text" unconditionally. That is a stronger guarantee than Claude's space-prefix workaround, and it needs no per-prompt inspection. The trade is the same one Claude makes: user-invoked Antigravity slash commands are unreachable through the ordinary composer and would need an explicit command action. Antigravity keeps its own separate flag-shaped-prompt guard — a prompt that is *exactly* a flag name (`-p`, `--model`) is rejected by `agy`'s arg parser before dispatch, so the adapter prefixes one transport-only space to any prompt whose first character is `-`.

Defense in depth: a non-error Claude `<synthetic>` envelope is still valid harness-authored output. The live parser emits its text blocks directly (normal model envelopes remain delta-only to avoid duplication), announces the envelope's `message.id` immediately like any other assistant response, and filters `<synthetic>` out of model metadata. Authentication-failure synthetic envelopes remain on the authored `AuthFailure` path and never double-render their raw text. Separately, the session parser reconstructs only structurally linked `sdk-cli` `system/local_command` input/output pairs and ignores interactive `cli` output. That compatibility/recovery reader serves pre-escape Switchboard history, attached SDK-created sessions, and unexpected future interception; its output-record UUID is disk-stable but intentionally not live-matched, so those turns correlate positionally.

## 1. Failures

Each turn ends in exactly one terminal outcome: `Completed` · `Failed { kind, message }` · `Cancelled { source }`. `kind ∈ { HarnessError, AdapterFailure, AuthFailure }` (`crates/harness/src/events.rs:347`, `#[non_exhaustive]`). **There is no `UsageLimit`/quota kind.**

### 1.1 Turn-completion detection

| Harness | Signal | Detection |
|---|---|---|
| Claude | `result` event, `is_error:false` | `claude_code/parser.rs:parse_result` ✅ |
| Codex | `turn.completed` | `codex/parser.rs:parse_turn_completed` ✅ |
| Gemini | `result.status:"success"` **OR** (`result.status:"error"` + answer streamed this turn + benign trailing-error signature) | `gemini/parser.rs:parse_result` / `classify_result_failure` ✅ |
| Antigravity | process exit **+** terminal `PLANNER_RESPONSE` answer in `transcript.jsonl`, with the control stream's `result` event as the verdict. Exit status varies by failure shape and is deliberately unused for classification (see §1.2) | `antigravity/parser.rs:is_terminal_answer` + `stream.rs` `result` + `classify_outcome` ✅ |

**Gemini streamed-then-error rescue (G17).** Gemini frequently appends an empty/malformed trailing step *after* it has already streamed a complete answer, tainting `result.status` to `"error"`. When answer content streamed this turn AND the failure carries the benign signature `"empty response or malformed tool call"` (matched on the distinctive tail phrase, case-insensitive — not the generic "invalid stream" prefix), the turn is reclassified `Completed`. The match is narrow and fails safe: signature drift sends such turns back to FAILED, never the reverse. See §1.2 and G17.

**Antigravity's backend fails turns transiently (observed 2026-08-29 @ agy 1.1.22).** A dispatch that should have produced a tool error instead terminated with `TurnEnd(Failed { HarnessError })` carrying **`"Agent execution terminated due to error."`** — a generic server-side message with no `Error:` detail and no tool events at all. The adapter classified it correctly; nothing is wrong on our side. It is recorded because the failure is **indistinguishable from a behavioral regression** when it lands on a live test: it surfaced as `live_antigravity_invalid_file_read_completes_as_tool_error` failing, which reads exactly like the adapter having stopped surfacing tool errors. Two immediate re-runs passed. Observed **once**, so no rate is claimed — but if a live Antigravity test fails with this message, re-run before investigating the adapter, and treat a *consistent* failure as the real signal. `agy` is a thin client to a server-side agent (§3.5, G15), so transient backend errors are structurally expected in a way the local-process harnesses' are not.

**Gemini message capture (G17).** The terminal `result.status:"error"` line frequently has **no** `error` field at all. The real reason rides a separate top-level `type:"error"` event one line earlier; the parser now captures it (`last_error_message` on `GeminiParserState`) and falls back to it, so a failed Gemini turn surfaces a real message (was empty before). The same captured signature drives the streamed-then-error reclassification (§1.1). **RESIDUAL RISK:** a turn that genuinely failed *after* streaming only partial content, emitting this same benign signature, would be shown as success — accepted trade vs. a misleading FAILED chip on every other complete turn. See `gemini/parser.rs`.

**Uniform authored auth messages (cross-cutting).** Every adapter authors its `AuthFailure` message — naming the harness and the recovery command — instead of surfacing the raw harness text (`"401 Unauthorized"`, `"Please set an Auth method"`, `"Not logged in · Please run /login"`). The user sees one consistent actionable line regardless of which harness's auth surface fired. **None mention "reload Switchboard"** — reactive-auth posture: discover on send, sign in, send again. Constants: `CLAUDE_AUTH_MESSAGE` / `CODEX_AUTH_MESSAGE` / `GEMINI_AUTH_MESSAGE` (`parser.rs` / `codex/parser.rs` / `gemini/parser.rs`); `ANTIGRAVITY_AUTH_MESSAGE` (`antigravity/mod.rs`).

**Reactive-only auth (working UI).** Auth has exactly one user-facing surface in the working UI: a failed turn in the transcript carrying the authored message. There is no proactive startup probe, no project-level "X not authenticated" banner, no per-agent status icon, and no agent-creation auth gate. A logged-out harness is discovered when the user sends to one of its agents; sign in, send again. This is the same path for "never tried" and "tried and failed" — one mental model, nothing to go stale. The backend `check_*_auth` Tauri commands feed the getting-started surface (no-project state), not the working UI.

**Proactive status (`HarnessStatusList`, two opt-in placements).** Install/auth status is shown proactively in exactly two places — the **no-project orientation surface** and a **Settings → "Supported CLIs"** section — both rendering the shared `HarnessStatusList`. Per harness it shows install status (present-on-PATH + version, via `get_harness_install_status` over the trait `HarnessAdapter::version()`) and a best-effort auth ✓/✗ (the four `check_*_auth` probes, including the Claude keychain probe). All four harnesses are uniform ✓/✗ — no "unsupported"/"?" case. The auth marks are **presence heuristics, not validity checks** (the authoritative test is a successful send); a ✗ never blocks anything, and an API-key user may show ✗ yet send fine. Probes refresh on mount and on window refocus (`visibilitychange`), so both placements stay current and neither reintroduces the removed interruptive/stale mid-work banner. **Detection is only as good as the PATH behind it, and that PATH is resolved asynchronously.** A GUI launch inherits a PATH too minimal to find any harness CLI, so Switchboard reads the user's login shell once per launch; nothing blocks on that read (an earlier design did, and froze turn dispatch for its whole timeout). Every install status therefore carries a `path_source` — `capturing` (the read is still in flight, so this answer is provisional), `login_shell` (final), or `fallback` (the read failed; detection is running against the process PATH widened with well-known install directories, so a CLI installed elsewhere may read as absent). The read runs the login shell interactively with job control disabled (`+m -ilc`, for shells that accept `+m`): the capture lives in its own process group, and an interactive shell whose group is *background on a controlling terminal* suspends itself waiting to be foregrounded — so a terminal-launched app (`make dev`, running the binary by hand) would otherwise hang every capture to its timeout and land on `fallback`, while a Finder/Dock launch (no controlling terminal) never hits it. `tests/path_capture_pty.rs` pins this with a real pty. A *negative* `capturing` result renders as “Checking…” rather than a confident “Not installed”, and a backend event re-probes every surface once the read settles; a positive one is trusted, since finding the CLI already proves it exists. A `fallback` result is a real answer, not a provisional one, and the list says so in product terms rather than asserting absence. 

**Refresh** (a button on both placements; internally a *recheck* — stronger than the ordinary refresh, which re-probes against the PATH already held) discards the cached PATH and re-reads it — the only in-app recovery from a read that failed at launch, which previously stuck until the app was relaunched. The note under the list speaks only when something is wrong (the re-read could not run, the PATH degraded to fallback *and* a CLI reads as missing, or the read is still in flight); a healthy list renders no explanatory copy, and a stale failure note is cleared by the next completed read's event. **A check that could not run is `probe_failed`, not “not installed”** — gating still fails closed, but no surface tells the user to install a CLI we merely failed to reach. Scope, precisely: this covers the status *call* failing (an IPC/join error). A binary that simply cannot be resolved on the PATH is still reported as absent — the backend collapses adapter probe errors into `installed: false`, and modelling `installed | missing | probe_failed` end-to-end is a pending follow-up. Auto-create waits (briefly, bounded) for a settled PATH before seeding a new project, and says so if it had to seed without one. The **version** is the parsed semver token (`subprocess::parse_cli_version`), not the raw `--version` line (CLIs pad differently: `2.1.156 (Claude Code)`, `codex-cli 0.134.0`, bare `0.44.0`); **no "update available" detection** — the CLIs self-update/notify, and a remote latest-version comparison is external-data-currency burden (§37) we don't take on. The "fix" hints name the **verified** recovery command per harness (`claude auth login`; `codex login`; run `gemini` / `agy`, which have no login subcommand). Caveat parity with the reactive probes: Claude's keychain presence heuristic is macOS-only and can false-positive on a stale entry (as Codex's `auth.json` check already does).

### 1.5 Cancellation

Uniform and correct across all four: token-driven (`select!`), adapter kills its process group and ends the stream with **no** terminal event, dispatcher synthesizes `Cancelled { source }`. Codex/Gemini/Antigravity all exit 0 on SIGTERM, which the token path correctly sidesteps. ✅ (each has a `live_<harness>_cancel_*` test).

### 1.6 Adapter / parse failure

All four synthesize `AdapterFailure` for malformed JSON, stdout read errors, and EOF-without-terminal (with the stderr tail appended); the frontend `heartbeat_timeout` path also synthesizes one. ✅ Gemini-logged-out and Antigravity-quota used to mis-land here; both now route to their correct `AuthFailure` / `HarnessError` classifications with authored messages (see G1/G2 in §4 — closed).

## 2. How failures surface in the UI (cross-cutting — the biggest finding)

**`error_kind` is carried to the frontend but read by zero components.** The Rust classification (`AuthFailure` vs `HarnessError` vs `AdapterFailure`) flows through `reducers.ts` into `Turn.error_kind` — and `UnifiedTranscript.svelte` renders *every* failed turn identically: the verbatim `turn.error` message in red (`text-status-failed`) + a "failed" `StatusChip`. This is by design now: a per-kind render would split the auth surface across two places (transcript + something else), reopening the disjoint-surfaces problem we just removed. The classification is still wire-carried (kept for future retry-policy decisions); the lever is the *message*, not the render.

**"Transcript disappears" when unauthenticated:** under reactive-only auth, an unauthenticated harness writes no session file, so hydration shows zero turns (correctly empty); the user discovers the auth state by sending, at which point the transcript renders the failed turn with the authored message. No banner stacks above to compete with the transcript content. The empty body is just the no-history state, not a "something is wrong" signal.

### 3.1 Event ⟂ on-disk parity (what survives restart)

For metadata-flavored fields, where a datum lives determines whether Switchboard can re-show it after the app restarts. The TUI never has this question — it doesn't restart mid-session — so any field Switchboard loses on restart is a **TUI-parity gap**. Four classes:

| Class | Meaning | Restart behavior |
|---|---|---|
| **A. Full parity** | Stream + harness session file agree | ✅ Survives — re-read from session file |
| **B. Disk-canonical (we enrich)** | Stream lacks it; session file has it; we re-read at turn-end | ✅ Survives — same source on rehydrate |
| **C. Stream-only, in-memory** | Lives in events; no on-disk equivalent; held in `Runtime` per agent | ❌ **Lost** until next event |
| **D. Absent everywhere** | Not in stream, not on disk, not in any harness file | — Impossible — TUI parity ceiling (workaround at best) |

| Field | Claude | Codex | Gemini | Antigravity |
|---|---|---|---|---|
| Assistant text / tool calls / per-turn final usage | A | A — both rollout generations (`history_mode` legacy *and* paginated; the paginated `item_completed` channel is read since G30 closed) | A (B for read-tool output) | (file is the only source — A by construction) |
| `rate_limit` snapshot | **C** | B (session file) | — (none emitted) | D (CLI log only) |
| Overage flag (`isUsingOverage`) | **C** | n/a | n/a | n/a |

**Persisted tool failure signals (Codex / Antigravity).** Live streams use structured fields where available: Codex reads the streamed command `exit_code`, and Antigravity uses `status:"FAILED"` when the transcript reports it. Durable records can lack those fields. Legacy Codex `function_call_output` strings carry `Process exited with code <n>` before the `Output:` body; 0.144.3's `exec` wrapper instead carries an array of text blocks headed by `Script completed` / `Script failed`, and may include the nested command result as compact JSON. The parser handles the legacy header and `Script failed`; it reads a full-result JSON `exit_code` only when the wrapper structurally decodes as one static shell call whose complete result is printed. Multi-call, mixed, and dynamic wrappers remain generic and do not borrow a nested command's status. When generated wrapper code prints only `result.output`, the rollout contains no exit code and a failed shell command can rehydrate as successful even though the live row was correct. Explicit structured result status always outranks these format-sensitive fallbacks — `patch_apply_end.success` on legacy rollouts, and on `history_mode: paginated` rollouts (Codex ≥0.148) the `item_completed` items, whose `CommandExecution` carries a **first-class integer `exit_code`**. Scope that precisely: **where a `CommandExecution` child is emitted**, its structured status/exit code decides and the sniff never runs. Two residuals keep the fallback load-bearing even on paginated threads — an operation that emits *no* child (a failed `apply_patch` does exactly this) still has the wrapper output as its only failure evidence, and a failure the wrapper script **catches** is unrecoverable on every path (G30). Legacy threads keep the sniff throughout, by design: the structured shell record does not exist there. Antigravity `RUN_COMMAND` records can likewise report `status:"DONE"` even when the wrapper says the command failed, so its parser reads `The command failed with exit code:` only before `Output:` / `Stdout:` / `Stderr:`. Free-text matches inside command output remain ignored to avoid false positives. Re-probe on CLI output-format changes.

**The C cells are the restart gaps.** Four were identified for Claude: **`rate_limit_event`** (used %, `isUsingOverage`, reset times), **`result.modelUsage.contextWindow`** (the context bar's denominator), **per-turn `result.total_cost_usd` + overage attribution** (the inline cost / "using credits" marker), and **`system/init.mcp_servers[].status`**. The first three are now **closed**: the rate-limit payload (G13) and `context_window` (M2/G29) by the last-write-wins per-agent **metadata sidecar** (`.meta.json`), and per-turn cost + overage (M4) by a separate per-agent **turn-metadata sidecar** (`.turnmeta.jsonl`, an append-log — one record per real-spend turn — re-joined onto the hydrated turn by `message.id`; see §3.1-cost below). The rate-limit payload is re-read with an "as of …" qualifier; `context_window` carries **no** age qualifier, but does carry the exact resolved parent-assistant model and final assistant `message.id` that supplied it. Claude may append `[1m]` only to that model's `modelUsage` key; the qualifier is accepted for lookup but is not part of the persisted transcript-model identity. Hydration overlays the snapshot only onto that exact turn when the model also matches and post-turn occupancy fits the window. Pre-G29 snapshots without both provenance fields are ignored until the next completed Claude turn rewrites them. The fourth (MCP live status, G14) remains open — also class-C, but deferred because a stale "up 3 days ago" indicator may be worse than none. (Mid-stream token deltas across all four are also class-C but have no UI surface today, so the loss is theoretical.) The metadata sidecar persists the class-C `rate_limit` and context-window snapshots; class-B sources (Codex's session-file rate-limit and context window) are not duplicated into it — the gate for the rate limit is the event's `RateLimitSource`, and for the window the `TurnEnd.context_window_source` (`StreamOnly` persisted, `SessionFileBacked` not). The turn-metadata sidecar gates on a per-turn join key being present **and** the turn being real-spend, not on harness identity — Claude is the only harness reporting cost in v1, so the gate is self-selecting and the dispatcher stays harness-agnostic.

**§3.1-cost — the M4 per-turn join (no backfill).** Cost (`total_cost_usd`) and the overage snapshot arrive on Claude's stream-only `result` record, which names no message and may never be written to the session file. The join key is the turn's **final non-subagent assistant `message.id`** — verified to round-trip identically between the live stream and the on-disk session file (a tool-use message can span two records sharing one `message.id` but with two different record-level `uuid`s, so `message.id` is the per-logical-message anchor; record `uuid` is per-record and was rejected). The live path stamps that id on `AdapterEvent::TurnEnd.stable_message_id`; the session-file parser stamps the same id on the hydrated `Turn::Agent.stable_message_id`. At turn-end the dispatcher appends `{message_id, total_cost_usd, spend, captured_at}` to the turn-metadata sidecar; on reopen the app re-joins by `message.id` and fills the hydrated turn's `spend` + `usage.total_cost_usd` (fill-if-empty). Best-effort throughout: a missing/corrupt log (or a corrupt line) degrades to "render nothing for that turn," never a failed hydration. **No backfill** — turns that completed before M4 shipped have no record and render no cost/overage on reopen; expected and documented, not a bug.

**§3.1-hydration — the stable hydration key (idempotent re-reads; refresh eligibility).** Distinct from the cost-join `stable_message_id` (Claude-only, private, `skip_serializing`'d) is a frontend-facing **`hydration_key`** on every hydrated `Turn::Agent` and on the live `NormalizedEvent::TurnEnd`. Its job is dedup: the frontend hydrate merge keys on it (falling back to `turn_id` when absent), so re-reading a session file never duplicates **agent** turns — `turn_id` is minted fresh per parse (`Uuid::now_v7()`) and can't recognize an already-loaded turn, the stable key can. **Scope:** only agent turns from key-bearing harnesses carry a key; **user turns are keyless** (the harness file doesn't know Switchboard's `send_id`) and fall back to the per-parse-fresh `turn_id`, so a re-read over an already-populated slice would *not* dedup them. The split-source design keeps user content owned by the journal overlay (replaced wholesale, dup-safe); a refresh must re-merge only agent turns through the keyed path, never harness user turns into a per-agent slice. Two properties matter and gate different things:

- **Q1 — re-parse-stable** (byte-identical across repeated parses of the *same* file). Enables reopen/refresh dedup of disk-only agent turns. Per harness: **Claude** ✅ ordinary turns use the **first** non-subagent assistant `message.id`; structurally linked `sdk-cli` local-command output uses its output-record UUID. Both are parse-invariant (distinct from the cost-join `stable_message_id`, which is the *final* assistant id and moves until an ordinary turn ends). **Codex** ✅ the turn's **`turn_context.turn_id`** (the observed shape annotates this the per-turn UUID; we deliberately do *not* use `task_started.turn_id`, whose per-turn-uniqueness is unconfirmed — a non-unique dedup key silently *drops* a new turn as "already seen", strictly worse than the duplication a too-volatile key causes); **Gemini** ✅ the turn's first `gemini` record `id` (a UUID, not the illustrative `g1`/`g2`); **Antigravity** ❌ no native per-turn id — keyless, the merge falls back to `turn_id`.
- **Q2 — live-matched** (the *live* stream carries the same id the file will store, so a turn that streamed live *and* is on disk dedups as one). Strictly stronger; **required for whole-file refresh**. Per harness: **Claude** ✅ confirmed for ordinary turns — the **first** non-subagent assistant `message.id` round-trips live↔disk and is announced immediately. SDK local-command compatibility records are the deliberate exception: their only disk identity is the output-record UUID, so they are re-parse-stable but not live-matched and correlate positionally. The cost-join `stable_message_id`, the *final* assistant id, round-trips separately per §3.1-cost. **Codex** ✅ **probe-verified for the durable send↔turn link, but not for refresh.** The live `TurnEnd.hydration_key` now carries the turn's `turn_context.turn_id`, sourced from the **post-terminal enrichment re-read** of the session file (`emit_terminal_with_enrichment`), so it equals the parser's `hydration_key` **by construction** — confirmed by the two-turn drift-guard `live_codex_hydration_key_matches_live_turn_end` (keys match per turn *and* vary across turns, i.e. no stale carryover). This is what lets the M2 `TurnLink` correlate Codex turns to sends. But it is **not** the strict live-matched property refresh needs: the key becomes available only at the *terminal* (read from disk by enrichment), not *mid-stream*, so a concurrent switch-back refresh of an in-flight Codex turn has no key to dedup on. Codex therefore stays **reopen-stable + link-eligible, but refresh-ineligible** — `supports_refresh` stays off. (Note we deliberately do **not** source from the live stream's `task_started.turn_id`, a different id the parser rejects for unconfirmed per-turn uniqueness; enrichment reads the exact `turn_context.turn_id` field the parser uses.) **Gemini** ❓ **unprobed** — disk key captured (Q1 ✅) but the live `TurnEnd` leaves `hydration_key: None`; a probe must establish **which** record's id the live stream carries (the disk key is the turn's *first* `gemini` record id). **Antigravity** ❌ never eligible (no key).

So **refresh eligibility is Claude-only today** (3-of-4 reopen-stable for disk-only agent-turn dedup; 1-of-4 live-matched). Flipping Gemini on is a one-line capability change once its probe passes (`HarnessKind::supports_refresh` is the single gate; the backend's `project_session_fingerprints` derives `refresh_capable` from it). Codex is a distinct case: it has a probe-verified **durable send↔turn key** (for the `TurnLink` correlation) but *not* a mid-stream live key, so it stays refresh-ineligible until/unless the live stream is shown to carry `turn_context.turn_id` mid-turn. `hydration_key` is best-effort and additive: a keyless turn simply dedups by `turn_id`, exactly as before.

**Durable send↔turn correlation (the M2/M3 key-join), per harness:** **Claude** ✅ and **Codex** ✅ join ordinary content-bearing turns to their sends by `hydration_key` via a journal `TurnLink` (Claude uses its first assistant `message.id`; Codex uses `turn_context.turn_id` — both live↔disk shapes are probe-verified). Claude SDK local-command compatibility output is disk-stable by output-record UUID but has no corresponding live key, so it intentionally uses positional correlation. **Antigravity** ❌ has no per-turn id, so it stays on **positional correlation** (order/count) — the fragile path a stray harness record can shift; recorded as a known limitation (**G24**). **Gemini** is out of scope (decommissioned; not extended). Per-harness user-side **bookkeeping audit** (the M1 principle applied out): Claude's bare `/compact` is the one confirmed non-prompt record that leaked into `Turn::User` (fixed, M1). Codex (`user_message`) and Antigravity (`USER_INPUT` carrying `<USER_REQUEST>`) show **no** non-prompt user-side record in the fixtures/probes — nothing to reclassify; Codex's compaction shape is **unprobed** (not triggerable on demand), left as-is rather than invented.

**§3.1-refresh — the staleness refresh (TUI-continued turns).** On switching **back** to an already-loaded project, Switchboard re-reads a refresh-capable agent's session file if it changed since last hydration, so a turn the user added by continuing the session in the harness's own TUI appears. The change check is a cheap backend `stat` (`project_session_fingerprints`, no parse) gated on **`(source_path, modified_at, byte_len)`** together (`byte_len` is the more reliable signal for an append-only JSONL; `source_path` catches a moved file, e.g. Gemini candidate selection); the expensive `load_project_conversation` parse runs **only** when that check shows movement, so an unchanged file is never re-parsed. The re-read uses the **project** path (not per-agent) so user content stays journal/overlay-owned, and applies agent turns through the M2 keyed merge for refresh-capable agents **only** — a non-refresh-capable agent that ran a turn in Switchboard this session already advanced its own file with a live key of `None`, so re-applying its disk copy would duplicate the live turn (the live-vs-disk hazard the gate prevents). The overlay drops any journaled row whose `send_id` is already live in a slice, so a re-read of the journal can't double a this-session send. **Benign failure modes:** a `stat` false-positive → a safe, deduped no-op re-read; a file read mid-write → the per-line parsers ignore the half-written trailing line and pick it up next refresh. **Known limitations** (documented, not bugs): (1) refresh fires on project **switch-back**, not while you stay inside a project — there is no live file-watch; the switch covers the "go to the TUI, come back" path. (2) In the rare *mixed* case — a **non**-refresh-capable agent continued in the TUI at the same time as a refresh-capable one triggers the re-read — the wholesale-replaced overlay surfaces that agent's new imported TUI **prompt** while its **reply** is (correctly) skipped, leaving a prompt with no answer until the next full app restart (which re-hydrates everything safely, since no live turns exist at open). It is not cleanly avoidable: imported prompts are keyless (fresh per-parse id), so filtering "new" non-refresh imported prompts would also erase legitimate existing non-refresh imported history — the rare, transient, restart-healed orphan is the better trade for a Claude-only-at-launch feature.

**§3.1-status — the EOF tail turn's terminality (in-flight vs finished).** Claude's session file has no per-turn completion marker, so the disk parser infers the tail turn's status from the **last assistant `stop_reason`** (`claude_code/session_file.rs::eof_tail_status`). The documented final reasons — `end_turn` / `max_tokens` / `stop_sequence` / `refusal` / `model_context_window_exceeded` — mark `Complete`; the continuation reasons (`tool_use`, `pause_turn`) and any unknown/absent reason mark `Streaming` — a **positive allowlist**, so a new/unrecognized stop_reason errs toward "still running," never "falsely finished" (a negative "not `tool_use` ⇒ done" check would mis-classify `pause_turn`). The allowlist must carry *every* documented terminal reason, though — dropping one (e.g. `refusal`) renders a genuinely-finished turn as a permanent spinner; the canonical list is the [Anthropic stop-reason reference](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons). An open tool (a `tool_use` whose result never bound — keyed on `output: None`, not the optional `completed_at` timestamp) also forces `Streaming`. Only the EOF **tail** turn is affected — every earlier turn is closed `Complete` by the following user prompt, which is definitive proof it ended. This is what lets a mid-flight re-read (switch-back/reopen while a turn streams, or a crash) render the tail as in-progress and dedup it against the live turn, instead of stacking a complete-looking turn with a perpetually-spinning tool. The disk parser can't distinguish "running right now" from "crashed/cancelled on a tool round" — both present as a trailing `tool_use` and both become `Streaming`; that residual is a status-display nuance resolved by the journal/dispatcher, not a dedup problem (the identity is stable either way). Asymmetric with Codex, whose per-turn `task_complete` marker lets *its* parser default a markerless tail to `Failed`.

**§3.1-provenance — user-prompt provenance (`promptSource`) and the housekeeping skip.** Claude's session file echoes the user's prompt back as a `type:"user"` record, so the merge must decide which of those the journal already owns (drop the harness copy) vs. which to render imported. Earlier this was inferred by **counting** harness turns against journal sends in order — which silently desyncs on long sessions, because the `user` channel also carries records that are **not** Switchboard sends, scattered through the history. Claude tags each `user` record with **`promptSource`**, a 4-value enum (corpus counts across all local sessions, 2026-06-21): **`sdk`** (1810 — dispatched by an SDK/headless client, i.e. Switchboard), **`typed`** (99 — typed into the bare TUI), **`queued`** (2 — typed into the TUI while a turn ran), **`system`** (1 — system-injected), and **absent** (3832 — older CLI with no marker; note this is the *majority*, so the absent→fallback path is the common one for historical transcripts, not an edge case). The parser (`claude_code/session_file.rs`) classifies each prompt into `UserPromptSource::{Sdk, External, Unknown}` (`sdk`→`Sdk`; `typed`/`queued`→`External`; absent/other→`Unknown`) on `Turn::User.source` (`#[serde(default, skip_serializing)]` — backend-private, never on the IPC wire, like `stable_message_id`). The merge (`commands.rs::classify_turns_by_provenance`) pairs slot-consuming `Sdk` prompts to journal sends (suppressing that copy) and renders `External` / `Unknown` / unpaired-`Sdk` / pre-journaling-`Sdk` imported; an agent with no positive provenance (all `Unknown`) falls back to the count path unchanged. **Housekeeping skip (load-bearing ordering):** before reading `promptSource`, the parser drops `user` *string* records that are not prompts — `isCompactSummary` / `isMeta` markers, and a maintained denylist of leading auto-generated tags (`<command-message>` ×713, `<command-name>` ×132, `<local-command-stdout>` ×100, `<task-notification>` ×101+, `<local-command-caveat>`, `<local-command-stderr>`). **`<system-reminder>` is absent from that denylist and does not need to be there** — Claude's harness reminders only ever appear as *array*-content blocks on `user`/`assistant` records, and the denylist is consulted only for `user` **string** records. Verified across 2.1.160→2.1.205: `message.role == "system"` has never been written to disk in any version, and 2.1.201's move of Sonnet 5 off the mid-conversation system role was an **API-wire** change with no session-file footprint. The invariant is load-bearing: a future CLI that emitted a reminder as *string* content would classify it as a real user prompt and render it as a typed send. Re-check on bump. The skip runs **first** because some housekeeping records carry `promptSource:"sdk"` (e.g. `<task-notification>` ×2) — mapping first would let them masquerade as a dispatched send and consume a journal slot, re-introducing the drift. A skip counter is logged at `finalize` so a denylist that stops matching is noticeable. **Bare slash-command reclassification (render/correlate split):** the denylist above catches the `<command-name>/compact</command-name>` *wrapper*, but Claude also writes the **bare** `/compact` back into the user channel — a lone slash-command string with **no `promptSource` and no `isMeta`**, so it slips past both `isMeta` and the prefix denylist and used to land as a real `Turn::User { Unknown }`. One such in-window `Unknown` prompt trips the straddling guard (below), abandoning provenance for the fragile count path, *and* the post-compaction continuation turn desyncs the count — the reported "latest prompt renders twice" bug. Fix (`is_bare_slash_command_record`): a `user` string record that is **provenance-less (`Unknown`) AND an exact match against a confirmed-command allowlist** (`KNOWN_BOOKKEEPING_SLASH_COMMANDS`, today just `/compact`) is routed to a non-correlating `SystemMarker::SlashCommand` — it **renders** (the user sees the command ran) but never consumes a send slot or advances a correlation counter (the render/correlate split, shared with the compaction summary marker). Both halves are load-bearing: keying on *absent* provenance (not `∉{typed,queued}`) keeps an `sdk`-dispatched `/compact` from the compose bar correlating, and an **exact allowlist** (not a `/token` shape rule) keeps both a genuine pre-`promptSource` prose dispatch (also `Unknown`) and a real lone-token prompt (`/review`) from being reclassified on a guess. The allowlist is confirmed ground truth (traced from the real auto-compaction session): the bare `/compact` record precedes the `compact_boundary` + `isCompactSummary`, and its `<command-name>` wrapper actually lands *seven records later* (after the summary), so a look-behind sibling-pairing would never fire — the allowlist is the honest ceiling of text-based detection. **Known limitations:** (1) a *manual* `/compact <focus…>` (compact with arguments) is **not** matched — indistinguishable from prose by any text rule; rarer than auto-compact, surfaced by the `commandish_not_reclassified` finalize breadcrumb, and backstopped by the M2 key-join. The real structural signal is the record's `parentUuid` chain (the auto-compact record is a child of the pre-compact `## Context Usage` hook), out of scope here. (2) This is Claude-specific; Codex/Antigravity bookkeeping shapes are audited separately. **Harness coupling** (gap-register class): this leans on Claude-internal fields that can change between CLI versions; the `Unknown` fallback bounds the blast radius to "no worse than the count path," and a `#[ignore]` live test (`live_claude_*`) asserts a dispatched prompt still writes `promptSource:"sdk"` so `make test-live` catches a rename. **Distinct shapes, same name:** the *live* `system/task_notification` **event** (subagent progress, G20 §4) and the on-disk `<task-notification>` **user-record** are different things — the former is a stream event mapped to `Liveness`, the latter is housekeeping the parser drops. Note the drop's boundary semantics have narrowed twice: **two** housekeeping shapes are **mid-turn continuations** (they land mid-dispatch and the process keeps responding), so they do not close the pending agent turn — (1) the `<task-notification>` record (G22; `is_task_notification_housekeeping` — a *typed* prompt merely starting with the tag remains a real prompt and boundary), and (2) any `isMeta` metadata row that is not a compaction summary (`is_meta_continuation`). The `isMeta` rule is deliberately **flag-based, not text-shape-based**: a genuine turn boundary is always marked by a real prompt record, so continuation is safe for the whole `isMeta` class, whereas matching on display text (`[Image: …]`) would silently resurrect the split when the CLI rewords the string. It rests on one invariant — **a dispatched prompt (`sdk`/`typed`/`queued`) never carries `isMeta`** (a violation would drop the prompt and merge the following turn backward) — guarded live by `live_claude_dispatched_prompt_never_carries_is_meta`, and the breadth is pinned by `non_image_meta_row_is_also_a_continuation`. Scope of that guard, stated honestly: it exercises the **`sdk` dispatch path** (the only class Switchboard originates); `typed`/`queued` prompts are TUI-side, and an `isMeta`-tagged one would have been **dropped identically before this change** (the old boundary-drop also discarded it), so the continuation rule adds no new exposure for those classes — only the boundary semantics changed, and a wrong non-boundary is inert because every genuine new turn begins with a real prompt record. The observed `isMeta` mid-turn shape is the `[Image: original WxH…]` description row Claude writes immediately after a `tool_result` whose content is an image — i.e. every time an agent reads a screenshot. Treating it as a boundary split one dispatched turn into several disk turns, each minting its own `hydration_key`; the live turn carries only the *first* fragment's key (`TurnIdentity` / `TurnEnd.first_message_id`), so on a switch-back refresh every later fragment failed the hydrate merge's key-dedup and rendered as a **duplicate turn** (and as fragmentation on plain reopen). Traced from a real duplication incident (2026-07-12): a 6-tool turn whose two screenshot reads split it into 1-, 1-, and 4-tool disk fragments with three distinct keys. `isCompactSummary` is explicitly excluded from the continuation: compaction is a genuine boundary whose continuation deliberately takes a distinct key — which means the compaction split shares this live↔disk key-mismatch hazard by design — reconciled by the `continuation_of` link the parser stamps on the post-compaction fragment (fixed; see **G28**). Every other housekeeping record remains a boundary. **Straddling sessions:** a file spanning the CLI version that introduced `promptSource` has both `Sdk` and journaled-region `Unknown` prompts; the merge routes those whole agents to the count fallback (an `Unknown` in the journaled region is a pre-marker dispatch the journal owns — importing it would duplicate it), so they're no worse than today but don't get the full fix. Detected as "any `Unknown` user turn at/after the agent's first journaled send"; pre-journaling `Unknown` (attached history) does not trigger it.

**Known limitation — a reload-stranded `Streaming` partial heals on next hydration, not live (deliberate, not a regression).** If the frontend reloads *mid-turn* (Vite HMR / `Cmd-R`), the backend keeps running the turn but the reloaded frontend has lost the dispatcher `turn_id`, so the turn's continuing live events are dropped (the reducer's unknown-`turn_id` guards) and a `Streaming` partial is left rendering a spinner. It heals on the **next hydration** — typically the next switch-back refresh after the turn completes, which supersedes the partial with the finished turn — **not live**. So a stuck spinner immediately after a reload is expected and self-corrects on the next project switch; it is not a regression in the in-flight-turn dedup work. Closing it *live* needs a dispatcher↔frontend resync that re-attaches the live stream to the hydrated turn (deferred "fix-c", out of scope for this work). This is distinct from the switch-back case, which the early `hydration_key` (§3.1-hydration) already collapses.

**Class B is *not* a gap** — we already re-read the session file at turn-end (Codex rate-limits, Codex model/context, Gemini tool output) and on project open, so the data is durable. The latency cost (one extra file read) is the trade.

**Class D is what no implementation can fix without external data** — e.g. Gemini does not emit a context window anywhere; Antigravity emits no token usage to disk. Document these as TUI parity ceilings; workarounds (hardcoded model→context maps) are case-by-case decisions.

**Surfacing (frontend).** A `Thinking` item renders via the `ThinkingWidget` — a collapsed-by-default disclosure with a one-line preview header and a muted Markdown body, distinct from and subordinate to the answer `Text` that follows. **Antigravity and Claude-on-Haiku feed it reasoning text today** (live and on reopen). **Every other current Claude model — Opus 5, Sonnet 5, Fable 5.1 — redacts the text** (§7.1), and we deliberately do **not** surface an empty placeholder, so those Claude turns show no reasoning disclosure (among the non-Haiku models Sonnet 4.6 was the last to expose it; its alias now points to Sonnet 5). **Gemini** is disk-only (never streams — confirmed 2026-05-29 @ 0.44.0), so reopened-only reasoning is dropped rather than shown as stale (decision). **Codex** encrypts it.

*Display remains carry-forward, unchanged by the above.* Antigravity announces the model in a `USER_SETTINGS_CHANGE` transcript sentence on turn 1 (`from None to X`) and on any later turn where the model **changes** — so the announcement now fires when *Switchboard's own* `--model` differs from the prior turn, not only when a human edits the settings file. Unchanged resumes emit no sentence, so the per-turn model is still reconstructed by **carrying the last announced model forward**, both live (the sentence rides the turn's own record) and on reopen (walk the transcript chronologically). One wrinkle the parser handles explicitly: the announcement is a *display name* (`Gemini 3.1 Pro (High)`), not the slug we dispatched, and its trailing parenthetical is split off as effort **only when it names a real level** — for several models the parenthetical is part of the name itself (see §3.4).

### 3.4 Reasoning effort — can we set the thinking level on a turn?

> **Status: shipped.** Effort is selected alongside the model in an agent's Primary or optional Secondary profile and sent every turn when set (`HarnessKind::supports_effort_selection` — Claude/Codex/**Antigravity**; Gemini config-only remains unavailable). Per-turn effort is recorded on the transcript for **Codex** (`turn_context.payload.effort`), **Claude** (session-file `effort` on reopen; the dispatched selection stamped live, since Claude's stream exposes none), and **Antigravity** (split off the announced display name's parenthetical when it names a real level). Antigravity is also the only harness where effort is **model-dependent and sometimes mandatory** — see `HarnessKind::effort_requires_model`. The transcript footer renders model and effort as a single `model (effort)` identity — effort qualifies the model rather than standing as its own column — and falls back to a bare model when no effort is known.

A *separate* axis from model (§3.3), with a **different capability set**. Verified empirically 2026-05-30 (claude 2.1.158, codex 0.134.0, gemini 0.44.0, agy 1.0.3), supplemented by docs where no CLI surface exists.

**Claude effort is model-specific in *effect*, but degrades safely (2026-06-05, doc-confirmed — both Anthropic effort/model-config pages — not exhaustively runtime-probed).** The CLI parser accepts all 5 levels for any model, but the *effective* set varies and an unsupported level **silently falls back to the highest supported level ≤ the one chosen — it never errors**: Opus 4.8/4.7 and Fable 5 honor all 5 (Fable verified live @ 2.1.170, 2026-06-09: `--model fable --effort low` → 4 output tokens, `--effort max` → 23, ≈6× more reasoning, neither errors); Sonnet 4.6 / Opus 4.6 cap at `high` (`xhigh`/`max` run as `high`); Haiku has no effort axis at all — and **the on-disk consequence of that is total omission, not a clamped value** (probed @ 2.1.241, 2026-08-23: `--model haiku --effort max` and `--effort low` both write **no `effort` key**, while `--model sonnet` records `max`/`low` verbatim). That distinction is load-bearing for anything that *displays* effort: a no-axis model gives you nothing to display, so a per-turn effort surface must be gated on the **resolved model id** rather than on the level we requested, and on an exact allowlist rather than a family match — the axis is a per-model property, so within one family Haiku has none while Sonnet 5 has one (see `parser.rs::model_records_effort`). **The gate's staleness tripwire has now fired once, as designed:** when the `fable` alias moved to `claude-fable-5-1` @ 2.1.257, the new id was absent from the allowlist, the live echo went blank, and `live_claude_session_file_effort_matches_the_dispatched_level` failed on the live-vs-disk mismatch (disk `"low"`, live `None`) — which is the probe. `claude-fable-5-1` records the requested level verbatim like the rest of the family and was added; `claude-fable-5` stays listed for agents pinned to the full id. **The live loop now sends Fable `max` rather than `low`** so the one family whose upper bound had only a hand probe carries a standing upper-bound guard (a boolean gate cannot see a clamped upper level; Opus 5 is the documented case). Fable 5.1's catalog entry carries `rejects_disabled_thinking`, which makes Opus 5's clamp path — an effort cap that applies only when extended thinking is *disabled* — structurally unreachable for it, a stronger argument than the mere absence of `thinking_disabled_effort_cap`. `claude-fable-5`'s own upper bound on disk is **unprobed** (2.1.170 measured output tokens at `max`, not the recorded `effort` value); it is reachable only by full-id pinning, so it stays listed on the strength of its `low` probe. **Unprobed, and deliberately so:** whether a *capped* model (Sonnet 4.6 / Opus 4.6 above) records the requested or the effective level on disk is not established — the gate withholds those ids rather than assuming either answer. **A second, orthogonal cap landed @ 2.1.251, and it is model-gated the same way.** With extended thinking turned off (`MAX_THINKING_TOKENS=0` or `"alwaysThinkingEnabled": false`), **Opus 5 — and only Opus 5**, via the catalog capability `thinking_disabled_effort_cap` — runs `xhigh`/`max` as `high` and **records the clamped level on disk**. Before 2.1.251 that combination failed the request instead, so the degrade-safely rule above now holds on this axis too, but only because upstream fixed it; Sonnet 5 was probed under both disable routes and is unaffected (§6). **Picker implication:** offer all 5 universally and keep dispatch dumb — the worst case is a silent no-op-down, never a failed turn — so a per-*model* effort matrix is **not** needed; a one-line UI caveat ("higher levels may run at a lower effort on some models") covers it. Precedence: `CLAUDE_CODE_EFFORT_LEVEL` env > `effortLevel`/`--effort` > model default.

**Antigravity is the opposite case, and it is why a per-model effort matrix exists for exactly one harness.** Claude needs no matrix because a mismatch silently degrades; Antigravity needs one because a mismatch **fails the dispatch**. Its validation is client-side, pre-dispatch, exit 1, quota-free, and names the valid set — so the picker can be exactly right and a wrong value costs nothing but a failed send. Three rules follow, all live-probed @ 1.1.19 (2026-08-23):

- **Effort is mandatory, not optional, for a model that has the axis.** `--model gemini-3.1-pro` with no effort is rejected: `requires --effort (available: low, high)`. So the picker must not offer a "Default (let the harness choose)" for those models — there is no such thing. This is the only harness with that rule, which is why it gets its own capability method (`HarnessKind::effort_requires_model`) rather than an inline special case; the negative half matters as much as the positive, since Claude and Codex both accept a model with no effort.
- **We dispatch base slugs, never `agy`'s folded ones.** The catalog offers both `gemini-3.1-pro-high` (effort folded into the name) and `gemini-3.1-pro` + `--effort high`. Folded slug plus `--effort` is rejected (`conflicts with --effort=low`), so the two spellings are mutually exclusive. Switchboard curates base slugs so effort is a genuine second control — the same shape the user already knows from Claude and Codex — rather than a model list with each level repeated as its own entry.
- **A model with a single level shows that level as an already-selected control.** `gpt-oss-120b` accepts only `medium`, and also dispatches fine bare — so hiding the control was defensible and was the original choice. It was reversed because it made the picker disagree with the transcript: agy announces `GPT-OSS 120B (Medium)`, and `split_announced_model` splits a real level off the parenthetical, so the turn footer renders model `GPT-OSS 120B` + effort `medium` either way. A single-option control states what the turn will run at; a `(Medium)` suffix in the model label contradicted the footer directly below it.

**"ultracode" / "ultrathink" are NOT `--effort` values** (verified 2026-06-05 — `--effort ultracode` → `Unknown --effort value`). `ultracode` is a Claude-Code-only `/effort`-menu **session mode** (sends `xhigh` + dynamic multi-agent orchestration); `ultrathink` is a **prompt keyword**. Neither is settable via `--effort`/`CLAUDE_CODE_EFFORT_LEVEL`, so the picker must not offer them — `max` and `xhigh` are the only real "above-high" `--effort` values.

**Caveats.** Claude `max` is **session-only** and had a historical "flag ignored" bug ([#50099](https://github.com/anthropics/claude-code/issues/50099), v2.1.113). **Re-probed @ 2.1.163 (2026-06-05): honored, bug does not reproduce.** Same reasoning prompt (`--model sonnet`): `--effort low` → 5 output tokens, `--effort max` → 80 (≈16×) at higher cost/latency, both reaching the correct answer — `max` demonstrably drives more reasoning, so it is safe for the M5 picker to offer. Re-probe on CLI bumps. Codex `none` is a *real* level (forces no extended reasoning) and is **not** the same as leaving effort unset (which passes no flag → harness default). The two harnesses no longer degrade in cleanly opposite ways — **Codex split its own behavior @ 0.151.0**. Claude silently runs the highest supported level ≤ the chosen one. Codex still **fails the turn** on an out-of-range `max`, with the server's own "Supported values are …" enumeration surfaced verbatim (re-probed @ 0.151.0: `gpt-5.5 -c model_reasoning_effort=max` → exit 1, `turn.failed` carrying the 400) — but **`ultra` now degrades client-side instead** (#41206: prefer the catalog override, else `max`, else the highest supported non-`ultra` level, else `medium`), so `gpt-5.5 + ultra` completes normally where it used to 400. The picker offers the full list for both — a Claude mismatch is a silent no-op-down, and a Codex mismatch is a self-explaining failed turn for `max` and a silent no-op-down for `ultra`. **The picker no longer withholds anything for Codex.** `gpt-5.5` — the only curated model that rejected `max` — was retired from `MODEL_OPTIONS.codex` (superseded by Terra at lower cost, per OpenAI's own guidance), which made `CODEX_MAX_ULTRA_MODELS` and its filter dead code and they were deleted with it. Codex effort is now uniformly permissive, matching how account/plan gating is already handled for every harness: an invalid level is discovered at dispatch, and Codex's own message enumerates the valid ones. **Antigravity keeps its per-model matrix** (`ANTIGRAVITY_MODEL_EFFORTS`), because there a mismatch fails the dispatch rather than the turn. Net: **effort is ours to drive on Claude, Codex, and Antigravity.** Gemini is now the lone holdout — it exposes a model flag but locks thinking behind harness-owned config, so it is the only harness left with an axis we can't reach. (Until agy 1.1.19 this read "mirror images": Gemini locked effort, Antigravity locked the model. That symmetry is gone — Antigravity now exposes both axes.) ### 3.5 Session branching (`/branch` / `--fork-session`)

> **Status: Claude-only headless support, with a caller-controlled fork id. Codex: headless path exists via the experimental app-server only (unwired). Gemini: lossy `--session-file` import (unwired). Antigravity: unavailable.**

"Branch" means diverging the conversation tree at the current tip: a new session ID is created that carries the full prior context, but subsequent turns go into the new session and don't affect the original. The TUI equivalent is Claude Code's `/branch` slash command. **Note on naming confusion:** the CLI flag for this is `--fork-session`, not `--branch`. The TUI's `/fork` command is a different operation — it spawns a background agent that *inherits* the conversation rather than branching it (see G20 for the background-agent subagent channel). `--fork-session` is the headless equivalent of `/branch`, not of `/fork`.

**A fork can only come into existence as a turn — there is no copy-a-session operation (probed 2026-08-10 @ 2.1.226).** `--fork-session` is a modifier on a resume, not a command: it redirects where the turn's result is written. Attempting to materialize a fork without a real prompt fails outright — both `-- ""` and omitting the prompt entirely are refused with `Error: … Provide a prompt to continue the conversation.` and **no child file is created**. Consequence for Switchboard: a fork cannot be created "empty" and pre-hydrated; the user's first message to the branch *is* the branch point. This is why the Fork affordance is a send-time option rather than a standalone create action, and why an eager fork would cost a synthetic turn in both transcripts.

**Interrupting a fork's first dispatch — a partial child file was never observed (probed 2026-08-10 @ 2.1.226).** Switchboard derives fork-vs-resume from whether the fork's own session file exists, so a child file left half-copied by a cancel would silently resume a shortened history. Across 22 `killpg` runs (mirroring Switchboard's cancel) at delays from 0.5 s to 8 s, against parents of 40 records / 35 KB and 31 records / 160 KB, on APFS, the child file was only ever **absent** or **content-complete** — never partial, never a torn JSON line, with the transition observed as a single step (at 160 KB: absent at 5.0 s, a complete 159 KB copy at 5.5 s). **This is a bounded observation, not a guarantee**: it covers those timings, sizes, one filesystem, and one CLI version; it cannot distinguish one atomic write from a create-then-append faster than the 0.5 s sampling, and it says nothing about I/O-error conditions (ENOSPC and kin). Switchboard's retry-idempotency (the `build_args` fork arm) **depends on this upstream behavior** rather than proving it; no partial-file guard is built, as a documented risk decision. Second consequence, recorded because it is worse than the first and not obvious from it: a partial child file can also make the transcript merge **misattribute** rather than merely truncate. A fork whose child file holds the copied in-window parent prompt and the synthesized reply but not yet its own prompt presents one candidate against one journal send — parity, where correlation is positional and text-blind by design — so the copied prompt is suppressed and the synthesized `"No response requested."` turn is shown as the answer to the user's branch message. That is silent misattribution, not the visible duplicate the merge otherwise degrades to. Falsifier for re-probes: a child file that parses cleanly but whose *conversation content* is a strict prefix of the parent's — note that raw record counts are a false signal (a complete child legitimately carries fewer records than its parent). Re-probe on CLI bumps.

**Forking while the parent is mid-turn — files stay intact, but the snapshot contains a synthesized in-window reply (probed 2026-08-10 @ 2.1.226).** Forking a session that another `claude` process is actively appending to: the fork **succeeds** with correct inherited context, the **parent file is not corrupted** (no unparseable lines; it continues appending its own turn normally), and the child file is valid JSON. The fork snapshots the parent's records as of its read. For the parent's in-flight turn — whose user prompt is on disk but whose answer is still streaming — Claude does **not** leave a dangling prompt: it copies the prompt (keeping the parent's timestamp) and synthesizes an assistant record reading **`"No response requested."`**. The parent's real answer never appears in the fork. Two properties of the synthesized record matter to Switchboard's merge (measured from the probe artifact): it is **stamped at copy time**, not with a parent-era timestamp — so it lands *inside* the fork's own live window, not in its pre-journal history — and its `message.id` is a **bare UUID** (`75b36508-…`), unlike every real assistant record's `msg_01…` id, so it carries a hydration key that never existed in the parent and never gets a `TurnLink`. Net effect: the branch permanently lacks the parent's answer to its last question (with a truthful "unanswered" stub in its place, visible in the transcript and in the model's context), and the merge must tolerate an in-window, keyed, link-less agent turn. Switchboard blocks this: the Fork affordance is hidden and the send is refused while the parent is running a turn (one check, at the chip advisorily and at dispatch authoritatively — `docs/implementation_plans/2026-08-10-claude-fork.md`). The in-process check is a **look, not a lock**. A second Switchboard instance — a dev build and the installed app, which have separate stores but share the harness's session files — used to slip through it, and now does not: every turn takes an advisory lock keyed on `(harness, session locator, cwd-namespace)` under a lock root deliberately *not* dev-isolated, and a fork that has not materialized yet locks its parent's key in addition to its own, for the whole of its first turn (`crates/app/src/session_lock.rs`). That last part makes the rule symmetric — the parent is also refused a turn while the branch is materializing, which the in-process gate never covered — and it is bounded to the branch's first turn, since a materialized branch never reads the parent's file again. What remains open is the writer Switchboard cannot see: a bare `claude` CLI run or a third-party automation on the same session takes no such lock and can still produce exactly this stub. That narrower residual is accepted.

**One exception inside Switchboard's own coverage, and the upstream assumption it rests on.** An agent's *first* Codex or Antigravity turn has no conversation id yet, so there is nothing to key a lock on and none is taken. This is safe only because **harness-assigned conversation ids are unique per conversation** — the harness mints the id during that dispatch, so no other writer can be holding it, and the *next* turn locks it normally. That is an assumption about upstream behaviour, not something Switchboard checks: there is no post-capture uniqueness scan (the `check_*_session_id_unique` functions run at *attach*, and the locator sink persists the captured id directly). Re-verify it if a harness changes how it assigns ids.

**Switchboard implication.** Because `--fork-session` works headlessly *and* the forked id is caller-controlled, Switchboard can expose "Fork" with no capture machinery at all: the command shape is `claude -p … --resume <parent session_locator> --session-id <pre-generated new uuid> --fork-session -- "<first prompt on fork>"`, and the new agent's `session_locator` is pre-generated at fork registration exactly like `Project::register_agent`'s Claude arm (the pre-2026-08-10 assumption that the id had to be read back from `system/init` is obsolete). Because a fork can only materialize as a turn (see above), the affordance is a **send-time option in the compose bar** — the send that carries it registers the branch and dispatches the first turn as one action — rather than a standalone agent action. Implementation: `docs/implementation_plans/2026-08-10-claude-fork.md`. The Codex/Gemini asymmetry (headless fork only via the app-server / only lossily) matches system-design §9's fork capability matrix; the option is the send button's second half and is hidden when unavailable (non-Claude recipient, multi-recipient, parent mid-turn, workflow mode, or a prompt with a field filled from another agent — that last one composes server-side and dispatches on an unbounded hold, so a branch taken for it would sit promptless or register against a stale gate); the `⇧⌘↵` shortcut stays live in those states and refuses with the reason, so the explanation survives the affordance being hidden. Forking with a **saved prompt** is supported: the prompt renders first, so a render failure — including an abandoned MCP sign-in — leaves no branch behind, and the composer is not cleared until the render has succeeded and the send has been revalidated against the parent's current state.

**`parent_session_id` is absent from the stream.** Switchboard has no wire signal that a session is a fork — the new session's `system/init` looks identical to any fresh session. The branch relationship lives only in the on-disk `parentUuid` chain. Switchboard does not need to read or track this chain; it is the harness's internal tree, not Switchboard's.

### 3.5b Claude session-directory encoding (cwd → `~/.claude/projects/<dir>`)

> **Status: read out of the CLI bundle (2.1.226) and confirmed on disk. Supersedes the archived probe, which records only the `/` and `.` cases. Re-read out of the 2.1.251 binary (2026-08-30) — all four rules below are unchanged, including the 200-character cap and the hash suffix.**

**Re-verification note (re-read @ 2.1.251; first written @ 2.1.241).** 2.1.234 added a `CLAUDE_CODE_PROJECT_DIR_NAME` override, which would replace the whole encoded name — but it is **gated on `CLAUDE_CONFIG_DIR` also being set** (`BOu = memo(() => CLAUDE_CONFIG_DIR ? sanitize(CLAUDE_CODE_PROJECT_DIR_NAME) : undefined)`, and the encoder falls through to the rule below otherwise). Switchboard sets **neither** env var, so it does not apply — but a future decision to give agents isolated config dirs would silently activate it, which is the shape to watch. Still gated that way @ 2.1.251, and 2.1.251's fix for "session transcripts silently overwritten when a directory change relocated a session onto an existing same-ID transcript" does not move the encoding: it adds `relocated`/`relocatedCwd` fields the CLI scans for when a `/cd` moves a session, a path Switchboard never takes (an agent's cwd is fixed per dispatch) and whose records the disk parser skips as unknown. Separately, 2.1.224's "long (>200 char) project paths resolving to another project's session directory" fix **is** rule 3 below; we already implement it, so that release was a no-op for us rather than the break it reads as.

Claude Code derives its session-storage directory from the agent's cwd. Switchboard must reproduce the rule exactly, because `build_args` picks `--session-id` (first turn) vs `--resume` (every later turn) purely from whether `<dir>/<session-uuid>.jsonl` exists. A mismatch makes every turn after the first look like a first turn, so the adapter passes `--session-id` for a session that already exists and the CLI rejects it with **`Session ID … is already in use`**. The check is a filesystem lookup, so it fails identically on every retry and across app restarts — the agent is stranded permanently, not transiently.

The rule, verbatim from the bundle:

```js
bes = e => e.replace(/[^a-zA-Z0-9]/g, "-")
gw  = e => { let t = bes(e); return t.length <= sQ ? t : `${t.slice(0, sQ)}-${T$g(e)}` }   // sQ = 200
T$g = e => Math.abs(xdt(e)).toString(36)
xdt = e => { let t = 0; for (…) t = (t << 5) - t + e.charCodeAt(r) | 0; return t }
input = NFC(realpath(cwd))
```

Four details, each of which independently produces the permanent strand above:

1. **Every** character outside `[a-zA-Z0-9]` collapses — not just `/` and `.`. `_` and spaces included: `switchboard-mcp_oauth` lives under `…-switchboard-mcp-oauth`. *(This is the one that stranded a real agent; fixed.)*
2. The regex has **no `u` flag**, so it runs over UTF-16 code units. An astral character (emoji) becomes **two** dashes, not one. *(Fixed — `encode_utf16`, not `chars`.)*
3. Names over **200** characters are truncated and suffixed with `-<base36 hash of the untruncated path>`. Reachable in ordinary use: the `.switchboard/projects/<uuid>` cwd shape alone adds 59 characters. *(Fixed.)*
4. The path is **NFC-normalized** first. **Not yet implemented** — a decomposed (NFD) path, which macOS produces routinely, still resolves to the wrong directory and strands the agent. Closing this needs a Unicode-normalization dependency (e.g. `unicode-normalization`); until then an NFD cwd containing non-ASCII is a known-broken shape.

Empirical corroboration: across a 161-directory sample of a real `~/.claude/projects/`, every name matches `[A-Za-z0-9-]*` — no `_`, `.`, or spaces survive.

**Transcript loading is insulated; dispatch is not.** `claude_code/session_file.rs` falls back to scanning `projects/*/<uuid>.jsonl`, which is encoding-independent, so a stranded agent still renders its full history while every dispatch fails — a confusing signature worth recognizing. `build_args` has no such fallback.

### 3.6 Tool vocabularies & facet mapping

> **Status: probed live 2026-07-13** (claude 2.1.206, codex 0.144.3, agy 1.0.16; gemini 0.44.0 **unprobeable** — see G26). Captures live under `crates/harness/tests/fixtures/<harness>/` (`tool-vocabulary*`, `file-change*`, `apply-patch*`, `exec-wrapper*`). Each adapter maps its raw tool vocabulary to a normalized `ToolFacet` (`crates/harness/src/facets.rs`) at both call sites (stream parser + session-file parser); the raw `name`/`input` ride alongside untouched.

**Path absoluteness (probe checklist result).** Every observed file path is **absolute** in every harness: Claude `file_path`/`path`, Codex `apply_patch` section paths and `workdir`, Antigravity `TargetFile`/`AbsolutePath`/`SearchPath`. Adapters still normalize defensively (lexical join against the turn's cwd where one is known), but no harness currently requires it.

**Claude (2.1.206).** Live stream `tool_use` blocks and on-disk session records carry identical `{name, input}` — one classifier serves both. Observed shapes: `Bash {command, description}` → Shell; `Read {file_path}` → Read; `Edit {file_path, old_string, new_string, replace_all}` → Edit (one file, one pair); `Write {file_path, content}` → Write; `Grep {pattern, path}` / `Glob {pattern, path}` → Search; `TaskCreate {subject, description}` / `TaskUpdate {taskId, status}` → Todo; `mcp__<server>__<tool>` → Mcp. **Vocabulary drift found by this probe:** `MultiEdit` and `TodoWrite` no longer exist in 2.1.206 (requested via `--tools` and silently dropped) — `Edit` absorbed multi-edit, the `Task*` family replaced todos. Both legacy names are still classified (historical session files may contain them) from their documented shapes — the only unverified mappings in the set (G27). `Task` (subagent dispatch) is deliberately unmapped → Other.

**Codex (0.144.3; third rollout generation added 0.147.0/0.148.0, supported since G30 closed).** The live stream is unchanged: shell calls use `command_execution`, and edits use `file_change` with paths/change-kinds but no content. Rollouts have **three** tool-record generations, all supported. In the third — `history_mode: paginated` — tool *rows* still come from `response_item` (the only complete record: a failed call can emit no item), while `event_msg/item_completed` supplies enrichment: `CommandExecution` (structured `exit_code`, clean argv, separate stdout/stderr — richer than anything legacy persisted), `FileChange` (same `changes` map as `patch_apply_end`, one facet builder for both generations, incl. `move_path` → the rename display), and `McpToolCall` (same three result envelopes as the live stream, decoded by the shared `extract_mcp_output`/`mcp_result_indicates_error`). Codex 0.149 can persist a healthy structured completion after its wrapper output because Code Mode and the nested operation lifecycle finish asynchronously. A 2026-08-27 scan of 995 local rollouts found 16 such completions in four files: 15 commands and one MCP call, all crossing `token_count`, four also crossing the completed-Reasoning record pair, with about 0.2–2.1 seconds between wrapper output and completion. The structured item id does not match the wrapper id or `call_id`.

Hydration therefore associates paginated tool detail in a file-local prepass rather than trusting adjacency alone. `item_completed.turn_id` must select one unique `task_started.turn_id` in the rollout and agree with `turn_context.turn_id` when that context exists. A canonical one-command wrapper may then match a `CommandExecution` by an exact command signature (and equal cwd when both sides supply one); matching is never fuzzy. Ordinary uncontested call→output intervals remain valid. A command or MCP completion may also cross only the observed post-output bookkeeping sequence (`token_count`, optionally the Reasoning item/response pair) when exactly one wrapper remains eligible; late `FileChange` is not admitted by that fallback. A new wrapper expires the older positional candidate but does not disable later tools. Missing, duplicated, conflicting, or ambiguous identity leaves the structured item unowned: the canonical wrapper survives unchanged and the parser records a developer diagnostic rather than risking a wrong attachment. A completion written after `task_complete` can still enrich its original turn through the validated producer id. This producer relation is internal to one rollout and is separate from the frontend hydration key.

Transcript diagnostics follow ownership rather than volume. Parser warnings
remain in `LoadedTranscript` for tests and developer drift detection, but they
do not produce an agent-card counter. A warning emitted while a structured
completion is being decoded is copied to that completion's proven tool row and
is visible in its expandable details; an unowned completion never annotates a
nearby row. Failure and cancellation remain the row's primary status. A stale
Codex locator recovers zero trustworthy history, so it fails the affected
agent's hydration instead of returning a successful empty transcript. (#87
applied the same rule to Gemini's ambiguous multi-session file — a collision
peculiar to its 8-hex-char filename prefix; that half went with the adapter's
removal and has no analogue in the remaining harnesses, whose session files are
addressed by full UUID, thread-id + date, or server-assigned directory.)

A wrapper proved to be a single shell command is enriched in place — and is then permanently an operation row, which no later sibling may supersede. Its one *expected* item is that call's own `CommandExecution`. An unexpected `FileChange` or `McpToolCall` inside the ordinary wrapper interval is warned and kept as its own row without superseding the command row. A second `CommandExecution` cannot reuse the proved single-command slot; without another canonical wrapper proving that operation ran, it remains unowned and is omitted with a developer diagnostic rather than rendered as an invented command. **Corpus observation (2026-08-23, codex-cli 0.149.0, 944 local rollouts):** across **6,432** single-command wrappers, no `FileChange`, no `McpToolCall`, and no second `CommandExecution` ever attached, in either order — which is why the shape reads as drift rather than ordinary shell behaviour. That is a real-world frequency at one point in time, **not** proof the shape cannot become healthy in a later CLI; a future capture showing it routine is grounds to relax the warning, not to suppress it silently. (Methodology: the scan approximated the decoder loosely — one `tools.` call, being `exec_command` — so the true single-command set is a subset of the 6,432 measured.) Batched wrappers get a row per operation and the wrapper row is then **superseded** — its children already render every operation it performed, so keeping it showed each one twice and exposed raw script text the live stream never surfaces. Two exceptions keep their row: a wrapper that attached **no** child (the only record the operation happened), and a **failed** wrapper (its children cover only the operations that got far enough to emit an item, so a batch whose second operation failed hard has its diagnostic nowhere else). The first two generations:

| Path | Record | Carries |
| --- | --- | --- |
| live stream | `file_change` item: `{id, changes:[{path, kind:"update"\|"add"\|…}], status}` | **paths + change-kind only — no content, no diff** |
| session file (0.143 legacy) | `function_call` name `exec_command` with JSON-string `arguments`; standalone `custom_tool_call` name `apply_patch` with patch-text `input`; scalar-string outputs; `event_msg/patch_apply_end` with per-file `{type, unified_diff\|content, move_path}` | raw shell command/cwd + two edit-content sources |

**MCP envelope.** Live `mcp_tool_call` items carry `server`, `tool`, and object-valued `arguments` directly on both start and completion records. The rollout representation is split: a `function_call` carries the bare tool name, JSON-string arguments, and sometimes `namespace:"mcp__<server>__"`, while a later `mcp_tool_call_end` keyed by `call_id` carries canonical server/tool identity and the result. A namespaced start classifies immediately; a namespace-less start is corrected when its matching end record arrives, reclassifying the retained arguments so live and reopened turns converge without deriving identity from the display name.

The adapter closes the live edit-content gap at turn end: the session-file enrichment reads the **mode-selected** edit source — on legacy rollouts the patch call or `patch_apply_end` (de-duplicated by `call_id` when both exist), on `history_mode: paginated` rollouts the `item_completed/FileChange` items in record order — and upgrades the live `file_change` row by ordinal position under a path-set guard. Both generations flow through the same facet builder, so they render identically. **The pairing keys on *source* paths deliberately:** the live `file_change` row only ever knows the source, so `EditedFile.path` must stay the source and a rename's destination rides on `EditedFile.moved_to` (populated from `*** Move to:` in patch text and `move_path` in structured change maps — both generations); flipping `path` to the destination would silently stop renames, and only renames, from receiving their live diff upgrade. Hydration concatenates the new output blocks and reconstructs a separate content-bearing Edit item from the same source. Observed `patch_apply_end` delete changes carry the deleted file's prior body in `changes[path].content`; the adapter preserves it as an all-removed diff, so a single-file row is labeled **Delete** and no longer falls back to content-unavailable. An `exec` wrapper becomes a Shell facet only when it structurally contains one static `tools.exec_command` call and no other operations; the parser extracts that call's real command/cwd while retaining the wrapper as raw input. Its argument literal is **JavaScript, not JSON**, and the form has changed across releases — 0.149 writes bare identifier keys over several lines where earlier releases wrote single-line quoted JSON — so the decoder accepts both. This is a silent-failure surface — nothing is logged — and its cost is uneven. A wrapper whose children are well-formed is unaffected in the transcript: the children supersede it and carry their own facets, so the decoder is not load-bearing there. Decode failure is most visible on **childless** wrappers, which then render as raw script text. It is not confined to them, through one narrow compound path worth stating precisely, because tracing it from a vaguer summary leads a reader to conclude it cannot happen. A superseded wrapper survives turn close **only if marked failed**, and the full-result exit code (`structured_script_exit_code`) — one of three signals that can supply the deciding mark, alongside the `Script failed` header and a plain process-exit line — is itself gated on a successful decode. So when **all four** hold at once — the decode fails, the child's own `status` is unreadable, the child's own `exit_code` is *also* unreadable or absent (either alone still convicts), and the wrapper's output carries none of the plain-text failure markers — no surviving row is marked failed. It is unrecoverable rather than merely unlikely: the child carries a synthetic `exec-<uuid>` id that never matches the wrapper's `call_id`, so the wrapper's own output-pairing fallback structurally cannot reach it. What remains is a **developer-visible parse warning** for the unreadable status — nothing restores a user-visible failure state. Pinned both ways by `decode_failure_with_a_blind_child_loses_the_failure_flag`. Re-probe on bump. Multi-call, mixed, dynamic, and unparseable wrappers degrade to Other because one durable call id/output cannot support a truthful nested breakdown. Renames are represented and rendered (`source → destination`, destination-targeted copy, and destination-keyed diff identity so a changed extension highlights correctly); what remains unobserved is a **live** move — the rendering is exercised by fixtures only, and real renames are rare (§5 carries the frequency note).

**Gemini (0.44.0).** Unprobeable — the CLI fails auth for individual accounts (G26). Builtin facet classification remains deliberately unmapped: non-MCP tools still receive `Other` and render through the generic path. MCP calls using the existing `mcp__<server>__<tool>` convention receive provider-neutral MCP facets from the stream's `parameters` object and the session file's equivalent `args` object; this path is covered by synthetic paired fixtures, not a live Gemini capture. The pre-sunset capture (`fixtures/gemini/tool-use.stream.jsonl`) shows `read_file {file_path}` / `update_topic {…}` under `tool_name`/`parameters` if builtin mapping is ever revisited.

**Antigravity (agy 1.0.16; full-transcript and failure shapes reconfirmed on 1.1.2).** Richly structured — six builtin tools, full content, absolute paths (supersedes the shell-only reading of the older `tool-use.transcript.jsonl` capture): `run_command {CommandLine, Cwd, WaitMsBeforeAsync}` → Shell; `view_file {AbsolutePath}` → Read; `replace_file_content {TargetFile, TargetContent, ReplacementContent, StartLine, EndLine, AllowMultiple}` → Edit; `write_to_file {TargetFile, CodeContent, Overwrite}` → Write; `grep_search {Query, SearchPath, IsRegex, CaseInsensitive}` → Search; `list_dir {DirectoryPath}` → Other. MCP dispatches surface as a `call_mcp_tool` wrapper whose arguments carry `ServerName`, `ToolName`, and `Arguments`; `Arguments` is a native object in the full transcript and a JSON string in the compact transcript. The adapter unwraps only a complete, object-valued argument envelope, preserving the original wrapper name/input as raw provenance.

**Two transcript representations:** current Antigravity writes the same record sequence to `transcript_full.jsonl`, whose tool arguments retain native JSON types and complete content, and compact `transcript.jsonl`, whose argument values are JSON encoded inside strings and whose large values can be clipped with a literal `<truncated N bytes>` suffix. The files are written independently: live tailing switches compact → full only after full reaches the emitted record cursor, preserves that cursor, and never switches back; hydration chooses full only when it has at least as many complete records as compact. This caught-up rule prevents a newly created but lagging full file from hiding available compact history. Compact fallback remains for older conversations and decodes one level; if Antigravity clipped an encoded string, it recovers only the valid decoded prefix and marks the facet truncated rather than displaying escaped source and the vendor marker as real content. `tool_calls` ride on `PLANNER_RESPONSE` records identically live (tail) and on reopen — one classifier with an explicit source-encoding boundary serves both paths. Normal results are `MODEL` records, but an invocation rejected before execution is a `SYSTEM` / `ERROR_MESSAGE` record whose `error` or `content` explicitly contains `invalid tool call`; the adapter treats only that narrow system-error shape as the pending tool's failed completion and prefers its timestamp-free top-level `error` for display. Other system errors such as `RESOURCE_EXHAUSTED` remain turn-level and never consume a pending tool.

### 3.7 Attachment staging location — can a harness read a file outside its cwd?

> **Status: probed 2026-08-27. Claude, Codex, and Antigravity all read an attachment staged wholly outside the agent's working directory. Gemini indeterminate (auth-dead, G26).**

Switchboard transports attachments by staging the file and appending its absolute path to the prompt (`docs/implementation_plans/2026-06-07-attachments.md`). That plan chose `<cwd>/.switchboard/projects/<id>/attachments/` on the reasoning that **inside `cwd` is the only location readable by all four harnesses** — a claim made before the current maximum-autonomy spawn flags settled, and never tested against an out-of-cwd path. It is the load-bearing constraint on where Switchboard may keep per-project state, so it was re-probed directly.

| Harness | CLI @ probe | Inside cwd | Outside cwd | Notes |
|---|---|---|---|---|
| **Claude** | 2.1.247 | ✅ | ✅ | `--dangerously-skip-permissions`; no path scoping observed |
| **Codex** | 0.149.0 | ✅ | ✅ | `--dangerously-bypass-approvals-and-sandbox`; sandbox off, so no workspace scoping |
| **Antigravity** | 1.1.21 | ✅ | ✅ | **The predicted failure — it passes.** `--add-dir <cwd>` establishes the workspace for the model's file tools, so an out-of-workspace read was expected to fail. It does not: the file is read with **no** second `--add-dir`. Re-probe on `agy` bumps; this is the one result most likely to regress, since it depends on workspace scoping *not* gating reads. |
| **Gemini** | 0.44.0 | ❌ | ❌ | **Indeterminate, not a failure of this property.** Both cases fail identically with an empty response because the CLI is auth-dead for individual accounts (G26) — the control fails too, so the probe cannot distinguish. Not a blocker: G26 already records that Gemini's live tests cannot run at all. |

**Consequence.** The "inside cwd is the only universally readable location" constraint is **not true at current CLI versions**, so Switchboard's per-project state is free to live outside the user's working directories. Do not read this as "sandboxing is gone" — it holds *because* all four adapters spawn with sandboxing/permissions fully disabled. If any adapter ever re-enables a sandbox, this table must be re-probed before trusting an out-of-cwd path.

**And the first hole in that reasoning arrived @ Claude 2.1.257: `permissions.blockReadsOutsideWorkingDirectories` is not disabled by `--dangerously-skip-permissions`.** When a user turns it on (a new one-time auto-mode prompt offers it, and it writes to **user** scope, so it applies to every project), Claude refuses the staged read while the turn still reports `subtype:"success"`. The Claude adapter now passes **`--add-dir /`** on every dispatch, which restores the read with the setting on and is a no-op with it off — so the table's Claude ✅ holds again, by flag rather than by the absence of a fence. See **G33** (closed) for the probe and the reasoning behind the root rather than the attachments directory. Tests: `live_<harness>_attachment_in_project_store_is_readable` (`crates/dispatcher/tests/live_end_to_end.rs`) stages at the real production location — `project.attachments_dir()` under a store the test opens in its own tempdir — alongside `live_<harness>_attachment_inside_cwd_is_readable` as the in-cwd control. **Correction 2026-09-01:** until then the "inside cwd" variant also staged under `project.attachments_dir()`, which had silently moved *outside* the cwd when the store left working directories, so both variants were the same out-of-cwd test and no harness had an in-cwd control at all; the control now stages at `<cwd>/attachments/` (all three harnesses pass it).

### 3.8 Browser control (Claude in Chrome) — how a harness exposes it, and how failure reads

> **Status: probed 2026-08-31 @ Claude 2.1.251 / codex-cli 0.151.0. Full detail, including the raw probe transcripts, in `docs/research/claude-chrome-extension.md`.**

Asymmetric across harnesses, so it is a per-harness capability rather than a shared one:

| Harness | How it's enabled | Switchboard can drive it |
|---|---|---|
| **Claude** | `--chrome` / `--no-chrome`, per invocation | ✅ — `DispatchOptions::chrome_integration`, from the `claude_chrome_enabled` preference |
| **Codex** | `[plugins."chrome@openai-bundled"] enabled = true` in `~/.codex/config.toml`, written by the `ChatGPT` desktop app | ❌ — global config we don't own; `codex exec` just inherits it |
| **Antigravity** | not probed | — |

**`--chrome` attaches an MCP server** named `claude-in-chrome` (22 tools: `navigate`, `read_page`, `get_page_text`, `read_console_messages`, `browser_batch`, `file_upload`, …), reported in `SessionMeta.mcp_servers` like any other. It does **not** appear in `claude mcp list`, being built in rather than user-configured, so Switchboard's MCP registry surfaces it only via `SessionMeta`.

**The failure mode is the important part: it is entirely invisible to a supervising process.** With the extension uninstalled, `--chrome` still exits 0, still loads all 22 tools, and still reports `status: "connected"` — that status describes the *local MCP server process*, not the browser. The final `result` event carries `is_error: false`. The failure surfaces only when a browser tool is called, and even then as an ordinary tool result whose text happens to be an error (`"Browser extension is not connected. …"`) with **no `is_error` key at all**. Nothing structural distinguishes it from success.

There is also **no pre-flight check**: `cachedChromeExtensionInstalled` in `~/.claude.json` stays `true` after an uninstall (stale cache), and the native-messaging manifest survives uninstall and isn't re-consulted once Chrome holds a connection. Hence the design: browser access is an explicit user assertion (a Settings toggle), not something Switchboard detects.

One adjacent behavior *does* set `is_error: true` — when multiple browsers are connected and none is paired, every browser call fails demanding `AskUserQuestion`, which doesn't exist in `-p`. Escapable in-conversation (`select_browser` works headlessly) and the pairing then persists user-globally in `~/.claude.json` → `chromeExtension.pairedDeviceId`, so it costs one round-trip once.

**Both flags shipped together in 2.0.72 (2025-12-17)**, the release introducing Claude in Chrome as a beta — verified by pulling that tarball and 2.1.0's from npm and finding `--no-chrome` in both `cli.js` files. GA was 2.1.198; current is 2.1.251. So there is no version window where `--chrome` parses and `--no-chrome` does not, and emitting one on every dispatch introduces no practical CLI floor. This was checked because an unconditionally-emitted flag couples *every* Claude turn — not just browser ones — to the CLI recognizing it, which would otherwise be a poor trade for an opt-in feature.

**Probed 2026-08-31 @ 2.1.251 — Claude Code's own "Chrome by default" does not reach `-p`.** With `~/.claude.json` → `claudeInChromeDefaultEnabled` set `true`: no flag → **0** browser tools; `--no-chrome` → 0; `--chrome` → **22**. The third arm is the control — it proves the probe can observe tools at all, without which the first arm's zero would be uninterpretable ("key is inert" vs "flag wins"). So that setting is interactive-only, and the conflict `--no-chrome` was introduced to prevent (agent holds browser tools while Switchboard's Settings reads off) **is not reachable**. The off-direction flag is kept as belt-and-braces — it costs nothing given both flags ship since 2.0.72, and it holds if the setting ever starts applying headlessly.

**Scope is global and per-turn, a deliberate v1 tradeoff.** One user-global preference, sampled per dispatch, so enabling it gives *every* Claude agent the browser tools and their ~2,400-token init cost on *every* turn, including agents doing unrelated work. `ToolSearch` deferral keeps the remainder unpaid until an agent reaches for the browser, but this part is not deferred. Accepted because extension install and browser pairing are machine-level facts, and because the per-agent sidebar already shows which agents carry the tools. A per-agent override remains open but is not free — it needs a persisted `AgentRecord` field, defaulting for existing agents, UI, and precedence rules against the global.

Test: `live_claude_chrome_flag_toggles_browser_tools` (`crates/harness/tests/live.rs`) — one agent, three turns, so the on/off assertions land on `--resume` invocations rather than fresh sessions (a CLI that latched the capability at session creation would otherwise pass). Deliberately extension-independent, so it runs anywhere `claude` is logged in.

**Data loss (Antigravity):**
- **G32 — a failed tool call leaves no trace on disk, so reopening a conversation loses it** (upstream, @ agy 1.1.19; mitigated, not fixed). A tool call that `agy` rejects during argument validation writes **no** `transcript.jsonl` record at all — not the call, not the error, not a `SYSTEM/ERROR_MESSAGE` (which is what 1.1.2 used to write; see §6). The call and its message exist **only** on the live `stream-json` channel as a `state:"ERROR"` step. *Consequence:* a user watching live sees the failed tool and its reason; the same conversation reopened later shows the tool as a call with no result. *Mitigation:* the adapter consumes the stream's `ERROR` steps live and, on reopen, closes any tool left without a result using a neutral authored line rather than leaving it pending forever. **The two views are therefore deliberately asymmetric, and cannot be made equal:** live carries `agy`'s own per-tool message, disk can only carry the neutral constant, because the real text never reached disk to be recovered. Live pairing is exact (the stream names the failing `step_index`); hydration is only as exact as the proven step→call invariant (`result_step = planner_step + 1 + call_index`). User-facing entry in `README.md`. Re-verified present @ 1.1.20.

### 5.1 Verified but deliberately unbuilt

Distinct from the list above: these are capabilities we **have** captured and confirmed work. They are recorded so a future reviewer doesn't rediscover them and mistake them for easy wins — each was costed and declined.

**Antigravity quota via `/usage` (probed @ 1.1.19–1.1.20, 2026-08-23/25; built to green tests, then cut).** `agy` began answering read-only slash commands in print mode @ 1.1.11/1.1.12. `agy -p "/usage" --output-format json` returns a complete quota payload without starting an agent turn, creating a conversation, or spending quota (`num_turns: 0`, `conversation_id: ""`):

```
command.data.groups[] : {name, description, buckets[]}
       buckets[]      : {id, name, window, remaining_fraction, reset_time}
       ids observed   : gemini-5h, gemini-weekly, 3p-5h, 3p-weekly
```

Quota is **account-scoped and split into two independent pools by model family** — "Gemini Models" (Flash, Pro) and "Claude and GPT models" (Opus, Sonnet, GPT-OSS) — each with its own 5-hour and weekly window. An agent spends from exactly one pool, so any display must pick a pool from the agent's model. Verified: the numbers update *at turn end* (a one-word turn moved the 5-hour bucket `1.000000 → 0.998452`), so a mid-turn poll is genuinely one turn behind rather than merely theoretically so.

**Why it was cut.** The poll is a second `agy` invocation that spawns its own language server: measured **3.7–6.6s** and **~150–250 MB RSS**. Because an agent is marked idle only when its adapter event channel closes, awaiting the poll after `TurnEnd` keeps the agent visibly "processing" for that whole window — with a Stop button that is already a no-op post-terminal — on *every* successful turn. The two ways to avoid that both cost more than the gauge is worth on Switchboard's least-used harness: polling concurrently with the turn doubles peak `agy` processes per agent (2N during a burst across N agents) *and* gives up the freshness above, while moving the poll off the turn lifecycle requires the dispatcher's per-agent actor to own it — a change to the loop every agent's every message runs through.

**If it is ever revisited, the cheap shape is:** poll once when a project opens, driven from the app layer rather than the turn lifecycle. Zero per-turn latency, no shared-code change, gauge refreshes on open. Verified safe to run alongside a live turn — a concurrent poll and dispatch both exited 0, the poll attached to no conversation, and the turn's answer was unaffected.

**Adjacent, also unbuilt:** `/credits` answers structurally (`{"remaining_credits":N,"upgrade_uri":…}`) — the overage-credits product story is a separate question and was never in scope. `/context` is **interactive-only** in print mode (exit 2), so Antigravity's context bar has no possible source and its absence is a genuine ceiling rather than a decision.
